## 静态钉死的事实

### 1. 当前 stall stage 的资源落点

- 当前 stage 是：
  `segment=3 / local_stage=2 / globalStageId=5 / layer=5`
- live log 已明确：
  - `action=4 stage=2 layer=5 acc_util=2 split=2 gm0=4 dm0=4`
  - `worker stage=2 subbatch=0 begin op=1 acc=4 dma=4 tiles=2`
- 因此当前 export 的 pair manager 是：
  `mgr4`

### 2. 当前 stage 的 RR cfg 没有撞到 cfg15

- `rr_cfg_id_for_stage(stage=2, opcode=2)` -> `cfg4`
- `rr_cfg_id_for_stage(stage=2, opcode=3)` -> `cfg5`
- `cfg15`
  仍只保留给 SPM xlate

所以当前主链不是
`cfg15`
  静态别名问题。

### 3. compute-done 之后最可疑的是 C2 export，不是 entry cleanup

- stage2 entry 是：
  `tensor7 / SHARED_SPM / C4`
- stage2 export 是：
  `tensor8 / DRAM / C2`

`compute-done` 之后：

- entry cleanup 只改软件状态位，
  没有新的硬件指令
- export loop 会进
  `prt_process_c2()`
  并真正发 DMA / RR 握手

### 4. 当前 export 一定走同步 Linux host-copy 路径

- `prt_process_c2()` 中当前 `to_ring = 0`
- 所以 `allow_overlap = 0`
- 路径固定为：
  `prt_dma_copy_spm_pages_to_dram_prefix()`
  ->
  `dma_copy_spm_pages_to_host_linux()`

并且：

- 整个 export 批次先 acquire 一次共享 RR scope
- 每个 chunk 共用该 scope
- 最后才统一 release

## 本轮最重要的新结论

### 1. 这条路径上有 3 个“会真的把 CPU 卡住”的具体指令

不是泛泛的“可能卡在 DMA/RR”，
而是下面三类指令：

1. `hw_dma_fence()` 里的 DMA custom fence
   - `ROCC_INSTRUCTION_R_R_R(XCUSTOM_DMA, status, 0, 0, 3);`
   - 只有在 `GemminiCoupledDMA` 内部
     `!dmaBusy && !respValid`
     时才 ready
2. `prt_rr_fence_scope()` 对应的
   `rr_fence(cfg4)`
   - manager 只有在
     `inst_q.empty && !io.busy`
     时才回 `sUnbusyAck`
3. `prt_rr_release_scope()` 里的
   `rr_read_csr(RRCFG4)`
   - 这条 readback 会被
     `cfg_acq_state != s_idle`
     的 CSR stall 卡住，
     直到 manager 回 `sRelResp`

### 2. `prt_rr_release_scope()` 不是“fire-and-forget release”

裸 helper：

- `rr_release(cfg)`
  本身只是写 `RRCFG=0`

但 runtime wrapper：

- 写完之后立刻读回同一个 `RRCFG`

因此：

- 真正可能卡住的是后面的 `csrr RRCFGx`
- 这解释了为什么过去一些日志看起来像
  `rr_release`
  附近在“碰运气移动”

### 3. pair wrapper 的 busy 让 DMA-side RR fence/release 同时受 Gemmini busy 影响

硬件上：

- `GemminiCoupledDMAPairWrapper.io.busy =
   gemmini.busy || dma.busy`

所以对当前
`mgr4`
  来说：

- `rr_fence(cfg4)`
  / `rr_release_scope(cfg4)`
  等的不是 DMA4 单独 idle，
  而是 pair manager 4 整体 idle

### 4. 但 compute 侧“没 fence 到底”不是当前首要解释

stage2 的 compute 是
`oc split`
两 tile，
实际执行的是：

- 对 `mgr4` 调
  `conv_call_for_manager_sync_strided()`
- 对 `mgr5` 调
  `conv_call_for_manager_sync_strided()`

这个 sync 路径内部已经显式做了：

- `rr_fence_scope()`
- `gemmini_fence()`
- `flush_scope_after_drain()`
- `rr_release_scope()`

所以到
`compute-done`
时，
compute 侧 manager4/5
已经走过同步 drain/release。

这不能 100% 排除 residual busy，
但静态优先级上，
更该先怀疑：

- `DMA wait`
- `RR unbusy`
- `release readback`

而不是“compute 根本没等完”。

## 当前最合理的嫌疑顺序

按优先级排序：

1. `dma_blocking_wait()` 中的 `hw_dma_fence()`
2. 紧接着的 `prt_rr_fence_scope(cfg4)`
3. 所有 chunk/page 完成后的外层 `prt_rr_release_scope(cfg4)` 读回

## 为什么卡点会显得在移动

当前可以更准确地解释为：

- 根因不一定在移动
- 实际是同一条
  `stage2 export / mgr4 / cfg4`
  corridor
  里有多条不同的可阻塞指令
- 日志如果只覆盖粗粒度边界，
  最后看到的 frontier
  就会落在不同 marker 前后

所以过去看到的：

- `compute-done`
- `rrf-b`
- `rr_release_begin`
- `spm_xlate_restore_end`

更像是同一 corridor 的不同观测面，
不是完全不同的新根因。
