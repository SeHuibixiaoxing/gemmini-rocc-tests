[`src/prt_runtime.c`](/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/src/prt_runtime.c#L4864)

## 本轮静态结论

### 1. page28 自己的 DMA wait/fence/release 已经返回

因为 breadcrumb 已到
`DMA_PAGE_AFTER_ACCOUNTING`，
所以 page28 这一页的：

- `dma_submit_wait_annotated_scoped()`
- `dma_blocking_wait()`
- `hw_dma_fence()`
- 外层共享 scope 下的 `rr_fence(cfg0)`

都已经完成。

因此把当前 freeze 继续解释成：

- “page28 的 DMA fence 还没退”
- 或 “page28 的 RR fence 还没退”

静态上不成立。

### 2. page29 之前还有一条无 breadcrumb 的软件走廊

page28 `after_accounting` 之后，
下一页 page29 在真正 submit 前，会先走：

1. 纯算术地址/长度计算
2. `dma_trigger_export_host("pset")`
3. `dma_chunk_needs_bounce(...)`
4. direct path 上的
   `prt_host_virt_to_phys(dst_ptr, &dst_pa)`
5. 之后才会：
   - `req.src_addr = ...`
   - `req.dst_addr = ...`
   - `dma_breadcrumb_page_begin(...)`
   - `dma_submit_wait_annotated_scoped(...)`

所以当前 freeze 还不能直接写成：

- “page29 的 DMA submit 卡住”

### 3. 当前最强静态嫌疑已经切到 `prt_host_virt_to_phys()`

`src/prt_page_table.c`
中的 `prt_host_virt_to_phys()` 在 Linux/RISC-V 上会：

- 读取 `/proc/self/pagemap`
- `pread()` 当前 VA 对应的 pagemap entry
- 解 PFN 生成 PA

当前 export path 又没有像 fixed-load path 那样给它套 debug scope，
所以如果它卡在：

- `pread()`
- 或其前后的 guest 内核路径

现有 breadcrumb 正好会停在
`page28 after_accounting`
而不会再前进。

### 4. 次级嫌疑是 `v2p` error 之后的 outer scope release cleanup

如果 page29 的 `prt_host_virt_to_phys()` 很快返回 error，
代码会走：

- `goto done`
- `dma_batch_scope_release(&scope)`

而这个 release 会执行：

- `rr_release(cfg0)`
- 紧跟 `rr_read_csr(RRCFG0)`

这个读回是阻塞的 release-ack wait。

但当前没有新的 RR breadcrumb，
所以这条路径目前只保留为次级解释。

### 5. bounce path 不是当前主嫌

当前 runtime page 是 `1024B`。
page28 记录的：

- `src=0x40005c00`
- `dst=0x103b31400`
- `bytes=0x400`

说明 direct path 上
`src_mod64 == dst_mod64 == 0`。

page29 会保持相同 64B 对齐关系，
因此 `dma_chunk_needs_bounce()` 不应成立。
