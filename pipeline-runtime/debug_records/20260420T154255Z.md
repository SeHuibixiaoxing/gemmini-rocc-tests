## 新观察

### 1. `page29 before_v2p` 之前的源码路径非常短

对当前 `segment=0 stage=0 sb=3 tensor=2 mgr=0` 的 direct export path，
`page28 after_accounting` 之后直到 `page29 before_v2p` 之前，只剩：

- 地址/长度重算
- `dma_trigger_export_host("pset", ...)`
- `dma_chunk_needs_bounce(...)`

在这之前没有新的 DMA submit/wait，也没有新的 RR fence/release。

### 2. 当前 run config 下，这段走廊里缺少可信的“正常阻塞点”

- `debug_trigger_enable=0`，
  `prt_trigger_log_note()` 会在 very early path 直接返回
- `page29` 不是 sparse page probe 点
- `page29` 不是默认 chunk-marker 点
- 由 `page28` 的已知地址顺推：
  - `page29 src=0x40006000`
  - `page29 dst=0x103b31800`
  - `chunk=0x400`
  - `src_mod64 == dst_mod64 == 0`
  所以静态上不应 bounce

因此，若执行真的停在 `before_v2p(page29)` 之前，静态上并不好解释。

### 3. breadcrumb 证据被之前写重了

`decode_prt_breadcrumb.py --all` 只显示偶数 `seq` 的 stable slot。

但直接读原始 `breadcrumb.bin` 可见，两份 live capture 的 `slot14` 都不是零，而是相同的 odd torn state：

- `seq=503`
- `kind=dma`
- `phase=dma_submitwait_after_cleanup`
- `seg=0 gstage=0 lstage=0 sb=3`
- `tensor=2 mgr=0`
- `page=19`
- `tok=1176`

odd `seq` 说明抓取时该 slot 处于半写状态。

### 4. `slot14` 同时还是 `page29/token0` 的目标哈希槽

复算当前 hash 公式后确认：

- `page29/token0` page-level breadcrumb 也会写到 `slot14`
- `page19/token1176` 恰好哈希碰撞到同一槽

再结合 `slot key` 不包含：

- `phase`
- alias `target_seq`

得到的直接后果是：

- “当前 ring 里没有稳定的 `page29 before_v2p`”
  不能严格推出
  “控制流一定还没到 `page29`”

### 5. stage/hart 并发不是这轮局部 frontier 的主因

- segment 之间串行推进
- 当前分析对象是 `segment0`
- `segment0` 本身是单 stage
- stage worker 的 action/context 是线程局部

因此，这轮局部 frontier 不应再混入 `segment3` 多 stage 并发叙事。

## 本轮结论

- 当前仍可强说：
  这轮最后一个**稳定 even** breadcrumb 是
  `page28 dma_page_after_accounting`
- 但不能再把这条结论写成：
  “已经证明执行停在 `page29 before_v2p` 之前”
- 更准确的说法应改成：
  - 最后稳定 front 在 `page28 after_accounting`
  - `page29` breadcrumb 证据当前带 torn/collision 歧义
  - 如果执行真的还没到 `before_v2p(page29)`，那它会卡在一段静态上几乎没有正常阻塞调用的极窄走廊里

## 下一步

1. 若继续低扰动验证，优先设计一个**不复用 `slot14` 等价类**的新判别点。
2. 若继续靠 breadcrumb，必须同时解决：
   - `phase` 不入 hash
   - alias `target_seq` 不入 hash
   - live 抓取时可能出现 odd torn slot
3. 若需要更直接的执行位置证据，可考虑回到 `TraceV / workerpc` 这类看 PC 的路径。
