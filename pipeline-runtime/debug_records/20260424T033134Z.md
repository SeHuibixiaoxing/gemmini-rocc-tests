## 为什么我把怀疑点收敛到 `SimpleNICBridge.scala`

### 1. `simplenic_t` host 驱动假设 input/output token 是同拍推进的

从 `simplenic.cc` 和 `SimpleNICBridge.scala` 顶部注释可以看出：

- host 每次推入一批 host->NIC token
- 同时拉出一批 NIC->host token
- 这是一个严格对拍的 token 循环

`simplenic_t::tick()` 的写法也在强化这个假设：

- 先 `pull()` 一整批 FPGA->CPU token
- 再等 switch 产出同样一批 host->FPGA token
- 最后 `push()` 回 FPGA

它默认认为：

- 只要一批输出 token 到了
- 相应的一批输入 token 也应该被 target 侧消耗出空间

### 2. 但 `SimpleNICBridge.scala` 原始实现没有真正使用 `tFire`

原代码虽然定义了：

```scala
val tFireHelper = DecoupledHelper(hPort.toHost.hValid,
                                  hPort.fromHost.hReady)
val tFire = tFireHelper.fire()
```

但后面实际没有用这条“同拍 fire”约束来推进两边。

原实现是：

```scala
hPort.toHost.hReady := ntht_queue.io.enq.ready
ntht_queue.io.enq.valid := hPort.toHost.hValid
...
hPort.fromHost.hValid := htnt_queue.io.deq.valid
htnt_queue.io.deq.ready := hPort.fromHost.hReady
```

也就是说：

- target->host 输出 token 侧，按 `ntht_queue` 自己的 ready/valid 节奏走
- host->target 输入 token 侧，按 `htnt_queue` 自己的 ready/valid 节奏走

两边是“各自独立排队”的。

### 3. 这和别的 bridge 的实现风格明显不同

对照：

- `UARTBridge.scala`
- `TracerVBridge.scala`
- `BlockDevBridge.scala`

这些 bridge 都是：

- 先构造一个统一的 `fire` / `DecoupledHelper`
- 再让 `hPort.toHost.hReady` 和 `hPort.fromHost.hValid` 同时由这个 `fire` 驱动
- 桥内部 queue 的 enqueue/dequeue 也跟随同一个 fire

这保证：

- target 一拍只在“输入 token 和输出 token 都能被完整处理”时前进
- host/target 不会在 token 数量上漂移

而 `SimpleNICBridge.scala` 旧实现没有这个性质。

### 4. 这正好能解释 `simplenic_t` 看到的“写回 0 bytes”

一旦 bridge 两边允许独立推进，就可能发生：

- host 已经拉出了一批 NIC->host token
- 但 target 并没有按同样节奏真正消费同数量的 host->NIC token
- CPU-managed `from_cpu` stream 的 occupancy 逐步漂移并积累
- 最终 host 再次 `push()` 时，发现 FPGA 侧队列已经没有足够空间
- `push(..., required_bytes = full_batch)` 直接返回 `0`

这就会触发我们现场看到的：

```text
actually wrote in 0 bytes, wanted 58560 bytes
```

## 本轮修复

我已在：

- `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`

做了一个静态修正：
