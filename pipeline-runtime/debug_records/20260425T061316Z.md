这些值给出三个明确结论。

### 1. 先前怀疑的 `fromHost.hValid` 自闭锁已经被排除

上一轮修复的核心风险是：

- `hPort.fromHost.hValid` 依赖 `hPort.fromHost.hReady`
- 当全局 `fromHost.hReady=0` 时，SimpleNICBridge 自己也撤掉 `fromHost.hValid`

本轮新寄存器显示：

- `from_host_valid_drive=1`
- `hostport from_host(v=1 r=0)`

所以本轮失败时，SimpleNICBridge 已经持续向 HostPort 宣告 host->target token valid。

这说明原来的 `fromHost.hValid` 反向依赖问题已经不再是当前直接 blocker。

### 2. SimpleNIC 本地成对队列不是当前 blocker

本轮新寄存器显示：

- `local_queues_ready=1`
- `htnt_queue_deq_valid=1`
- `ntht_queue_enq_ready=1`
- `htnt=10`
- `ntht=0`

这说明：

- host->target 队列有 token 可出；
- target->host 队列有空间可入；
- 如果全局 target cycle 允许推进，SimpleNIC 本地队列边界可以完成一次成对交接。

因此，继续在 `htnt/ntht` 局部队列上加更多 snapshot 的收益已经很低。

### 3. 当前直接 blocker 是 HostPort/global target-cycle ready 没有抬起

本轮失败时：

- `target_cycle_ready=0`
- `hPort.toHost.hValid=1`
- `hPort.fromHost.hReady=0`
- `to_host_ready_drive=0`
- `from_host_valid_drive=1`

因此 `tFire=0` 的直接原因是：

- SimpleNIC 自己已经准备好；
- 但 HostPort 的 `fromHost.hReady` 仍为 `0`；
- 也就是全局 target-cycle finishing / host-port 聚合条件没有满足。

这个结论和上一轮静态审计一致：`fromHost.hReady` 是 HostPort 级聚合 ready，不是单独的 NIC input ready。

## 本轮结论

1. 新 no-Trace AGFI 确实被构建、同步、刷入并执行。
2. gdbserver smoke 仍在同一个早期 SimpleNIC push 路径失败，guest 没有进入 Linux/gdbserver 成功路径。
3. `SimpleNICBridge` 的 `fromHost.hValid -> fromHost.hReady` 自闭锁修复已经生效：失败时 `from_host_valid_drive=1`。
4. SimpleNIC 本地 `htnt/ntht` 队列不是当前直接 blocker：失败时 `local_queues_ready=1`。
5. 当前需要继续追的是 HostPort/global target-cycle 层面的 `fromHost.hReady=0` / `target_cycle_ready=0` 来源。
6. 由于本轮 AGFI 存在 post-route timing violation，不能把这次 FPGA 结果当作最终功能性证明；下一步最好先获得 timing-clean AGFI，或者把全局 target-cycle observability 加到下一颗 bitstream 中。

## 补充静态检查：no-Trace 只排除了 TracerV，不等于排除了全局项

检查本轮 no-Trace 生成物：

- `/home/ubuntu/chipyard/sims/firesim/deploy/results-build/2026-04-25--03-23-38-firesim_rocket_singlecore_nic_notrace_30mhz/cl_f2-firesim-FireSim-FireSimRocketNICNoTraceConfig-BaseF2Config/design/FireSim-generated.sv`

结论：

- `TracerV` / `tracerv` / `triggerCredit` / `triggerDebit` 无命中。
- `targetCycleFinishing` 仍是一个跨 bridge 的全局合取，包含：
  - AXI4 memory 通道
  - blockdev 通道
  - TSI 通道
  - UART 通道
  - SimpleNIC 的多组 sink/source 通道
  - reset/peek-poke 相关通道

关键片段位于生成物约 `160740..160820` 行：

- `_GEN_61` 聚合 source 侧的 ready/valid fired 条件；
- `targetCycleFinishing = _GEN_61 & ...` 继续合入多组 sink valid；
- 其中明确包含 `ep_2_axi4_*`、`ep_bdev_*`、`ep_4_tsi_*`、`ep_1_uart_*`、`ep_3_nic_*`。

因此：

- no-Trace 配置已经排除了 `TracerVBridge` 对这条链的直接影响；
- 但当前 `fromHost.hReady=0` 仍不能归因到 SimpleNIC 自身；
- 下一颗观测 bitstream 应拆分这些全局项，而不是继续只在 SimpleNIC 内部加寄存器。

## 后续建议

下一轮不要再优先扩 SimpleNIC 局部队列寄存器。更有价值的观测点应放在跨 bridge/global 层：

- 暴露 `targetCycleFinishing` 的主要 AND 项分解；
- 或至少暴露每个 bridge HostPort 的 ready/valid blocker；
- 特别是 AXI4 memory / blockdev / TSI / UART / SimpleNIC 在同一拍对 target cycle finishing 的贡献。

如果继续用 FPGA 验证，应优先处理 timing：

- 尝试更小/更低频/更少 bridge 的 config；
- 或调整构建策略直到 post-route 不再生成 `VIOLATED.dcp`。

`+simplenic-relaxed-required-bytes=1` 可以作为软件侧补充实验，用于区分“完全 0 字节进展”和“有部分 token 但达不到整批阈值”。不过本轮已经看到 `from_cpu_stream count=3072 space_available=0`，所以最强证据仍指向 target-cycle/global ready 没有放行。
