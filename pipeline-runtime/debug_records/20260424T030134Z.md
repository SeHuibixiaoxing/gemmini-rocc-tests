调试类别：main

本轮围绕 `pipeline-runtime` 的 `gdbserver` host-side 网络准备路径做静态排查，目标是回答一个关键问题：

- 为什么最近几轮 `cfg32 + NIC` bitstream 上，`runworkload` 的 switch 行为看起来不稳定，
  甚至会出现“这轮 `infrasetup` 生成的是一个 switch，实际 run 里启动的像是另一版 switch”的现象

结论先写在前面：

- 这不是 `SimpleNIC` RTL 本身先天不稳定的第一嫌疑点
- 目前更直接的根因在 `prepare_firesim_networked_gdbserver.sh`
- 该脚本原先按 `find | sort` 的字典序去挑 `switch0-*-build`
- 但这些目录后缀是随机 disambiguator，不表示时间先后
- 因此 `run` 前的 network-prepare 很容易 patch 到一版历史旧 switch build，
  再把这版旧二进制 scp 到 run host
- 结果就是：
  - `infrasetup` 这轮刚生成/下发的 switch
  - 与 `run` 阶段真正被 `SSHPort` patch 并重新下发的 switch
  并不一定是同一版

## 这次对了哪些证据

### 1. FireSim 文档和仓库现有 SOP 都说明：gdbserver 不是默认 switch 路径

本地文档：

- `/home/ubuntu/chipyard/sims/firesim/docs/Advanced-Usage/Miscellaneous-Tips.rst`
- `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/docs/testing/gdbserver_integration_sop.md`

两边都明确写了同一个事实：

- `example_1config` 默认只给单节点准备基础 networked topology
- 如果目标是 host 侧通过网络进入 guest，
  需要把 `switchconfig.h` 改成带 `SSHPort(1)` 的版本
- 然后还要在 run host 上准备 `tap0`

所以 `gdbserver` 路线天然分成两段：

1. `infrasetup` 先生成一版 stock switch
2. `run` 前 workflow 再把它改写成 `SSHPort` 版

这本身没有问题，前提是“第二步改写的是第一步刚生成的那一版”。

### 2. 当前 workflow 的 network-prepare 确实会在 `run` 前自动改 switch

检查：

- `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/scripts/pairdummy_sbus128_workflow.sh`
- `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/scripts/prepare_firesim_networked_gdbserver.sh`

关键链路：

- `pairdummy_sbus128_workflow.sh run`
  会在 `gdbserver + example_1config` 模式下调用
  `maybe_prepare_networked_gdbserver`
- 这会执行：
  `prepare_firesim_networked_gdbserver.sh <private-ip>`

也就是说，`runworkload` 之前的 host-side switch 确实不是完全静态的，
而是会被 workflow 二次改写。

### 3. 脚本原来的“最新 switch build”判断是错的

排查脚本原逻辑时看到：

```bash
mapfile -t switch_build_dirs < <(
  find "${switch_root}" -maxdepth 1 -mindepth 1 -type d -name 'switch0-*-build' | sort
)
latest_index=$(( ${#switch_build_dirs[@]} - 1 ))
switch_build_dir="${switch_build_dirs[${latest_index}]}"
```

问题在于：

- `switch0-*-build` 后缀不是时间戳
- 它是随机串
- `sort` 只是在做字典序排序
- “最后一个”并不等于“最新”

因此这个脚本会系统性地把“随机串字母更靠后”的老目录当成“最新目录”。

### 4. 这和本轮现场现象完全对上

本轮证据里有两个关键 build 目录：

- `switch0-F4VA...-build`
- `switch0-UTY0...-build`

对应关系如下。

`2026-04-24 02:24:40` 这轮 `infrasetup` 日志明确显示：

- 新建并构建的是 `switch0-F4VA...-build`
- 其 `switchconfig.h` 是 stock `example_1config`：
  - `NUMPORTS 1`
  - `NUMDOWNLINKS 1`
  - `NUMUPLINKS 0`
  - `ports[0] = new ShmemPort(...)`
- 然后它被下发到：
  `/home/ubuntu/switch_slot_0/switch0`

但本轮 `runworkload` 结果目录里的 `switchlog` 又明确显示：

- `Slot ID not specified. Assuming tap0`

这条字符串只会来自：

- `/home/ubuntu/chipyard/sims/firesim/target-design/switch/sshport.h`

也就是说，真正启动的 switch 带了 `SSHPort`。

再看本地 build 目录时间：

- `switch0-UTY0...-build/switchconfig.h` 在 `2026-04-24 02:27:52 UTC` 被改写
- 它随后在 `02:27:53 UTC` 被重新编译
- 其内容正是：
  - `NUMPORTS 2`
  - `NUMDOWNLINKS 2`
  - `ports[1] = new SSHPort(1);`

而 `UTY0...` 这版目录最早是当天 `02:09` 另一轮 `infrasetup` 生成的旧目录，
只是因为 `U` 在字典序里比 `F` 更靠后，
所以被旧脚本误选成了“latest”。

这就把所有看似矛盾的现象串起来了：

1. `02:24` 这轮正式 `infrasetup` 生成的是 `F4VA...`
2. `02:27` `run` 前的 network-prepare 却按字典序挑中了历史 `UTY0...`
3. 脚本把 `UTY0...` patch 成 `SSHPort` 版并重新 scp 到 run host
4. 最终 run host 启动的 switch 不再是本轮刚下发的 `F4VA...`
5. 于是从日志上看，就像“switch 行为漂移/这轮不是上一轮那版”

### 5. 这能解释为什么这条路径调起来像“碰运气”

只要本地 `target-design/switch/` 下积累了多轮 `switch0-*-build`：

- 旧脚本就不保证每次 patch 到的是当前这轮 `infrasetup` 刚生成的目录
- 它会受到随机目录名字母顺序影响

于是同样的 runtime/hwdb/workload 组合下，
网络准备步骤实际使用的 switch 二进制可能来自完全不同的一轮历史构建，
这会直接污染：

- `switchconfig.h`
- `MACPORTSCONFIG`
- 是否包含 `SSHPort`
- 乃至本轮对当前 bitstream / 当前 workflow 的判断

这就是这条 host-side gdbserver 网络路径“看起来不够确定”的一个真实来源。

## 与上游 issue / 文档的关系

上游背景也支持这个判断：

- FireSim 文档把
  “ssh into simulated nodes / access internet”
  放在 `Experimental Support` 章节
- 上游 `firesim/firesim` issue 里，单节点 NIC / SSH 路径也长期不是最稳的默认主线
  例如：
  - `#429 Help : how to run boom with nic`
  - `#1807 Enable ssh over FireSim simulations`

所以当前更合理的策略不是先怀疑 NIC RTL，
而是先把 host-side `SSHPort` switch 准备流程做成**确定且可重复**。

## 当前结论

当前 `gdbserver` 路线最直接的静态 bug 是：

- `prepare_firesim_networked_gdbserver.sh`
  误把随机目录名字典序最后一个 build 当成“最新 switch build”

这会导致：

- `run` 阶段 patch / 下发的是历史旧 switch
- 而不是本轮 `infrasetup` 刚生成的 switch

因此：

- 近期 `gdbserver` / `switch` 现象中的一部分“漂移感”
  是由这个 host-side workflow bug 造成的
- 在修掉这个 bug 前，
  继续从这些 run 现象反推 `SimpleNIC` / guest 网络是否稳定，结论会混杂环境噪声

## 下一步建议

1. 先修 `prepare_firesim_networked_gdbserver.sh`：
   改为按修改时间选最新 `switch0-*-build`
2. 重新生成记录并固定索引
3. 下一轮若继续走 `gdbserver`：
   必须保证这次 patch 到的是当前 `infrasetup` 刚生成的 switch
4. 在这条 host-side选择 bug 修掉后，
   再看 `simplenic_t::tick()` 的 token mismatch 是否仍然存在；
   那样得到的才是更干净的 NIC 证据
