## 新观察 / 新卡点

### 1. 当前 run 没有卡回 boot ROM；它在用户程序 prefill

live gdb 读 Verilator root frame 得到：

- hart0：
  - `wb/mem/ex/ibuf` 落在 `0x80002354 ~ 0x80002364`
- hart1：
  - `wb/mem/ex/ibuf` 落在 `0x80002030 ~ 0x80002034`

反汇编对应：

- hart0 在 `thread_entry` 里的 `fill_pattern(stage0_src, ...)` 循环
- hart1 在 `barrier_wait.constprop.0` 的自旋等待循环

因此，这轮不是“又回到 boot ROM `wfi`”。

### 2. 之前把循环上界看成 `0x8000` 是误读；真实上界是 `0x80000`

反汇编关键片段：

- `0x80002350: lui a0,0x80`
- `0x80002364: bne a4,a0,0x80002354`

这表示循环终点是：

- `a0 = 0x00080000 = 524288`

而不是之前容易看错的 `0x8000`。

结合源代码：

- `REROCC_EXPORT_STAGE0_BYTES = 512 * 1024`
- `REROCC_EXPORT_STAGE1_BYTES = 64 * 1024`
- `fill_pattern()` 是逐字节 LCG 填充

所以 marker 前的静默窗口本来就非常长。

### 3. `metasim_stderr.out` 现在已经是活的退休指令流，可直接回答“卡在哪条指令”

本轮最关键的新证据不是新日志，而是：

- `tail /home/ubuntu/sim_slot_0/metasim_stderr.out`
  已经连续出现：
  - `C0 pc=0x80002354/58/5c/60/64`
  - `C1 pc=0x80002030/32/34`

其中典型样本：

- `C0 ... pc=[000000008000235c] W[r14=... ]`
  说明 hart0 的 `a4` 循环计数器在递增
- `C1 ... pc=[0000000080002032]`
  / `pc=[0000000080002034]`
  说明 hart1 正在 `while (barrier_epoch == epoch)` 自旋

这已经能直接回答“用户程序卡在哪条指令”：

- hart0 当前卡在 `fill_pattern(stage0_src)` 的 5 条短循环
- hart1 当前卡在 `barrier_wait()` 的 3 条短循环

### 4. 当前不是死锁，而是“很慢但在前进”

从 `metasim_stderr.out` 做一分钟双采样：

- `2026-04-19T07:47:21Z`
  - `C0 ... pc=0x8000235c W[r14=0x000000000001794a]`
- `2026-04-19T07:48:21Z`
  - `C0 ... pc=0x8000235c W[r14=0x0000000000018041]`

可见 hart0 的循环计数从：

- `0x1794a -> 0x18041`

一分钟内前进了：

- `0x6f7 = 1783`

因此当前 run 不是停死，而是在慢速推进 stage0 prefill。

### 5. `TRACEFILE-C0/C1 == 0` 仍然是预期行为

源代码里 start marker 在：

- `run_stage0_segment3_case()`
  中的 `rerocc_seg3_tracerv_start_marker()`

而 `thread_entry()` 的执行顺序是：

1. `fill_pattern(stage0_src, 512 KiB)`
2. `fill_pattern(stage1_src, 64 KiB)`
3. `barrier_wait()`
4. 进入 `run_stage0_segment3_case()`
5. 才执行 start marker

当前 hart0 仍在第 1 步，所以：

- `TRACEFILE-C0 = 0`
- `TRACEFILE-C1 = 0`

是符合配置语义的，不是新的硬件死锁证据。

## 分析

- “卡点总在移动”的根因不是随机性，也不是 reset / TSI / CLINT 又出了新问题。
- 真正的根因是：
  - 我们之前把 marker 前的长 prefill 窗口低估了；
  - 同时又把不同观察面混在了一起。
- 这导致了两个误判：
  1. 把旧的 / 稀疏的 `uartlog` 或早期尾部输出，当成当前 PC
  2. 把同一个长 prefill 循环里的不同采样点，误记成“卡点又后移 / 又前移”

本轮可以明确下结论：

- 当前 active run 真实状态是：
  - hart0：`fill_pattern(stage0_src)` 慢速推进
  - hart1：`barrier_wait()` 等待 hart0
  - start marker 尚未执行
- 所以当前最该修的“根因”不是继续加日志，
  而是：
  - **改变 TraceV 验证策略，让 marker 更早或 prefill 更短**

按本轮采样速率粗估：

- stage0 剩余：
  `0x80000 - 0x18041 = 0x67fbf`
- 再加 stage1：
  `0x10000`
- 剩余总 prefill 约：
  `0x77fbf = 491455`
  次迭代
- 若仍按 `~1783 iter/min`，
  到 start marker 还需要约：
  `275.6 min ≈ 4.6 h`

这也是为什么继续守着当前 full-size repro，短时间内看不到 `TRACEFILE` 非零。
