## 新观察

### 1. 这轮 `runworkload=1` 的直接原因不是 guest 显式失败，而是实例回收后 manager 再次 SSH 轮询失败

- `runworkload` 尾部直接报：
  `paramiko.ssh_exception.SSHException: Error reading SSH protocol banner`
- 触发点在：
  FireSim manager 对 `192.168.1.243` 执行 `monitor_jobs_wrapper -> running_simulations -> screen -ls`
  时，目标实例已经不再正常提供 SSH banner。
- 同时 host watchdog 在更早时刻已经执行：
  - capture
  - `terminaterunfarm --forceterminate`
- 因而这轮 manager 的 `exit 1`
  不能直接解释成 guest `pipeline-runtime` 自己返回 nonzero。

### 2. 当前最强系统级信号是：heartbeat 长时间继续推进，但 watchdog 不把它算作 progress

- watchdog arm 后记录到：
  - `hb='10743729197, 586'` 时 `guest_sparse=319955`
  - 之后 heartbeat 一直推进到
    `hb='23130797908, 1206'`
  - 但 `guest_sparse` / `guest_log` / `guest_status` 等大小都不再变化
- `scripts/firesim-prt-host-watchdog.sh`
  当前只把这些文件增长视为 progress：
  - `uart`
  - `guest_log`
  - `guest_sparse`
  - `guest_status`
  - `guest_runner*`
  - `guest_checkpoint`
  - `guest_trigger`
- `heartbeat.csv` 只被打印进日志，
  不会刷新 `last_progress_epoch`
- 最终 watchdog 以：
  `host idle timeout reached after 625s`
  主动抓取 capture 并回收 runfarm。

### 3. 当前 `guest_sparse` plateau 不是 authoritative stall 证据

- capture sparse tail 已经出现：
  - `stage-exec-views phase=end segment=0 stage=0 layer=0 rc=0 flush=1`
  - `worker stage=0 subbatch=3 begin op=1 acc=0 dma=0 tiles=4`
  - `conv-sync-strided stage=0 mgr=0 acquired`
  - `conv-sync-strided stage=0 mgr=0 flushed use_pointwise=1`
  - `conv-sync-strided stage=0 mgr=1 begin`
- 末尾 `mgr=1 begin` 是半行截断，
  不能当作精确停点。
- breadcrumb `--all` 又给出更靠后的直接证据：
  - `sb=3 mgr=0 rr_release_end`
  - `sb=3 mgr=0 gemmini_pointwise_postcall_release_return`
  - `sb=3 mgr=1 rr_release_end`
  - `sb=3 mgr=1 gemmini_pointwise_postcall_release_return`
  - `sb=3 mgr=2 rr_acquire_after_call`
- 这说明当前观测前沿至少已经越过
  `mgr0`，
  也大概率越过
  `mgr1` pointwise 返回边界；
  不能再把 sparse 半行尾巴当成真实 blocker。

### 4. 当前 fixed profile 下，pointwise 热路径后的 sparse 静默本来就是设计结果

- 当前 profile 保留 breadcrumb，
  但关闭：
  - `PIPELINE_RUNTIME_PROGRESS_HOT`
  - `PIPELINE_RUNTIME_CRITICAL_UART_PROBE`
  - `PIPELINE_RUNTIME_GUEST_DEEP_LOG_ENABLE`
- `prt_should_emit_pointwise_sparse_progress()`
  在 breadcrumb enabled 时会关闭 pointwise coarse sparse progress。
- 所以在 `use_pointwise=1` 的热路径里，
  出现
  `heartbeat` 继续前进而 `guest_sparse` 长时间不增长，
  本身并不等价于 compute 没在跑。

### 5. `g6` artifact 已经切到 `6 gemmini / 6 dma`，但 `cfg15` 与 xlate 的静态别名风险并没有因此消失

- g6 fixed env 明确设置：
  - `NUM_GEMMINI=6`
  - `NUM_DMA=6`
- g6 manifest / hardware target 也明确写着：
  - `num_gemmini: 6`
  - `num_dma: 6`
- 但 `prt_rerocc.c` 中 RR cfg 分配逻辑是：
  - `RR_MAX_CFGS = 16`
  - `PRT_RR_SPM_XLATE_CFG_ID = 15`
  - `rr_cfg_id_for_stage(stage_id, opcode_id) = ((stage_id * 2) + lane) % 16`
- g6 pipeline mapping 静态展开后仍有：
  - `globalStageId` 覆盖到 `39`
- 因而对 `opcode_id=3` 的 Gemmini 路径，
  `cfg15` 会被这些 stage 复用：
  - `stage_id = 7, 15, 23, 31, 39`
- 结论：
  把 workload 从旧 mapping 切到 `g6`
  只解决了 artifact 层面的 Gemmini 数量，
  **没有自动解决**
  `cfg15` 被 xlate 固定占用、同时又被 stage-based opcode3 取模复用
  的静态 alias 风险。

## 分析

### 1. 这轮当前最强结论是“host watchdog 误杀风险”，不是“guest 已被证明卡死”

- 证据链完整闭合：
  1. watchdog 只认 guest 文件大小增长
  2. heartbeat 连续推进 600s+
  3. fixed profile 下 pointwise 热路径本来就可能 sparse 静默
  4. watchdog 仍按 `idle=625s` 回收实例
  5. manager 最终只是在实例回收后再次 SSH 失败
- 所以这轮最应该先修的不是 guest 热路径再加日志，
  而是 host watchdog 与当前 breadcrumb-first 调试策略之间的语义错配。

### 2. “卡点看起来在移动”在这轮里再次体现为：不同观测面截到了不同前沿

- sparse 给到的只是半行尾部：
  `mgr1 begin`
- breadcrumb 又显示：
  `mgr1 pointwise_postcall_release_return`
  甚至 `mgr2 rr_acquire_after_call`
- 这再次说明：
  当前 authoritative frontier 不能只取某一份 sparse 文件尾。

### 3. `cfg15` alias 是第二优先级静态风险，但目前还不能拿它解释这轮为什么结束

- 它是一个真实存在的静态设计风险，
  而且 `g6` 并没有消掉它。
- 但就本轮现有直接证据而言，
  当前 run 是先被 watchdog timeout 回收；
  在 watchdog 误杀没有排除前，
  还不能把这轮结束主因直接归到 `cfg15` alias。
- 更合理的顺序是：
  先让下一轮 run 不被 watchdog 过早回收，
  再观察是否还会在更靠后的 stage/thread 窗口暴露 `cfg15` alias 症状。

## 本轮结论

- 当前 `g6 bertmini` 这轮最稳的结论是：
  **host-watchdog 的 idle 语义与当前 breadcrumb-first / pointwise-silent profile 冲突，存在明显误杀风险。**
- `runworkload` 的 `exit 1`
  不是 guest 自身失败的充分证据；
  它是实例被回收后 manager 再次 SSH 失败。
- 当前 `guest_sparse` plateau
  不是 authoritative frontier；
  breadcrumb 已经证明前沿比 sparse 尾部更靠后。
- `g6` 虽然把 artifact 改成 `6 gemmini / 6 dma`，
  但 `cfg15` / xlate / opcode3 的静态 alias 风险仍然存在，
  需要在排除 watchdog 误杀后继续验证。
