## 本轮静态结论

### 1. 软件层面不是强制“一 stage 一 hart”

- `stage_worker_main()`
  入口会先调用
  `stage_bind_current_thread()`
- `stage_bind_current_thread()`
  通过
  `pick_affinity_cpu(exec->stage_acc_ids[stage], &target_cpu)`
  选择目标 CPU
- `pick_affinity_cpu()`
  的逻辑是：
  - 枚举当前线程允许使用的 CPU 集合
  - 用
    `preferred_idx % allowed_count`
    选目标 rank

因此：

- 当可用 CPU 数量足够时，
  不同 stage 通常会被分散到不同 hart
- 但当 `allowed_count` 变小，
  不同 stage 仍可能因为取模碰撞落到同一 hart

### 2. 同 hart 的真实风险不是“custom opcode 槽不够”

- ReRoCC client 是 hart/tile 侧的 `LazyRoCC`
- 同一 hart 上共享一套：
  - `RROPC0..3`
  - `RRCFG0..15`
  - `RRBAR`
  - `cfg_acq_state`
  - `io.cmd`
- 因此如果多个 stage 真跑在同一 hart：
  - 指令本身仍是单 hart 串行发出
  - 但会共享同一套 hart-local CSR / client state
  - `rr_set_opc()` 可能互相覆盖
  - `RRCFG` acquire / release / readback 可能互相 stall
