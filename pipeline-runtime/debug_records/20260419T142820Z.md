## 新观察

### 1. 旧 blocker 的确已经被越过

- 本轮 sparse log 已经明确越过上一轮 authoritative frontier：
  `spm-xlate-release ... phase=restore-begin`
- 新 tail 真实停在：
  `spm-xlate-release mgr=7 cfg=15 phase=fence-end prev_opc3=0x1`
- 因而 `prt_rr_release_scope()` 中新增的
  `rr_release(cfg) + rr_read_csr(CSR_RRCFGx)` 修正是有效的；
  它确实把主线从旧的 `restore-begin` 风险窗口推进过去了。

### 2. 这次 breadcrumb 与 sparse log 不一致，不是因为 sparse log 一定错，而是 breadcrumb 对这条路径本来就有盲区

- `decode_prt_breadcrumb.py --all` 的最新有效 slot 仍然落在：
  - `dma_page_end page=63`
  - `rr_release_end sb=4 mgr=0`
- 但静态阅读 `src/prt_runtime.c` 后确认：
  `stage_prepare_exec_views()` 内部调用
  `runtime_flush_stage_spm_xlate()` 时，
  **外层并没有先调用**
  `prt_log_gate_set_context(segment, global_stage, local_stage, ...)`。
- 当前 fixed profile 又把 breadcrumb 过滤钉在：
  - `segment=0`
  - `global_stage=0`
  - `local_stage=0`
  - `subbatch=any`
- `prt_breadcrumb_note()` 会先读 `prt_log_gate` 上下文；
  若 context 还没设好，
  `segment/global_stage/local_stage` 会退回 `ANY`，
  然后被 breadcrumb filter 直接拒掉。
- 这意味着：
  **`stage_prepare_exec_views()` 里的 `spm-xlate` breadcrumb 实际上会被静默丢弃。**
- 所以这轮里 `last_slot=rr_release_end` 并不能反驳 sparse log 的
  `mgr=7 fence-end`；
  它只是说明我们当前 binary breadcrumb 没覆盖到这条准备阶段的 `spm-xlate` 路径。

### 3. 当前 “fence-end -> release-begin” 只是 coarse frontier，不足以直接下结论为“卡在这两行之间”

- `prt_spm_xlate_release_scope()` 静态顺序是：
  1. `rr_fence(scope->cfg_id)`
  2. breadcrumb `SPM_XLATE_RELEASE_FENCE_END`
  3. `PRT_PROGRESS_LOG(... phase=fence-end ...)`
  4. breadcrumb `SPM_XLATE_RELEASE_BEGIN`
  5. `PRT_PROGRESS_LOG(... phase=release-begin ...)`
  6. `prt_rr_release_scope(scope)`
- 因而当前 capture **只能**说明：
  - `rr_fence(cfg15)` 已返回；
  - `fence-end` 这条 coarse log 已经落盘；
  - 后续没有新的 coarse log 被捕获。
- 但它还不足以把真正阻塞点精确落到：
  - `breadcrumb note`
  - `release-begin progress log`
  - `rr_release(cfg15)`
  - `rr_read_csr(CSR_RRCFG15)`
  这几者中的某一个。

### 4. “卡点移动”仍然是同一类问题的不同观测切面，不是随机碰运气

- 第一层移动来自协议语义：
  - `rr_release()` helper 原先返回过早；
  - 普通代码/普通日志可以越过 release request；
  - 下一条 RoCC-sensitive CSR / `fence` 会再被 ReRoCC client `io.busy` 挡住。
- 第二层移动来自观测面差异：
  - sparse 文本日志只能看到“写到文件并被周期性 `sync` 刷回 guest image”的边界；
  - breadcrumb 能看到更细 phase，但前提是 log-gate context 必须已设好；
  - 当前这条 `stage_prepare_exec_views -> runtime_flush_stage_spm_xlate`
    路径恰好缺了 context，因此 breadcrumb 对它失明。
- 所以“这次没到上次位置、上次又没到这次位置”不是随机，
  而是：
  **同一条主线在不同协议窗口、不同观测面上被截到了不同前沿。**

## 本轮结论

- 当前最稳的结论不是“新硬件 blocker 一定在 `fence-end -> release-begin` 之间”，
  而是：
  1. 旧 `restore-begin` blocker 已被越过；
  2. 新 authoritative coarse frontier 在
     `stage_prepare_exec_views()` 的第二轮
     `spm-xlate-release mgr=7 cfg=15 phase=fence-end`；
  3. 当前 breadcrumb 对这条路径有已确认的 context 盲区，
     不能再继续拿 `last_slot` 直接对冲 sparse frontier。
