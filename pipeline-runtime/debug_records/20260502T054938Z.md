## 结论

`agfi-0222b9995be0d673e` 不能作为 gdbserver/NIC 功能判据。

原因不是 guest Linux、gdbserver、tap/SSH tunnel 或 workload 脚本：

1. driver-debug run 已证明目标至少能推进到约 3.13e8 target cycles；
2. 失败点是 FireSim master/clock/peekpoke OCL register surface 同时从有效 magic
   变为全 0；
3. 对应 AGFI 有明确 post-route timing violation，且 AWS 脚本把 DCP 标成
   `.VIOLATED.dcp`。

因此这轮“target cycle 0”只是 OCL 寄存器归零后的二次症状，不是目标一开始没有启动。

## 与 8BP 线的关系

8 个 Rocket hardware breakpoint/watchpoint 资源不是当前阻塞点：

- `FireSimRocketNICNoTrace8BPConfig` 只是在 `FireSimRocketNICNoTraceConfig` 前增加
  `WithNBreakpoints(8)`。
- 历史 8BP AGFI 也存在 `.post_route.VIOLATED.dcp`，且 F2 上出现过 cycle0 deadlock、
  prelaunch stall、early exit 等不稳定现场。
- Buildroot/RISC-V `gdbserver` 已实测不支持当前链路下的 `hbreak` / hardware
  watchpoint；pipeline-runtime 调试主路径依赖的是软件断点、线程栈、寄存器、内存读写、
  Ctrl-C 抢回控制。

## 下一步

1. 不再用 `agfi-0222b9995be0d673e` 继续判断 gdbserver 功能。
2. 构建新的当前源码 single-core NIC no-Trace AGFI 时优先使用 `TIMING` 策略；
   启动 Vivado 后必须再次核对远端 generated Verilog/driver 字符串包含最新改动。
3. 新 AGFI 只有在不出现 `.post_route.VIOLATED.dcp` 或至少 F2 不再出现 OCL 控制面归零后，
   才进入 remote gdbserver 能力回归。
4. remote gdbserver 回归的通过标准：
   - `target remote` 成功；
   - 多个软件断点可设置并命中；
   - `continue`、`next`、`Ctrl-C` 抢回控制、`info threads`、
     `thread apply all bt`、寄存器读取、反汇编、变量/内存读写、线程/frame 切换、
     `detach` 与 20260501T045108Z 的能力矩阵一致。
