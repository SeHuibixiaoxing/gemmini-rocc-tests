## 新观察

### 1. `rr_cfg_id_for_stage()` 现在吃到的是当前 active segment 内的 local `stage_id`

- worker thread 创建时：
  `exec->stage_threads[i].stage_id = i`
- host-serial 路径里：
  `for (uint32_t stage_id = 0; stage_id < seg->num_stages; ++stage_id)`
- `conv_call_for_manager_sync_strided()` /
  `conv_call_for_manager_nb()` 等 Gemmini 路径把这个 local `stage_id`
  直接传给：
  `prt_rr_acquire_scope(..., stage_id, manager_id, 3U, ...)`
- `prt_rr_acquire_scope()` 再调用：
  `rr_cfg_id_for_stage(stage_id, opcode_id)`
- 因而这里参与 cfg 映射的是：
  **segment-local stage index**
  而不是 artifact 里的 `globalStageId`

### 2. `globalStageId` 当前主要用于 log gate / observability，不用于 RR cfg 映射

- `runtime_stage_global_id(action, local_stage_id)`
  只是从当前 segment 的 `stages[local_stage_id].stage_id`
  取出 artifact 里的全局编号
- 这一路随后用于：
  - `prt_log_gate_set_context(...)`
  - trigger / breadcrumb / deep-log 过滤
- 它没有被传进 `rr_cfg_id_for_stage()`

### 3. 当前 g6 artifact 每个 segment 的 local stage 数最大只有 4

- 对
  `pipeline_mapping...g6...ours2.yaml`
  的静态展开结果：
  - segment local stage count 分别为
    `1,1,1,3,3,2,1,1,3,1,2,2,1,3,1,4,1,1,3,2,2,1`
  - 最大值为 `4`
- 因而当前 g6 下，普通 stage-based `opcode3`
  实际只会命中：
  - local `stage_id=0 -> cfg1`
  - local `stage_id=1 -> cfg3`
  - local `stage_id=2 -> cfg5`
  - local `stage_id=3 -> cfg7`
- 不会因为存在 `globalStageId=39`
  就命中 `cfg15`

### 4. 当前真正成立的静态风险是“未来若某个 segment 升到 8+ local stages，才会碰到 `cfg15`”

- `RR_MAX_CFGS = 16`
- `PRT_RR_SPM_XLATE_CFG_ID = 15`
- `rr_cfg_id_for_stage(stage_id, opcode_id) = ((stage_id * 2) + lane) % 16`
- 对普通 `opcode3`，
  要命中 `cfg15` 需要：
  `((stage_id * 2) + 1) % 16 = 15`
- 也就是 local `stage_id = 7`
- 所以当前正确说法应是：
  **只要某个 active segment 的 local stage 数达到 8，普通 stage scope 才会静态撞上保留给 xlate 的 `cfg15`。**

  不是 `globalStageId` 导致的 `cfg15` 静态碰撞。

  若未来 artifact 出现 `8+` local stages 的 segment，
  当前普通 stage-based `opcode3` 映射仍可能打到 `cfg15`。
