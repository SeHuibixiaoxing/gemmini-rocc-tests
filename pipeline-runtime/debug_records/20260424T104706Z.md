## 静态审计一：`SimpleNIC` host driver 的硬前提

### 1. `LINKLATENCY=6405` 会被换算成 `SIMLATENCY_BT=915`

代码：

- `/home/ubuntu/chipyard/generators/firechip/bridgestubs/src/main/cc/bridges/simplenic.cc`

关键关系：

- `TOKENS_PER_BIGTOKEN = 7`
- `SIMLATENCY_BT = LINKLATENCY / TOKENS_PER_BIGTOKEN = 6405 / 7 = 915`
- 每个 big token 是 `64` 字节
- 所以每轮 bulk 交换是 `915 * 64 = 58560` 字节

也就是说，当前 `SimpleNIC` host driver 的基本执行单位不是“单个 token”，而是“一整轮 915 个 big token”。

### 2. init 会先往 `from_cpu` 预塞 915 个 big token

同文件 `simplenic_t::init()`：

- 会先检查 `to_cpu` 是否为空
- 然后往 `from_cpu` 一次性 `push` `915 * 64 = 58560` 字节

这一步的目的不是传真实网络包，而是先给 target-side NIC-local 时钟域垫出一个初始的 link latency 窗口。

### 3. steady-state `tick()` 只接受“整批 915 个 big token”

同文件 `simplenic_t::tick()`：

- `pull(... requested_token_bytes, requested_token_bytes)`
- `push(... BUFWIDTH * tokens_this_round, BUFWIDTH * tokens_this_round)`

这里 `required_bytes == requested_bytes`，不是“尽量多拉/多推”，而是：

- 要么一整批 `915` 个 big token 都满足
- 要么这轮直接不做

所以当前 host driver 的行为本质上是：

- 只要 `to_cpu` 队列里小于 `915`
- 这一轮就完全不 `pull`

这与 FireSim 文档里“NIC driver moves tokens in bulk”是一致的，但它也意味着只要 target-side 两个方向的 token 不是严格按同一节拍推进，就可能积累出漂移。

## 静态审计二：`CPUManagedStream` 的 `count` 含义不是猜测，是 FPGA 队列 occupancy

关键代码：

- `/home/ubuntu/chipyard/sims/firesim/sim/midas/src/main/scala/midas/core/CPUManagedStreamEngine.scala`
- `/home/ubuntu/chipyard/sims/firesim/sim/midas/src/main/cc/bridges/cpu_managed_stream.cc`
- `/home/ubuntu/chipyard/sims/firesim/sim/midas/targetutils/src/main/scala/midas/Utils.scala`

结论：

- `count_addr` 对应的是 `Queue.io.count`
- `Queue.io.count` 是 queue occupancy，不是空闲数，也不是 credit
- 因此：
  - `pull_blocked ... count=911` 的语义是：
    `to_cpu` 队列里当前确实已经堆了 `911` 个 big token
  - `push_blocked ... count=3072 fpga_buffer_size=3072` 的语义是：
    `from_cpu` 队列已经满了，不存在歧义

这一步很关键，因为它排除了“我们只是把计数寄存器看反了”这种解释。

## 静态审计三：`HostPort` 语义要求 bridge 每次 fire 同时消费一个输入 token、产生一个输出 token

关键代码：

- `/home/ubuntu/chipyard/sims/firesim/sim/firesim-lib/src/main/scala/bridgeutils/HostPort.scala`
- `/home/ubuntu/chipyard/sims/firesim/sim/midas/src/main/scala/midas/core/FPGATop.scala`

`HostPort.scala` 明确写了：

- 这是 MIDAS-I legacy `HostPort`
- 它面向的是“consume a single input token and produce a single output token”

`FPGATop.scala` 里也把 target-side所有 `toHost` 通道折成一个 `hp.toHost.hValid`，
把所有 `fromHost` 通道折成一个 `hp.fromHost.hReady`。

这意味着：

- 对 `HostPort` bridge 来说，一个 target cycle 的正确推进条件应该是：
  - 本轮有一份完整的输出 token 可以交给 host
  - 同时也有一份完整的输入 token 可以从 host 交给 target
- 如果 bridge 内部让“输出路径单独前进”而“输入路径没有同步前进”，就会破坏这个单步语义

## 静态审计四：当前 `SimpleNICBridge` upstream 写法确实存在漂移风险

关键文件：

- 本地当前文件：
  - `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`
- 官方主线对应文件：
  - `https://raw.githubusercontent.com/ucb-bar/chipyard/main/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`

### 1. upstream 主线的核心行为

当前官方主线 `SimpleNICBridge.scala` 里，`tFireHelper` 只看：

- `hPort.toHost.hValid`
- `hPort.fromHost.hReady`

没有把下面两件事并入同一个 fire 条件：

- `ntht_queue.io.enq.ready`
- `htnt_queue.io.deq.valid`

也就是说，它没有显式要求：

- target 这一步产生的 `NICToHostToken` 一定能进入本地小队列
- target 这一步需要消费的 `HostToNICToken` 一定已经在本地小队列里准备好

### 2. 本地未提交 patch 在做什么

本地工作树里的 `SimpleNICBridge.scala` 已有一份未提交 patch：

- 把 `ntht_queue.io.enq.ready`
- `htnt_queue.io.deq.valid`

也并入 `tFireHelper`

并且让：

- `ntht_queue.io.enq.valid := tFire`
- `htnt_queue.io.deq.ready := tFire`
- `target.in.valid := ... && tFire`

它要表达的语义非常直接：

- target 不应该只“吐出一边的 token”
- 也不应该只“吞入一边的 token”
- 而应该在同一个 `tFire` 上，同时完成这一步输入/输出 token 的交换

### 3. 为什么当前日志与“漂移”高度一致

如果 `SimpleNICBridge` 允许输出方向前进得比输入方向更快，就会出现：

1. `to_cpu` 持续增长
2. 但 `host driver` 因为还没到 `915` 的整批阈值，暂时不 `pull`
3. 一旦到达阈值并进入成功 round，host 会一次性 `pull 915`
4. 如果 target-side 这时并没有按同速率消耗 `from_cpu`
5. host 再把一个或多个 `915` 大小的 round 往 `from_cpu` 回推
6. 最终 `from_cpu` 被填满到 `3072`

本轮日志正是这条链：

- 先看到 `to_cpu` 从 `0` 涨到 `911`
- 然后最终在 `from_cpu` 满 `3072` 时失败

注意：

- 我们之所以没有在日志里看到“成功的 `pull` 回合数”，
  只是因为本轮 host-only 日志只打印了 blocked path，没有打印 success path。
- 这不妨碍静态上判断：
  `from_cpu` 想从 init 的 `915` 走到最终 `3072`，必须发生过至少一轮以上的成功 bulk `push`，
  而这与“两个方向速率失衡，host 在阈值到达后补推过快”是相容的。

## 与文档/外部资料的对齐

### 1. FireSim 官方文档

FireSim 文档明确说明：

- `link_latency` 必须是 `7` 的倍数
- 且不能超过 NIC widget 的 buffer size

这与当前：

不能直接拿来解释当前问题。

## 当前结论

本轮结论分成三层：

### 第一层：已经动态钉死的事实

- `to_cpu` 不是空，而是在持续积累
- `host driver` 直到攒够 `915` 个 big token 才肯 `pull`
- 最终失败发生在 `from_cpu` 已满的 `push`

### 第二层：最强静态方向

- `SimpleNICBridge` 当前 upstream 写法没有把“本轮输入 token 是否就绪”和“本轮输出 token 是否可入队”同时并入同一个 `tFire`
- 这会让两个方向的 token 有机会不同步推进
- 该风险与本轮日志高度一致

### 第三层：当前验证边界

- 本轮 run 可以支撑“漂移风险”这个根因方向
- 但不能把本地 `SimpleNICBridge.scala` patch 直接宣称为“已在当前 AGFI 上验证通过”
