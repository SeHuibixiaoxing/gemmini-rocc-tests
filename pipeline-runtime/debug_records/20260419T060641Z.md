## 直接证据

### 1. 当前 run 已越过 boot ROM `wfi`

`/home/ubuntu/sim_slot_0/metasim_stderr.out` 持续更新，尾部 PC 已经进入
`0x8000...` 用户程序地址，而不是停在 boot ROM：

- hart0: `pc=0x80002354/0x80002358/0x8000235c/0x80002360/0x80002364`
- hart1: `pc=0x80002030/0x80002032/0x80002034`

这些 PC 与当前 bootbinary 反汇编对应为：

- `0x80002354` 附近：
  `thread_entry` 中 `fill_pattern(stage0_src, sizeof(stage0_src), ...)`
- `0x80002030` 附近：
  `barrier_wait.constprop.0` 中等待 `barrier_epoch` 改变

对应源码：

- `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/bareMetalC/learn-gemmini/rerocc_lc_export_dma_bertmini_segment3_repro.c`
  - line 521: core0 填充 `stage0_src`
  - line 528: 两核进入首个 barrier

结论：`TSIToTileLink` 的 PutFull 修复后，当前现场不再是
“CLINT 写未唤醒导致 boot ROM wfi 永久等待”。

### 2. live gdb 中的 CPU-managed stream read 是 TraceV 正常等待形态

对 `PID 122664` 做短暂 attach 时看到：

- main thread 在 Verilator `eval_step`
- bridge thread 在 `FPGAToCPUDriver::pull -> simif_emul_t::wait_read`

结合 TraceV 文件持续增长：

- `/home/ubuntu/sim_slot_0/metasim_stderr.out`
- `/home/ubuntu/sim_slot_0/TRACEFILE-C0`
- `/home/ubuntu/sim_slot_0/TRACEFILE-C1`

这个 `wait_read` 不是新的死锁证据，而是 TracerV host pull 在等待更多
CPU-managed stream 数据的瞬时状态。

### 3. 当前“卡点移动”的主要原因是全程无 trigger TraceV 太慢

当前 config 使用：

- `tracing.selector: 0`
- `start: 0`
- `end: -1`
- `+trace-min-batch=0`

这会导致：

- 从 boot 起全程采集两颗 hart 的 TraceV
- host 侧允许 0 beat 最小批量，频繁做很小的 pull
- 在用户程序 512 KiB prefill 循环中，TraceV 仍在逐步推进，但速度非常低

现场采样显示，hart0 loop index 从约 `0x409` 推进到 `0x1019` 需要数分钟；
该阶段本来就没有 UART 输出，因此看起来像“又卡到了新位置”。

## 综合结论

- `PutFullData` 修复后，当前 run 已经从 boot ROM 进入用户程序。
- 这轮 gdb/TraceV 不能再支持“loadmem 卡死”判断；那只是 host pull 采样到的瞬时等待。

  `selector=0 + trace-min-batch=0 + 512 KiB prefill` 造成的可解释慢推进。
- 下一轮应停止当前 sel0 全程 trace run，改用 instruction-trigger + batched pull 的本机 metasim。
