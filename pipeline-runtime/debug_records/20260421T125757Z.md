本轮围绕用户提出的“当前卡点可能发生在 bounce path”这一假设，做了一轮带软件开关的排除实验：如果某次 host<->SPM 传输实际落入 bounce path，则**不走真实 DMA，也不做真实数据搬运**；然后在同一套 `cfg32` bitstream / `g6 bertmini` 主线上重新跑一轮 FireSim。

## 本轮目标

1. 验证 `bounce path` 是否真的被当前主线卡点命中；
2. 若命中，观察“跳过真实 bounce DMA/搬运”后卡点是否消失或后移；
3. 若未命中，明确把当前主线 blocker 从 `bounce path` 假设上移开。

## 分析

### A. 这轮实验没有支持 “卡点发生在 bounce path” 这个假设

这次 rerun 的实验设计是：

- **只有在实际命中 bounce path 时**
  才绕过真实 DMA / 真实数据搬运

如果当前主线卡点真的主要由 bounce path 导致，那么至少应看到下面二者之一：

1. sparse log 中出现 `bounce-bypass` 标记；
2. 命中 bypass 后，卡点消失或明显后移。

而实际观察是：

1. 全量 guest sparse log 中没有任何 `bounce-bypass`；
2. 稳定 plateau 对应的 `dma-export-host` 日志明确是 `bounce=0`。

因此，本轮实验对当前主线给出的最强结论是：

**当前这次主线 stall 并不是由“已经进入 bounce path 的真实 DMA/搬运”直接触发的。**

### B. 当前 front 更精确地落在 `target_seq=1` 的 direct export 内部

当前最后可见日志是：

- 第二个 alias target
  `target_seq=1`
  `target=address2`
  的 `first-chunk-submitwait-end`

但还没有看到：

- `export-target-dispatch ... target_seq=1 ... phase=end`

因此更精确的表述不是：

- “卡在 first-chunk-submitwait-end 这一行”

而是：

- **卡在 `target_seq=1` 的 direct export 调用内部，位置晚于 first-chunk 第一次 submit/wait 返回，早于整个 alias target 导出函数返回。**

由于当前 coarse sparse log 只给：

- first chunk begin
- first chunk end
- 整个 target export end

所以当前真正的可疑区间是：

1. 同一次 direct export 的后续 page/chunk 迭代；
2. 该 direct export 在 first chunk 之后的无日志区间；
3. 该 alias target 对应的 direct-path 相关地址翻译 / DMA 提交等待 / 清理流程。

### C. 这轮 plateau 比之前的 `segment3` plateau 更早

之前 `cfg32 + no-TraceV` 的 authoritative plateau 在：

- `segment3` compute 区域

而本轮 `bounce-bypass-enable=1` 这次收敛到：

- `segment0 stage0 tensor2 target_seq=1(address2)` 的 direct export 路径

这说明两点：

1. **当前主线卡点确实还存在漂移 / 分岔现象；**
2. 但这次漂移并不是“因为真正走了 bounce path”，因为现场已经直接证明 `bounce=0`。

所以，若要继续解释“为什么卡点看起来会移动”，当前更值得怀疑的是：

- 同一条 direct export 主线内部仍然存在时序敏感窗口；
- 当前 coarse sparse log 分辨率不足，导致多个不同的内部停点被压缩成同一个表面 front；
- 使得我们先前看到的 `segment3` plateau 与本轮更早的 `segment0` plateau，可能只是不同 rerun 下先暴露出来的两个稳定窗口。

## 结论

- `PIPELINE_RUNTIME_DMA_BOUNCE_BYPASS_ENABLE=1` 已经实际进入 guest 镜像并参与了这轮实验；
- 但当前主线 plateau **没有命中任何 bounce-bypass 路径**；
- 当前这轮稳定卡住的位置是：
  `segment0 stage0 tensor2 target_seq=1(address2)` 的 **non-bounce direct export**；
- plateau 位置晚于：
  `first-chunk-submitwait-end bounce=0`
  这条日志，
  早于：
  `export-target-dispatch ... target_seq=1 ... phase=end`
- 因而本轮实验已经基本排除了：
  “当前主线 stall 是 bounce path 真实 DMA/搬运导致”

## 下一步建议

1. 不再把 `bounce path` 当作当前主线最高优先级假设。
2. 回到 direct export 主线，静态审计：
   - `dma_copy_spm_pages_to_host_linux()`
   - second alias target (`target_seq=1/address2`)
   - first-chunk 之后到函数返回之前的无日志区间
3. 若继续做低扰动验证，下一轮不要再加泛化大日志，而是补：
   - direct export 的 `page>0` / `copied>0` 观测点
   - `target_seq=1` 专属的 begin/end 或 page-N marker
4. 若需要直接看到 guest 线程停在哪个系统调用 / 哪条指令，再启用单独的 `gdbserver` 路线；这比继续围绕 bounce path 试探更有信息量。
