# NIC coherent TX bounce 后仍出现 target-to-host bit-clear corruption

日期：2026-04-30T16:20:00Z

## 关键动态证据

从 F2 host 对 guest `172.16.0.2` 做多种 ping pattern，网络没有丢包，但 echo reply
payload 稳定被清 bit：

- 默认递增 pattern：payload byte `#35` 从 `0x23` 变成 `0x22`
- `-p ff`：payload byte `#20` 从 `0xff` 变成 `0x7f`；后续还有 `0xff -> 0xfe`
  和 `0xff -> 0xfd`
- `-p 00`：无可见错误，因为清零不改变 0
- `-p aa`：payload byte `#20` 从 `0xaa` 变成 `0x2a`；后续还有 `0xaa -> 0xa8`
- `-p 55`：payload byte `#35` 从 `0x55` 变成 `0x54`
- `-p 0123456789abcdef -s 80`：出现 `0x89 -> 0x09`、`0x67 -> 0x66`

这说明问题是确定性的 bit-clear，不是随机 bit flip，也不是简单字节丢失。

`tcpdump -vvv` 给出更强证据：坏 reply 的 ICMP checksum 是按未损坏 payload 算出的，
payload 被清 bit 后 checksum 才变错。例如默认 pattern：

```text
ICMP echo reply ... wrong icmp cksum 2690 (->2691)
```

这里 `0x23 -> 0x22` 让正确 checksum 应该增加 1，但包里仍是旧 checksum。结论是：
target Linux / ICMP 栈在 checksum 计算时看到的 payload 仍是正确的，corruption 发生在
target 已经生成 skb 之后的 TX 出口链路，而不是 host->target ingress / guest RX 路径。

另外，host bridge 的 `switch_to_target_peer` / `host_to_target_push` token debug 显示
host 送入 target 的 ping request payload 在 push 前是正确的；而
`target_to_switch_pull` 中同一类 reply payload 已经损坏。这排除了 software switch
写 TAP 之后才损坏，也排除了 ping request 在 host side 构包阶段已经坏。

## 本轮排除项

1. **旧的双向通信/boot/gdbserver prelaunch 问题已不是当前 blocker。**
   Linux、IceNet、guest IP、host ping 都已经工作。

2. **普通 skb non-coherent DMA map/sync 不是充分解释。**
   TX 已改为 `dmam_alloc_coherent` bounce ring，发包时复制完整 skb 后交给 IceNet，
   但 bit-clear 仍复现。

3. **host->target / guest RX 不是本轮 payload bit-clear 的根因。**
   ICMP reply checksum 仍对应未损坏 payload，说明 target 的协议栈在 TX 前看到的是好数据。

4. **software switch / TAP 不是首个损坏点。**
   `target_to_switch_pull` 的 host bridge token debug 在 switch 写 TAP 前已经看到坏 flit。

## 当前最强链路定位

剩余问题段被缩到 target TX checksum 之后、host switch 之前：

```text
guest Linux skb with correct payload/checksum
  -> IceNet TX coherent bounce buffer
  -> IceNet StreamReader / ReservationBuffer / Aligner
  -> IceNicSendPath / RateLimiter
  -> SimpleNIC hPort.nicOut
  -> ntht_queue
  -> NICTokenToBigTokenAdapter
  -> CPUManagedStreamEngine to-host stream
  -> F2 PCIS 512<->64 read bridge / fpga_pci_peek64
  -> simplenic target_to_switch_pull buffer
```

下一轮硬件观测必须能区分：

- `hPort.nicOut` 上的数据是否已经坏；
- `ntht_queue.io.enq` 是否与 `hPort.nicOut` 一致；
- `NICTokenToBigTokenAdapter.pcie_out` 打出的 bigtoken 是否已经坏；
- F2 PCIS read bridge 返回给 host 的 64-bit lane 是否在该点才坏。

如果 `hPort.nicOut` 已坏，应继续查 IceNet `StreamReader` / `Aligner` / send path；
如果 `hPort.nicOut` 好但 host pull 坏，应优先查 `NICTokenToBigTokenAdapter`、
CPU-managed stream to-host unpack 或 F2 PCIS read width bridge。

## 下一步建议

启动下一颗 bitstream 前，应加入面向上述链路的可综合 debug：

- 对 target-to-host 每个 packet 的前 16 个 valid flit 做 snapshot，至少捕获 flit
  `7/8/9/11/14` 的 `data/keep/last`；
- 同一组 snapshot 同时放在 `hPort.nicOut`、`ntht_queue.io.enq`、
  `NICTokenToBigTokenAdapter.pcie_out` 三个位置；
- F2 PCIS bridge 增加最近若干次 read 的 wide addr、lane、narrow rdata、wide rdata lane
  placement、AR/R handshake 计数；
- host `simplenic` dump 时打印这些 snapshot，避免下一轮只能靠 pcap 和 token buffer
  反推。

只有当这些观测说明错误在某个硬件边界前已经确定出现时，再做功能修复；否则下一轮仍应以
观测 bitstream 为主。
