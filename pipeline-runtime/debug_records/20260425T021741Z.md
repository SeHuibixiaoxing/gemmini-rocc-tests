## 新观察

### 1. `uartlog` 里的 `from_host_ready=0` 不是 “NIC input 不 ready”，而是 HostPort 聚合信号

`HostPortIOConnectChannels2Port` 明确把：

- `hp.fromHost.hReady := fromHostChannels.foldLeft(true.B)(_ && _.ready)`

写死在：

- `/home/ubuntu/chipyard/sims/firesim/sim/midas/src/main/scala/midas/core/FPGATop.scala:474`

所以：

- `SimpleNIC` debug regs 看到的 `hport_from_host_ready=0`
- 其真实含义是：`SimpleNIC` 这整个 bridge 的 **所有 host->target channel** 里，至少有一个 channel 目前不能再接下一拍 token。

它不是某个单独的 `nic.in.ready`，因为 `NICIOvonly` 根本没有真实的 decoupled ready。

### 3. 这些 `SimpleNIC` sink 的 `ready` 不是本地信号，而是统一被 `targetCycleFinishing` 门控

### 5. 当前 `SimpleNICBridge` 本地 lockstep patch 会把这种全局 backpressure 放大成更稳定的闭锁状态

当前本地修改后的 `SimpleNICBridge`：

- `hPort.toHost.hReady := tFireHelper.fire(hPort.toHost.hValid)`
- `hPort.fromHost.hValid := tFireHelper.fire(hPort.fromHost.hReady)`

证据：

- `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala:183-189`
- `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala:241-248`

而旧版上游 `SimpleNICBridge` 是：

- `hPort.toHost.hReady := ntht_queue.io.enq.ready`
- `hPort.fromHost.hValid := htnt_queue.io.deq.valid`

这一点可以直接从旧版源码对比出来：

- `git show f23b1d283:generators/firechip/firesim-only/src/main/scala/bridges/SimpleNICBridge.scala`

这两种语义差别很大：

当前本地版本里：

- 一旦 `hPort.fromHost.hReady` 因为 `targetCycleFinishing=0` 掉下去，
- `SimpleNICBridge` 自己又会把 `hPort.fromHost.hValid` 一起撤掉，
- 同时也撤掉 `hPort.toHost.hReady`

而生成后的 `sv` 又把：

- `ep_3_nic_*_sink_valid`
- 组合成 `SimpleNICBridgeModule_0_hPort_fromHost_hValid & 其它 sink_ready`

证据：

- `/home/ubuntu/chipyard/sims/firesim/deploy/results-build/2026-04-24--14-08-02-firesim_rocket_singlecore_nic_30mhz/cl_f2-firesim-FireSim-WithNIC_WithDefaultFireSimBridges_WithFireSimHighPerfConfigTweaks_chipyard.RocketConfig-BaseF2Config/design/FireSim-generated.sv:42064-42179`

这意味着：

1. 先有任意 bridge 让 `targetCycleFinishing` 暂时变成 `0`
2. `SimpleNIC` 全部 sink ready 一起掉
3. `SimpleNICBridge` 因为 `fromHost.hReady=0`，把自己的 `fromHost.hValid` 也撤掉
4. 目标侧看到的 `ep_3_nic_*_sink_valid` 也一起撤掉
5. `targetCycleFinishing` 需要这些 `sink_valid`，于是更难重新抬起来

这就是一个比“局部 queue 满了”更强的、跨 bridge 的闭锁结构。

### 6. `TracerV` 也明确在这个全局闭锁环里，不能把它当成无关背景

生成后的 `sv` 明确把：

- `tracerv_triggerDebit_sink_valid`
- `tracerv_triggerCredit_sink_valid`

放进了 `targetCycleFinishing` 的全局 AND：

- `/home/ubuntu/chipyard/sims/firesim/deploy/results-build/2026-04-24--14-08-02-firesim_rocket_singlecore_nic_30mhz/cl_f2-firesim-FireSim-WithNIC_WithDefaultFireSimBridges_WithFireSimHighPerfConfigTweaks_chipyard.RocketConfig-BaseF2Config/design/FireSim-generated.sv:163782-163784`

同时 `TracerVBridge` 自己的 `hPort` 交握也依赖：

- `hPort.toHost.hValid`
- `hPort.fromHost.hReady`
- `streamEnq.ready`
- `initDone`

证据：

- `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/TracerVBridge.scala:183-203`

这就意味着：

- 只要 `TracerV` 自己的 host stream/backpressure/init 条件出问题，
- 它就有资格把整个 `targetCycleFinishing` 拉低，
- 然后在 `uartlog` 里表现成 `SimpleNIC from_host_ready=0`

所以之前用户反复提醒“`TraceV/TracerV` 可能会干扰判断”是对的。

## 本轮分析

### A. 上一轮 `SimpleNIC debugregs` 已经证明：本地 `htnt/ntht` 队列不是当前最强根因

上一轮 authoritative 现场里：

- `htnt_queue_count=10`
- `ntht_queue_count=0`
- `t_fire_blocked_from_host_ready=1`
- `t_fire_blocked_ntht_enq_ready=0`
- `t_fire_blocked_htnt_deq_valid=0`

结合本轮静态结果，正确解释应当是：

- 当前不是 `ntht_queue` 自己塞满
- 也不是 `htnt_queue` 自己空掉
- 而是 `SimpleNICBridge` 在等待全局 `targetCycleFinishing`

换句话说，`SimpleNIC` 更像是“全局 cycle 没完成时，第一个把局部队列表现成满/不 ready 的观察窗”，不一定是原始触发点。

### B. “卡点漂移”现在有了更可信的静态解释

如果真实问题在 `targetCycleFinishing` 这种全局 AND 上，那么：

- 任何 bridge 的 `source_valid` / `source_ready` / `sink_valid`
- 都可能成为当轮最先露出的局部表征

这就会导致：

- 一轮看起来卡在 `SimpleNIC`
- 另一轮看起来卡在 `TracerV`
- 再一轮可能看起来卡在 `TSI`、`AXI4` 或某个局部 queue

而日志、trace、额外 stream、甚至不同 bitstream 的轻微时序变化，都会改变：

- 哪个 bridge 最先把“全局 cycle 没 finishing”暴露成可见症状

所以“卡点在移动”这件事，本轮静态上可以更严谨地改写为：

- **局部症状在移动**
- 但更上层的真实结构，是跨 bridge 的 `targetCycleFinishing` 闭锁

### C. 当前最强静态嫌疑点

本轮不直接下“已经唯一定位根因”的结论，但可以把当前嫌疑收敛为两个层级：

第一层，已经基本坐实：

- `SimpleNIC from_host_ready=0` 不是独立根因，而是 `targetCycleFinishing=0` 的局部投影

第二层，当前最值得优先验证的结构性嫌疑：

- 当前本地 `SimpleNICBridge` lockstep patch
- 把上游原本更松的 `htnt/ntht queue` 边界
- 改成了更强的 `hPort.fromHost.hValid / hPort.toHost.hReady` 同时撤销
- 这很可能把“短暂全局 backpressure”放大成“稳定闭锁”

这也是为什么：

- 这轮不能再继续只盯 `NICTokenToBigTokenAdapter`
- 而必须把 `SimpleNICBridge <-> HostPort <-> targetCycleFinishing` 一整条链一起看

## 下一步建议

### 1. 下一轮低扰动验证，优先比较 `SimpleNICBridge` 当前 lockstep 语义与上游原始语义

最有信息量的 A/B 验证不是再加 guest 文本日志，而是：

- 保持 workload 不变
- 保持其它 bridge 不变
- 只比较：
  - 当前本地 `SimpleNICBridge`
  - 上游原始 `SimpleNICBridge`

验证目标：

- `from_host_ready=0` 是否仍稳定出现
- `tick_push_mismatch` 是否消失或显著后移
- `SimpleNIC` 本地 queue 计数关系是否恢复成非闭锁形态

### 2. 如果还需要加观测，下一轮不要继续往 `SimpleNIC` 局部 queue 堆日志

更低扰动、信息量更高的观测应当是：

- bridge 级别的 `hPort_fromHost_hValid`
- bridge 级别的 `hPort_toHost_hValid`
- bridge 级别的 `hPort_toHost_hReady`

优先对象：

- `TracerVBridge`
- `TSIBridge`
- `SimpleNICBridge`
- 必要时 `FASEDMemoryTimingModel`

因为这些信号才直接参与 `targetCycleFinishing` 闭锁。

### 3. 针对 `gdbserver` / NIC 最小 smoke，建议继续减少无关 bridge 干扰

这条线的目标只是把 NIC + 网络 + guest attach 跑通，所以：

- 如果当前 `TracerV` 不是必须观测面，应尽量去掉
- 至少不要一边带 `TracerV` 一边把 `SimpleNIC` 局部 ready 误判成唯一根因

## 本轮结论

- 本轮静态审计把问题层级从 `SimpleNIC local ready/queue` 提高到了 `FireSim targetCycleFinishing` 全局闭锁。
- `SimpleNIC fromHost.hReady=0` 现在应被视为**结果信号**，而不是已定位的最初坏点。
- 当前最强静态嫌疑不是 `NICTokenToBigTokenAdapter` 单点，而是：
  - `SimpleNICBridge` 当前 lockstep patch
  - 与 `HostPort` / `FPGATop` / `targetCycleFinishing` 的全局耦合
- 这也给“为什么卡点看起来在漂移”提供了更可信的解释：
  - 真正在漂的是全局闭锁下最先露头的局部症状
  - 不是问题真的在 guest 程序里不断后移/前移
