## Round Goal

用 live `TracerV` rerun 的直接证据判断：

- `taskset -c 0` 包住 `/usr/bin/firesim-start-trigger` 的验证是否成功；
- 如果失败，失败是在 “还没到用户程序” 之前，还是已经进入 runtime 之后仍然没有 trace。

## Key Evidence

### 1. 这轮 guest 已经完整进入 wrapper、runner 和 runtime 二进制

从 live run host `192.168.1.94` 对 guest image 做 `debugfs cat`：

- `bertmini-batch8.wrapper.stage`
  - 已到 `before-child-wait pid=134`
- `bertmini-batch8.runner-early.stage`
  - 已到 `before-runner-enter`
- `bertmini-batch8.runner.stage`
  - 已到 `after-bin-spawn method=ours2 pid=199`
- `bertmini-batch8.wrapper-proc.stage`
  - child 是 `/bin/sh /root/rerocc-linux-tests/run_rerocc_pipeline_runtime_bertmini.sh --batch 8`
- `bertmini-batch8.runner-proc.stage`
  - 已经 spawn：
    `/root/rerocc-linux-tests/pipeline-runtime/rerocc_pipeline_runtime-linux ...`

所以这轮不是 “没到 `/firemarshal.sh` / 没到用户程序”。

### 2. runtime 已经推进到真实工作负载初始化内部

同一轮 `bertmini-batch8.log` 已经包含：

- `[prt-early] enter main`
- `[prt-early] calling runtime_init`
- `[prt-progress] runtime begin ...`
- `[prt-progress] init load-model-yaml begin ...`
- `[prt-progress] init load-pipeline-yaml begin ...`

也就是说：

- `rerocc_pipeline_runtime-linux` 已经真正在 guest 内执行；
- 而且已经过了启动壳脚本，进入 runtime 主体。

### 3. 在以上前提下，`TRACEFILE-C*` 仍然严格没有写出

run host live 状态：

- `/home/ubuntu/sim_slot_0/TRACEFILE-C0..C3` 全部仍为 `0`
- `sudo cat /proc/<FireSim-f2-pid>/fdinfo/7`
  - `pos: 0`
- `sudo cat /proc/<FireSim-f2-pid>/io`
  - `syscw` 在增长
  - 但 trace fd 本身位置仍为 `0`

这说明：

- 不是 copy-back 还没发生；
- 而是到 runtime 已经在跑时，host trace file 仍没有实际写入。

### 4. `/firemarshal.sh` 命令链本身是对的

live image 里的 `/firemarshal.sh` 为：

`/usr/bin/taskset -c 0 /usr/bin/firesim-start-trigger && /usr/bin/taskset -c 0 /root/rerocc-linux-tests/run_rerocc_pipeline_runtime_bertmini_fileonly_sync_capture.sh --batch 8 && /usr/bin/taskset -c 0 /usr/bin/firesim-end-trigger`

因此这轮不是：

- workload JSON 没生效；
- `/firemarshal.sh` 没更新；
- guest 没有执行到 start-trigger 包装命令链。

### 5. trigger 小工具的 ELF 入口指令也仍然是精确的目标值

host 侧直接读取 FireMarshal trigger ELF：

- `software/firemarshal/.../trigger/start`
  - `.text` 首 32-bit word = `0x00008013`
- `software/firemarshal/.../trigger/end`
  - `.text` 首 32-bit word = `0x00010013`

对应 `TracerV` 配置仍是：

- `+trace-start=ffffffff00008013`
- `+trace-end=ffffffff00010013`

所以这轮也不是 “trigger 工具本身的编码变了”。

## Conclusion

`taskset` 这一轮验证已经可以判定失败：

- guest 确实执行到了 runtime 主体；
- `/firemarshal.sh` 也确实执行了 taskset 包装命令链；
- 但 `TRACEFILE-C*` 仍完全没有写出。

因此下一步不应继续沿 shell 级 `firesim-start-trigger` 碰运气。

更强、更局部的下一步应是：

1. 在 `stage_worker_main()` 的 worker 本地路径里发出精确原始 trigger 指令；
2. 只在 isolated `tracerv-inst` 构建里启用；
3. 让触发点与真正执行 hot worker 的 hart 绑定，而不是绑定 shell / wrapper 进程。
