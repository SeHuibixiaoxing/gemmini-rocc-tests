# single-core NIC 新比特流退化的第四次静态钉证

日期：2026-05-03T05:13:19Z

## 目标

继续排查为什么 04-30 通过的 single-core NIC AGFI 可以跑通
`Linux + IceNet + gdbserver`，而后续新构建 bitstream 退化。

本轮只做静态排查和本地 `replace-rtl`，目标是把当前源码继续向旧通过
AGFI 的生成形态收敛，而不是继续在错误的硬件形态上跑 F2。

## 本轮新钉死的问题

上一轮 `20260503T035648Z.md` 的方向是对的：删除未被旧通过版验证的
`first16`、ready/partial-fire debug、PCIS write-order debug，并恢复 04-30
通过版 payload snapshot。

但本轮用旧通过版 generated RTL 逐项对照后发现，上一轮对 snapshot CR 顺序的
理解仍然有误。

04-30 通过版 `SimpleNICBridgeModule` 的 CR 顺序是：

```text
44 bigtoken_current_slot_meta
45 bigtoken_current_slot_data_0
46 bigtoken_current_slot_data_1
47 bigtoken_last_latched_word0_0
48 bigtoken_last_latched_word0_1
49 bigtoken_last_latched_word1_0
50 bigtoken_last_latched_word1_1
51 bigtoken_last_latched_word2_0
52 bigtoken_last_latched_word2_1
53 nicbig_special_counter
54 nicbig_full_flush_count
55 nicbig_partial_flush_count
56 nicbig_last_flush_slot
57 nicbig_pcie_out_fire_count
58 nicbig_last_pcie_out_word0_0
...
```

也就是说，旧通过版并不是“所有 `nicbig_*` counter 之后再接 snapshot”，而是
在 `bigtoken_current_slot_meta` 后先接 `bigtoken_current_slot_data` 和
`bigtoken_last_latched_word*`，再接 `nicbig_special_counter..pcie_out_fire_count`，
随后才是 `nicbig_last_pcie_out_word*` 与 `to_host_hist*`。

本轮修复前的新生成物是：

```text
44 bigtoken_current_slot_meta
45 nicbig_special_counter
46 nicbig_full_flush_count
47 nicbig_partial_flush_count
48 nicbig_last_flush_slot
49 nicbig_pcie_out_fire_count
50 bigtoken_current_slot_data_0
...
```

这是明确的 old/new CR 地址顺序差异。它不会直接改变 target 数据通路的 Scala
语义，但会改变 OCL CR map、driver static layout、以及综合后调试面/扇出形态。
在当前 NIC 退化链路里，已经有“删掉/移动 payload snapshot 面后 target->host
payload corruption 复现”的直接历史证据，因此这类差异不能继续保留。

## 本轮修复

修改：

```text
generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala
generators/firechip/bridgestubs/src/main/cc/bridges/simplenic.h
```

修复内容：

- 把 `bigtoken_current_slot_data` / `bigtoken_last_latched_word*` 的 `attach`
  移回 `bigtoken_current_slot_meta` 后、`nicbig_special_counter` 前；
- 同步调整 `SIMPLENICBRIDGEMODULE_struct` 字段顺序；
- 将 host history 寄存器名恢复为旧通过版生成物里的 `toHostHistoryData` /
  `toHostHistoryMeta`，便于 generated RTL 对照。

## 结论

当前最硬的退化链仍是：

```text
04-30 target->host payload corruption
  -> 加入 payload snapshot
  -> agfi-0079cbbca617eca4e 跑通
  -> 05-02 “硬件归位”裁掉 snapshot
  -> agfi-032d10150efc1d4ec 再次 payload corruption
  -> 之后又混入 first16 / ready 聚合 / partial-fire / PCIS write-order debug
  -> 新 bitstream 不再等价于旧通过版
```

本轮进一步钉死：即使恢复 snapshot，也必须恢复 04-30 通过版的 CR 顺序；
上一轮“snapshot 在 `nicbig_pcie_out_fire_count` 后”的恢复方式仍然不是旧通过
AGFI 形态。

下一步应基于当前 SHA 重新构建 single-core NIC bitstream。进入远端 Vivado 后必须
再次核验远端 generated RTL / driver SHA 和 marker，防止 stale collateral。
