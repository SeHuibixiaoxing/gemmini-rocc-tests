# NIC gdbserver RSP payload corruption after latest single-core AGFI

日期：2026-04-30T15:27:36Z

## 本轮目标

接续 `singlecore + NIC + Linux + remote gdbserver` F2 调试，复盘最新 single-core
NIC AGFI 的失败现场，确认新卡点是否仍是早期 NIC 双向通信失败，还是已经推进到更深链路。

## 测试对象与现场

- AGFI：`agfi-0859279e1361ac1ff`
- AFI：`afi-096252cc36ee42f1b`
- HWDB：`sims/firesim/deploy/config_hwdb_f2_rocket_singlecore_nic_notrace_30mhz.yaml`
- Run host：`i-03029f7bc85717e6e` / `192.168.1.20`
- FireSim result：
  `sims/firesim/deploy/results-workload/2026-04-30--14-42-55-rocket-singlecore-nic-gdbserver-smoke-f2-rocket-singlecore-nic-gdbserver-smoke-notrace-relaxed-noprint-longheartbeat-preserve/`
- 手工回收现场：
  `tmp/firesim-aws-f2/nic-scenes/singlecore-nic-gdbserver-rsp-slow-20260430-1507/`

Run host 已确认不再处于 running 状态。现场目录中保留了 `uartlog.remote`、
`switchlog.remote`、`tap0-20260430-1443.pcap` 与 gdb 日志。

## 已经推进过的旧卡点

这轮不是“host/target 没有双向通信”的旧问题：

- Linux boot 成功。
- IceNet 注册成功：`Registered IceNet NIC 00:12:6d:00:00:02`。
- guest `eth0` 获得 `172.16.0.2/16`。
- `gdbserver` 已监听 `172.16.0.2:2345`。
- TCP 三次握手成功，remote gdb 的 RSP 初始协商已经开始。

因此，`fromHostValidDrive` / no-packet token / ARP / TCP SYN-SYNACK-ACK 这批早期链路问题已经被越过。

## 新卡点

新卡点是 target-to-host 方向的 TCP payload 内容损坏，且损坏发生在 FireSim software
switch / TAP 写包之前。

pcap 证据：

```bash
tcpdump -nn -tttt -vvv -S -XX \
  -r tmp/firesim-aws-f2/nic-scenes/singlecore-nic-gdbserver-rsp-slow-20260430-1507/tap0-20260430-1443.pcap \
  'tcp and src 172.16.0.2'
```

关键现象：

- target 发出的 562B TCP payload 被 host 判为 bad checksum：
  `cksum 0xce88 (incorrect -> 0xd891)`。
- 这不是单纯 checksum 字段写错，因为 payload 文本本身已经损坏：
  - 正常应为 `PacketSize=47ff;QPassSignals...`
  - 实际看到 `PacketSize<47ff;QPassSienals...`
  - 后续也有 `QSetWorkingDir` 变成 `QSetWoriingDir` 的同类字符损坏。
- host ACK 停在旧 seq，不接受这个坏 payload；gdb 最终因 300s timeout 退出。

更强证据来自 `uartlog.remote` 中的 SimpleNIC host bridge token debug：

```bash
grep -a -n -A18 -B2 \
  'SIMPLENIC TOKEN DEBUG \[target_to_switch_pull\] event=6' \
  tmp/firesim-aws-f2/nic-scenes/singlecore-nic-gdbserver-rsp-slow-20260430-1507/uartlog.remote
```

`target_to_switch_pull event=6` 已经显示第一批 RSP payload flit 损坏，例如：

- `data=0x63615024a8a36c88`，低字节可读为 `$Pac...`，但中间字节已异常。
- 后续样本包含 `0x6c616e6569537373`，对应 `ssSienal`，而不是正常的 `ssSignal`。

这说明坏数据在 FPGA/bridge 被 host driver pull 出来时已经存在，不是 software switch
写 TAP 时才破坏。

## Timing 排除强度

最新 build：

- `sims/firesim/deploy/results-build/2026-04-30--10-41-55-firesim_rocket_singlecore_nic_notrace_30mhz`

该 build 的 post-route timing 仍有 DDR reset / async recovery 类 violation，例如 top slack
`Slack (VIOLATED) : -3.399ns`。但旧通过 build
`2026-04-29--14-56-47-firesim_rocket_singlecore_nic_notrace_30mhz` 的 top slack 与路径类型相同。

因此，当前证据不支持把新 RSP payload corruption 直接归因到这些既有 timing report；
同样的 timing report 在旧 AGFI 上没有破坏 gdbserver RSP payload。

## 当前判断

本轮把问题前沿从“NIC 是否有双向通信”推进到了：

```text
guest gdbserver writes RSP
  -> Linux TCP/IP stack
  -> IceNet TX path reads guest memory
  -> target-to-switch bridge pull
  -> software switch / TAP / host gdb
```

坏数据在 `target_to_switch_pull` 时已经出现。当前最高优先级不是 ARP/TCP/switch
连通性，而是 IceNet TX 读 guest skb 数据的 cache/DMA/coherency 链路，或更下游的
IceNet send-path stream 化硬件。

下一步先做不需要新 bitstream 的判别实验：IceNet TX 改为使用 driver 预分配的
`dma_alloc_coherent` bounce ring。发包时把完整 skb，包括 `NET_IP_ALIGN` 前导 padding，
复制到 coherent buffer，再把 coherent DMA 地址交给 IceNet。

判别标准：

- 如果该软件改动后新 AGFI 不再损坏 RSP payload，则根因钉到 IceNet TX 从普通 skb
  做 DMA 读时的 cache/DMA 同步链路；后续可以保留 coherent bounce 或继续追设备
  DMA 属性为何 `dma_map_single` 不足。
- 如果 coherent bounce 后仍损坏，则 checksum/offload/DMA-map 方向被进一步证伪，
  下一轮应在 IceNet send path、`hPort.nicOut`、`NICTokenToBigTokenAdapter`、
  host bridge pull 寄存器上加 byte-level 可综合观测后再构建 bitstream。
