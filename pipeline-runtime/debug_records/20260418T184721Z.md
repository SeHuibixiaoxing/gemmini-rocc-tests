## Static code findings

### 1. `tsi_t::reset()` is only the hart0 MSIP write

From `objdump -dC /home/ubuntu/sim_slot_0/VFireSim`:

- `firesim_tsi_t::reset()` only waits on `is_loaded_in_target` and then jumps to
  `testchip_tsi_t::reset()`
- `testchip_tsi_t::reset()` does:
  - `perform_init_accesses()`
  - if `write_hart0_msip`, jump to `tsi_t::reset()`
- `tsi_t::reset()` is a tiny function that directly calls virtual
  `write_chunk(0x2000000, 4, &one)`

This is critical because it proves:

- for the current run, the only boot-wake transaction that matters is the
  serial-TL write of `1` to CLINT MSIP base `0x2000000`
- `bootAddrReg` is not written by this reset path; its correct `0x80000000`
  value can come from the default boot-address register state

### 2. Current binary is not the historical 16-thread Verilator SCC case

From generated source:

- `Vemul::threads() const { return 1; }`

So the older archived `thread-16` SCC diagnosis is relevant historical context,
but it does not explain this exact run directly.

## Consolidated conclusion

This round narrows the regression to a single functional window:

- host loadmem completed
- host TSI queues drained
- target TSI / LoadMem widgets are idle
- harts are still asleep in boot ROM

Therefore the current failure is best described as:

`the final serial-TL hart0 wakeup write to CLINT MSIP did not produce an effective wakeup`

More specifically, the next question is no longer "which guest instruction is stuck?"
because guest code never started. The next question is:

- did `tsi_t::reset()` actually issue the `write_chunk(0x2000000, 4, 1)` on this run?
- if yes, where did that single MSIP write get lost or neutralized?

## Recommended next step

Do not add more guest breadcrumbs.

Run one controlled local metasim rerun and observe the reset write directly,
preferably without changing functional behavior:

1. attach gdb very early and set breakpoints on:
   - `firesim_tsi_t::reset`
   - `testchip_tsi_t::reset`
   - `tsi_t::reset`
   - `testchip_tsi_t::write_chunk`
   - `tsi_t::write_chunk`
2. verify that the `0x2000000` / 4-byte MSIP write is actually called
3. on the target side, sample around the same time:
   - `clint.ipi_0`
   - `tsi2tl.state/cmd/addr/len`
4. if the write is issued but `ipi_0` never pulses, the bug is in the
   serial-TL / CLINT delivery path
5. if `tsi_t::reset()` is never reached, the bug is in the host FESVR control
   flow after loadmem completion
