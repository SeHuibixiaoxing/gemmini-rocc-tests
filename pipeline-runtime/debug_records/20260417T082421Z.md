## Static Findings

### 1. The moving frontier is real, but it is not a single mechanism
- Current evidence supports three mechanisms operating together:
  1. observability perturbation
  2. guest-file visibility and capture-boundary artifacts
  3. a real timing-sensitive soft/hardware blocking condition
- Therefore the last visible line in a sparse log or trigger log is not automatically the true blocker.

### 2. Observability perturbation is confirmed by both docs and code
- `docs/testing/observability.md` explicitly says hot-path string probes move the frontier and that breadcrumb should be preferred over high-frequency text logs.
- `debug_records/20260415T144925Z.md` already proved one concrete regression source:
  leaving `PIPELINE_RUNTIME_DMA_EXPORT_PAGE_START/END` empty re-enabled the built-in export sparse page logging window and moved the observed frontier earlier.
- The runtime worker hot path still contains many conditional marker/progress sites around:
  - stage dispatch
  - Gemmini issue
  - export sync
  - export retire
- In Linux mode, guest/deep/marker logs still ultimately go through `write(...)` on `O_APPEND` file descriptors, and the marker path deliberately uses best-effort direct writes because stdio flushes had previously wedged hot windows.
- Even after those mitigations, these writes still consume time and can perturb lock hold times, scheduler interleavings, and accelerator busy windows.

### 3. Guest-file evidence is not perfectly synchronous with runtime progress
- `src/prt_breadcrumb.c` maps the breadcrumb file with `MAP_SHARED`, but only calls `msync()` during init and destroy.
- The live policy in `docs/testing/observability.md` is therefore correct:
  the wrapper-side periodic `sync` is what makes guest-file progress visible to host-side `debugfs` reads.
- `debug_records/20260413T111906Z.md` and `debug_records/20260415T084758Z.md` already showed that sparse log and breadcrumb can temporarily disagree because the runtime progressed further than the currently persisted guest image.
- This means a frozen breadcrumb can be a visibility lag, not necessarily a stalled execution point.

### 4. Trigger logs have a built-in capture cutoff which can look like a frontier
- `src/prt_trigger_log.c` shows that unmatched events return before formatting or writing, so the narrow trigger family is already low-disturbance relative to broad logging.
- But once a match occurs, the trigger logger:
  - takes a global mutex
  - flushes the per-thread pre-ring
  - writes matched/post-match lines to the trigger file
  - stops after `post_budget` lines
- Because the logger disables itself once `budget_remaining` hits zero, the final visible trigger line can be exactly the capture budget boundary rather than the true runtime stop.
- This is consistent with the earlier control note that “last trigger line” needs confirmation from sparse log or breadcrumb before it is treated as the blocker.

### 5. The runtime is timing-sensitive even when there is only one stage worker
- `debug_records/20260415T084758Z.md` correctly noted that the current mainline run has only two runtime threads:
  - main thread
  - stage-0 worker thread
- But the absence of many pthreads does not make the system deterministic.
- The worker loop in `src/prt_runtime.c` repeatedly alternates between:
  - entry DMA/ring waits
  - `stage_wait_exports_ready(...)`
  - Gemmini dispatch and busy/fence completion
  - export alias sync
  - export DMA submission/retire
- Export retirement itself has ordering-sensitive state in `src/prt_scheduler.c`:
  - token-live tracking
  - `subbatch_offset`
  - ring fill/use counts
  - `cmd_running`
  - `state_epoch`
- Any timing shift around these transitions can move where progress becomes externally visible.

### 6. The hardware-side release/restore path is explicitly gated on busy becoming false
- In `generators/rerocc/src/main/scala/manager/Manager.scala`, `sRelResp` is only emitted when:
  - state is `s_rel_wait`
  - `!io.busy`
  - `inst_q.io.count === 0`
- `sUnbusyAck` is only emitted when:
  - state is `s_unbusy`
  - `!io.busy`
  - `inst_q.io.count === 0`
- So any residual accelerator busy condition directly delays RR release/unbusy completion.

### 7. Gemmini and coupled DMA both expose wide busy windows
- In `generators/gemmini/src/main/scala/gemmini/Controller.scala`, `io.busy` is the OR of:
  - raw command presence
  - loop unrollers
  - reservation station busy
  - scratchpad busy
  - unrolled command presence
  - loop/conv command presence
- The same file also contains a long-cycle `pipeline_stall` assertion, which is another sign that this controller expects long busy windows and treats lack of forward progress as a real risk.
- In `generators/gemmini/src/main/scala/gemmini/GemminiCoupledDMA.scala`, fence completion is only accepted when `!dmaBusy`, and `io.busy` stays high while the DMA state machine or response path is active.
- That means RR release/restore timing depends not only on software order but also on whether Gemmini or coupled DMA has actually drained its internal state.

### 8. The earlier `spm-xlate mgr=5 cfg=15 restore-begin` frontier is still plausible, but not authoritative by itself
- `src/prt_rerocc.c` shows the `spm-xlate` release path is:
  - `rr_fence(scope->cfg_id)`
  - `prt_rr_release_scope(scope)`
  - `rr_restore_opcode_binding(3U, prev_binding)`
- The previously observed stall at `restore-begin` is therefore a real and meaningful boundary.
- But the later rerun in `debug_records/20260417T080300Z.md` demonstrated that the system can also stall earlier, at `dma_submitwait_after_cleanup` on `sb=5 / tensor=2 / page=8`, before it even re-enters that later SPM-translate window.
- This is exactly the pattern expected when a latent timing-sensitive bug is present and observability changes or natural runtime variation change which busy window becomes the first externally stable one.

## Net Conclusion
- “卡点反复移动” is not explained by one bug or by one bad log line.
- The repeated movement is the combination of:
  1. probe-induced perturbation in hot paths
  2. guest-file persistence / capture-boundary artifacts
  3. a genuine timing-sensitive blocker in the DMA/RR/Gemmini interaction path
- Therefore:
  - the last visible frontier is only a candidate frontier
  - candidate frontiers must be ranked by control strength
  - breadcrumb-only or narrow trigger reruns are still necessary to separate “capture boundary” from “true blocking instruction”

## Practical Implication For Next Rounds
- Treat the current `dma_submitwait_after_cleanup seg=0/stage=0/sb=5/tensor=2/page=8` point as the best low-disturbance frontier for the next narrowing step.
- Do not interpret any later `spm-xlate` frontier as authoritative unless a control rerun reaches it again under equally quiet observability.
- Continue using only:
  - fixed profile baseline
  - breadcrumb as primary hot-path evidence
  - a single trigger-gated family per rerun
- Avoid reopening broad export sparse logs or stacking multiple probe families in one round.
