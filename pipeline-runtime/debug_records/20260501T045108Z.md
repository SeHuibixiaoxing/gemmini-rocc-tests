# Remote GDB 能力矩阵验证

## 背景

目标是判断 `pipeline-runtime` 后续卡死调试需要依赖哪些 remote gdb 功能，并在最小
`singlecore + NIC + Linux + gdbserver` bitstream 上先验证这些功能是否可靠。

本轮依据主线 debug records，当前 `pipeline-runtime` 卡点主要需要回答：

- 卡住时每个用户线程停在哪个函数 / 哪条指令；
- direct DMA / export / compute 可疑区间能否用断点缩小；
- 卡住后能否从运行状态抢回控制并采样现场；
- 能否读取关键全局变量、指针指向内存、寄存器与当前指令窗口。

## 已验证通过的功能

1. `target remote`
   - 证据：`target remote :32355` 成功进入 `_start`。
   - 认定：RSP/TCP/NIC/SSH tunnel 链路可用。

2. 源码级软件断点
   - 证据：`break main`、`break smoke_iteration_hook`、`break smoke_worker_heartbeat`
     均成功，并能命中源码行。
   - 认定：可用于在 `pipeline-runtime` 的 direct DMA / export / compute 关键函数上下断点。

3. `continue` 到断点
   - 证据：`continue` 命中 `main`、worker 线程的 `smoke_worker_heartbeat`、
     主线程的 `smoke_iteration_hook`。
   - 认定：可从程序起点推进到指定软件前沿。

4. 单步 / next
   - 证据：`next` 从 `puts` 行推进到 `fflush` 行。
   - 认定：可在窄窗口内做少量源码级单步。

5. 多线程枚举
   - 证据：`info threads` 看到 5 个线程：
     主线程加 4 个 worker 线程。
   - 认定：可用于判断 pipeline runtime 卡住时到底是哪个 worker/线程停住。

6. 全线程调用栈
   - 证据：`thread apply all bt` 输出主线程 `main -> sleep`，
     worker 线程 `smoke_worker_main -> usleep`。
   - 认定：这是当前 pipeline runtime 卡死调试最核心能力，已通过。

7. 运行中抢回控制
   - 证据：程序 `continue` 后，发送 `Ctrl-C`，gdb 返回：
     `Thread 1 "gdbserver-smoke" received signal SIGINT, Interrupt.`
   - 认定：可以模拟 workload 卡死后手工中断，然后采集线程栈/寄存器/PC。

8. 寄存器读取
   - 证据：`info registers pc sp ra a0 a1` 成功输出。
   - 认定：可用于确认当前 PC/返回地址/参数寄存器。

9. 指令窗口反汇编
   - 证据：`x/12i $pc`、`x/10i $pc` 成功输出当前指令。
   - 认定：可替代一部分 TraceV 的用户态 PC 附近观测。

10. 全局变量读取
    - 证据：`print smoke_counter`、`print smoke_worker_counters` 成功。
    - 认定：可读取 `pipeline-runtime` 中带符号的关键状态变量。

11. 内存读取
    - 证据：`x/8gx &smoke_memory_probe` 成功输出 8 个 64-bit word。
    - 认定：可查看指针/数组/状态缓冲区内容。

12. 变量/内存写入
    - 证据：`set variable smoke_memory_probe[7] = 0xabcdef` 后
      `print/x smoke_memory_probe[7]` 返回 `0xabcdef`。
    - 认定：若后续需要临时改软件变量绕过等待或打开运行时 flag，这条能力可用。

13. 线程切换与局部参数查看
    - 证据：`thread 2`、`frame 3`、`info args` 返回
      `smoke_worker_main(arg=0x1)`。
    - 认定：可在 pipeline runtime 多线程栈中切到具体 worker 现场。

14. `detach`
    - 证据：`detach` 返回：
      `Ending remote debugging. [Inferior 1 (process 116) detached]`
    - 认定：可以在采样后不杀死 inferior。

## 未通过 / 不应依赖的功能

### Hardware watchpoint

命令：

```gdb
watch smoke_counter
continue
```

结果：

```text
Hardware watchpoint 4: smoke_counter
Could not insert hardware watchpoint 4.
Could not insert hardware breakpoints:
You may have requested too many hardware breakpoints/watchpoints.
```

判断：

- 当前 `gdbserver`/Linux/RISC-V 组合下，数据 watchpoint 不能作为可靠能力。
- 这不是 NIC 通信问题；同一会话中普通断点、线程栈、寄存器、内存读写都正常。
- 更可能是 Linux target-side debug register / gdbserver hardware watchpoint 支持不足或数量为 0。

是否需要改硬件：

- 为当前 pipeline-runtime 卡死定位，不需要立刻改硬件。
- 如果后续一定要“某个内存地址一被写就停住”，应优先用软件条件断点/日志/显式检查点；
  只有这些都不够，再考虑硬件 debug/watchpoint 支持，但那会超出 NIC 修复范围。

## 限制

- 本轮验证的是 `gdbserver --once <program>` 启动式 remote debug；
  不是 `gdbserver --attach <pid>` 附加到已运行进程。
- 条件断点没有单独跑命令验证；它通常由 gdb 在普通断点命中后基于已验证的变量读取能力求值，
  因此不需要额外硬件支持，但后续用于主线前可在 pipeline runtime 上顺手确认。
- `detach` 后本轮 smoke 没有自然出现 `[gdbserver] phase=exit`；
  因此这种 smoke 验证用 `detach` 收尾只适合保留现场，不适合作为自然 PASS 测试。

## 结论

当前 remote gdb 已足够支撑 pipeline runtime 卡死调试的主路径：

- 先用 `gdbserver --once` 从程序起点启动；
- 在 direct DMA/export/compute 可疑函数下普通断点；
- 继续运行到卡死或可疑窗口；
- 用 `Ctrl-C` 抢回控制；
- 用 `info threads`、`thread apply all bt`、`info registers`、`x/i $pc`、
  变量/内存读取来复原用户态现场。

除 hardware watchpoint 外，本轮列出的核心能力均已在真实 F2 + 单核 NIC bitstream 上验证通过。
