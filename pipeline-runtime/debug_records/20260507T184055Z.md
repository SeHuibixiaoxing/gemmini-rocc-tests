## Result

The run reached `gdbserver` and the GDB marker chain successfully advanced
through:

- `segment-begin` for segment 0.
- `worker-create` for segment0/stage0.
- `worker-entry` for segment0/stage0.
- First DMA wait-enter for segment0/stage0, tensor 0, page 0, token 1.
- First DMA wait-return for segment0/stage0, tensor 0, page 0, token 1, `rc=0`.

The newly added `debug_page_idx` path is effective for token 1: GDB marker state
reported `page_idx=0` on both wait-enter and wait-return.

After the token1 wait-return marker, the chain was intended to wait for
`dma-wait-return token16`. No token16 output appeared before the non-interactive
GDB session was interrupted from the host. The SIGINT/timeout-wrapper path caused
GDB to disconnect without producing a live stack, so this run cannot prove a
real token2/token16 hang by itself. It does prove that the next probe must be
finer grained around token1 return, token cleanup, and token2 submit/wait.

## Next action

Do not jump directly from token1 to token16. Re-run with a shorter GDB command
chain that:

1. Stops at token1 wait-return.
2. Clears the generic `prt_gdb_marker_stop` breakpoint or keeps it filtered.
3. Steps/continues to token2 wait-enter, token2 wait-return, then token4/8/16.
4. Adds temporary source markers if needed immediately after `prt_dma_wait`,
   after `prt_dma_token_cleanup`, and at the top of the next page iteration.

If token2 remains hard to observe, add an `if (stage_idx == 0 && tensor_id == 0
&& i == N) { volatile int marker = 0; marker++; }` style source breakpoint in
the fixed-load page loop, then use GDB to move the page frontier without relying
on a large fixed breakpoint set.
