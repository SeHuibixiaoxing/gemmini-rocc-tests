## 尚未通过的点

手工 GDB 连接确实被 guest `gdbserver` 接受，但没有拿到完整 inferior 控制权。
GDB 侧现象为：

```text
warning: unrecognized item "timeout" in "qSupported" response
Remote replied unexpectedly to 'vMustReplyEmpty': timeout
The program is not being run.
```

随后 `gdbserver --once` 被消费，guest 侧记录 `Killing process(es): 116`，
workload 仍以 `rc=0` 结束并给出 FireSim `*** PASSED ***`。

这说明 TCP/RSP 连接已经到达 guest，但本轮手工命令序列没有形成可用的 GDB inferior
控制会话。该结果不能直接归因于 NIC 硬件失败，因为同一轮已经证明了：

- guest Linux boot 正常；
- IceNet 注册并拿到 `172.16.0.2`；
- host 到 guest 的 TCP 连接可达；
- `gdbserver` listen / accept / exit 路径完整；
- FireSim workload 自身 PASS。

## 当前判断

最新 `agfi-032d10150efc1d4ec` 已经把之前的 NIC / boot / gdbserver 基础链路问题
推进过去。剩余待验证的是 full remote GDB 功能矩阵：

- `target remote` 后稳定停在 `_start` / `main`；
- 多个 software breakpoint；
- `continue` / `next`；
- `info threads` / `thread apply all bt`；
- 寄存器、反汇编、变量和内存读写；
- 运行中 `Ctrl-C` 抢回控制。

下一轮不再使用手工一行式 GDB。应 fresh launch F2 后等待
`[gdbserver] phase=listening`，第一条 TCP 连接直接使用
`run_remote_gdbserver_software_expect_smoke.sh`，并设置足够长的
`GDBSERVER_SMOKE_EXPECT_TIMEOUT`。若 expect 仍复现 `qSupported` /
`vMustReplyEmpty` 失败，再保留现场并转向 RSP timeout / guest gdbserver 交互排查。
