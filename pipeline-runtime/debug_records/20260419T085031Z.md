## 新观察

### 1. 当前主线 authoritative frontier 仍是 `spm-xlate restore-begin`

- 低扰动、非 `TraceV` 主线下，当前最强的 authoritative 结论没有变：
  `spm-xlate-release mgr=5 cfg=15 phase=restore-begin`
- 对应软件边界在
  `src/prt_rerocc.c`：
  `release-end` 之后立刻记 `restore-begin`，
  再执行 `rr_restore_opcode_binding(3U, prev_binding)`，
  之后才会出现 `restore-end`
- 而 `rr_restore_opcode_binding()` 本体只剩一条：
  `rr_write_csr(CSR_RROPC0 + opcode_id, binding)`，
  再往下展开就是 `csrrw`

### 2. `TraceV/workerpc` 分支不是矛盾证据，而是同一 freeze 的更早暴露面

- `20260417T151600Z` 表明：
  sparse log 表面停在
  `stage=0 / subbatch=1 / tensor=2 / first-chunk-submitwait-end / page0`
  但 breadcrumb 实际已经深入到后续 page，
  最近可见 phase 是
  `dma_submitwait_after_cleanup`
- 这说明：
  当前 freeze 并不是“随机在不同地方卡住”，
  而是同一条长热路径会被不同观测面截成不同前沿

### 3. “卡点移动”主要来自 4 类观测误差，而不是 blocker 真在乱跑

1. **probe 扰动**
   - 文档已明确热路径文本日志会改变时序
   - 旧结论里多次出现 frontier 随 probe 类型变化而前移/后移
2. **sparse log 采样过粗**
   - `page0 first-chunk-submitwait-end` 只是 coarse 采样边界
   - 不能直接当真实停点
3. **breadcrumb 是更深证据，但也可能只显示“最后覆盖到的槽位”**
   - 只能说明执行至少推进到该 phase
   - 不能反推更早 coarse 文本边界就是最终冻结点
4. **guest sleep 型 probe 会在 freeze 后彻底失效**
   - `20260417T151600Z` 已证明 guest 时间停在约 `1970-01-01T00:00:04Z`
   - 依赖 `sleep 10/30/60s` 的 shell delayed probe 根本不会醒

### 4. 当前最小、最值得继续收窄的窗口仍有两层

- **层 1：主线 authoritative**
  - `spm-xlate restore-begin -> rr_write_csr(CSR_RROPC3, prev_binding) -> restore-end`
- **层 2：同一 freeze 的 earlier visible hotspot**
  - `dma_submit_wait_annotated_scoped()` 返回后
  - `dma_page_end`
  - `sw-e`
  - `copied/remaining` accounting
- 这也是为什么上一轮只补了二进制 breadcrumb phase，
  而没有继续堆字符串日志

## 分析

- 当前没有静态证据支持“blocker 每次都真的移动到别的逻辑点”。
- 更合理的统一解释是：
  1. 真正问题依旧是 timing-sensitive；
  2. coarse sparse / delayed shell probe / 热路径日志，会把同一 freeze 映射成不同表面前沿；
  3. 低扰动主线下，最可信的 authoritative frontier 仍然是
     `spm-xlate restore-begin`；
  4. `TraceV/workerpc` 分支只是说明同一 freeze 在 export DMA 热路径上也有更早可见热点。
