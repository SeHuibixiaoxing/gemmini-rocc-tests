## 本轮静态钉死的问题

`simif_f2.cc` 把 BAR4 以 `BURST_CAPABLE` 方式 attach：

```text
sims/firesim/sim/midas/src/main/cc/simif_f2.cc
fpga_pci_attach(... APP_PF_BAR4, BURST_CAPABLE, &pci_bar4_handle)
```

AWS F2 SDK 的 `fpga_pci_attach()` 在 `BURST_CAPABLE` 打开时会映射 `/sys/bus/pci/devices/.../resource4_wc`，也就是 write-combining BAR4 映射；`fpga_pci_poke64()` 本身只是对 mmap 地址做普通 `uint64_t` store。

CPU-managed stream 不是普通内存：

- host->target `push()` 先读 FIFO count，再把 token beat 写入 `dma_addr()`；
- target->host `pull()` 读出的数据是 destructive FIFO dequeue；
- `CPUManagedStreamEngine` 明确把 from-host streams 实现为 AW/W/B 写入 BRAM FIFO，把 to-host streams 实现为读出 FIFO。

AWS F2 文档要求 prefetchable/WC BAR 必须按客户逻辑支持的方式访问，并提示包含 FIFO / clear-on-read 语义的空间不能按普通可预取内存处理。F2 SDE 示例也同时保留普通 BAR4 handle 和 WC BAR4 handle，只把受约束的 descriptor RAM 用 WC，并在文档中明确传统 write-combine 会产生乱序写，SDE 不支持乱序 descriptor write。

结论：当前 FireSim F2 driver 用 WC 映射访问 CPU-managed stream FIFO 是一个确定的软件缺陷。它会破坏 FIFO push/read 的顺序和可见性契约；这与当前 `dma-pcis-timeout` 写侧 timeout、host 包已进入 SimpleNIC push 路径但 target 没有形成回包闭环的证据一致。

## 本轮修改

修改：

```text
sims/firesim/sim/midas/src/main/cc/simif_f2.cc
```

把 BAR4 attach flags 从 `BURST_CAPABLE` 改为 `0`，即使用非 WC 映射访问 CPU-managed stream：

```text
fpga_pci_attach(slot_id, FPGA_APP_PF, APP_PF_BAR4, 0, &pci_bar4_handle)
```

这不是硬件 RTL 修改，不需要重新构建 bitstream。需要重新 `infrasetup`，让 F2 run host 使用新编译的 driver，然后 fresh F2 runfarm 重跑同一 AGFI。
