因此这不是 remote gdbserver 本身的失败；guest 内核、网络配置、`gdbserver --once`

## 与已知通过路径的关系

`20260502T123027Z.md` 已验证 old AGFI `agfi-0079cbbca617eca4e` 在同一类 relaxed
runtime 下可以完成 software-breakpoint remote gdbserver 回归：

- `target remote` 成功；
- 多个软件断点可设置并命中；
- 多线程 `info threads` / `thread apply all bt` 可用；
- 寄存器读取可用；
- guest 最终 `*** PASSED ***`。

因此当前 `agfi-061be7985d82296be` 的失败不推翻 “NIC + software gdbserver 链路已经
在 old AGFI 上跑通” 这个结论。它说明最新 single-core NIC bitstream 仍没有复现 old
AGFI 的硬件运行稳定性。

## 当前结论

本轮卡点比 remote gdbserver 更早：最新 AGFI 在 target cycle 0 全局闭合失败，Linux
未启动。静态排查应优先回答：

1. 最新源码相对于 old AGFI 已知通过语义，是否引入了会改变 first-cycle ready/valid
   闭合的 RTL/driver 行为；
2. `SimpleNICBridge` 当前 self-generated no-packet token、`macAddr`、`rlimit`、
   `pauser` 的 valid/ready 驱动是否与 FireSim HostPort 合约一致；
3. `TargetCycleDebugWidget` / debug instrumentation 是否只是观测，还是可能改变
   bridge scheduling 或 first-cycle ready/valid；
4. 若代码层无直接错误，再把 `agfi-061be7985d82296be` 视为受 timing/OCL 风险污染的
   bitstream，重新构建前必须加入更完整、可综合且低扰动的 HostPort / OCL / bridge
   闭合观测点。
