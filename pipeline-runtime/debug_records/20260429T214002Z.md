## 静态判断

当前软件/RTL 事实：

- `SimpleNICBridge` 已经抑制 target->host 空 token：`ntht_queue.io.enq.valid := toHostPayloadValid`；
- host C++ driver 的 relaxed pull 模式只清 bigtoken header；
- `simplenic.cc` 的 `count_valid_flits()` 只看 bigtoken/LRV header，不验证 data 是否构成有效以太网帧；
- `SSHPort::send()` 会按 valid/last flit 组包并写入 TAP。若 switch 收到一个 `valid+last` 且 data 为 0 的单 flit，TAP 层会看到全零或近似空的短帧；
- 当前 `simplenic round debug` 为 0，`switchlog` 也没有 flit 内容 dump，所以现有现场还不能直接证明零帧是在 driver pull buffer、switch shared-memory 入口，还是 tap 发送前生成的。

结论：PCIS read lane 修复已经把系统推进到 Linux/gdbserver listening；当前最需要钉死的是 target->host 包在 host 软件链路中的第一个损坏点。这个判断不需要先重建 bitstream，应该先加 C++ driver/switch 的 bounded instrumentation 后重跑同一 AGFI。

## 下一步

先做软件侧观测补丁，然后 `infrasetup` 重新构建 driver/switch，再用 fresh F2 runfarm 跑同一 AGFI：

- 在 `simplenic.cc` 中打印 target->host pull 到的 token 字节数、valid flit 数、首批 valid/last/data；
- 对 `valid+last && data==0`、首 flit 为 0、非以太网最小长度等情况打一次性告警；
- 在 host->target push 前打印来自 switch 的 peer flit 样本；
- 在 switch `SSHPort::send()` 前打印将写入 TAP 的 packet flit 数、tap length、前 16 字节，并标记短帧/全零以太网头；
- 在 switch input 组包处打印来自 ShmemPort 的首批 flit，确认损坏是否已经出现在 shared-memory 入口。

如果 bounded instrumentation 能钉死为 C++ driver/switch 逻辑错误，则直接软件修复并重测；如果钉死为 BAR4/PCIS 写侧或 RTL stream protocol 错误，再启动下一轮 `m8i.2xlarge` bitstream 构建。
