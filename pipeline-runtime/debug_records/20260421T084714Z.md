## 这次看了哪些链路

### 1. FireSim runtime topology 本身只负责 host 侧拓扑

检查：

- `/home/ubuntu/chipyard/sims/firesim/deploy/runtools/user_topology.py`

关键代码：

- `example_1config()` 只做：
  - `self.roots = [FireSimSwitchNode()]`
  - `servers = [FireSimServerNode() for y in range(1)]`
  - `self.roots[0].add_downlinks(servers)`

这说明：

- `example_1config` 只是 manager/runtime 侧的
  `switch -> server`
  拓扑定义
- 它不会修改 target RTL
- 更不会给一个本来不带 NIC 的 target “凭空补一个网卡”

所以之前看到：

- `tap0 LOWER_UP`
- `switch0` 绑定 `tap0`

只能证明 host 侧拓扑和 switch 路径是通的，
不能证明 guest 内就一定会出现 `eth0`

### 2. 当前自定义 pairmanager target config 并没有显式加 `WithNIC`

检查：

- `/home/ubuntu/chipyard/generators/chipyard/src/main/scala/config/GemminiLearningReRoCCPairManagerConfigs.scala`
- `/home/ubuntu/chipyard/generators/firechip/chip/src/main/scala/TargetConfigs.scala`

关键点：

- 当前 12-pair 目标类是：
  `GemminiLearningConfigSpadReRoCCGlobalNoC4C2x2P12x4x3CoupledDMAPairManagerDummy16x16Sbus128`
- 它最终拼接的是：
  - pair manager 自定义配置
  - `WithUniformBusFrequencies`
  - `WithNBigCores`
  - `WithNMemoryChannels`
  - `AbstractConfig`
- 它自己没有显式拼 `new firechip.chip.WithNIC`

对照 FireSim 官方 target config 写法可见：

- FireSim 若要带 NIC，通常会显式把 `WithNIC` 串在 target config 名字里
- 当前这条自定义配置没有这样做

### 3. 真正决定 guest 是否出现 NIC 的硬件门槛在 `NICKey`

检查：

- `/home/ubuntu/chipyard/generators/icenet/src/main/scala/NIC.scala`
- `/home/ubuntu/chipyard/generators/chipyard/src/main/scala/iobinders/IOBinders.scala`

关键逻辑：

- `CanHavePeripheryIceNIC` 只有在 `p(NICKey)` 非空时才会构造 `icenicOpt`
- `WithNICIOPunchthrough` 也只有在 `system.icenicOpt` 存在时才会产生 `NICPort`
- `NICPort` 才会进一步被 FireSim 的 `WithNICBridge` 接出去

也就是说，这条链是：

`WithIceNIC/WithNIC -> NICKey 生效 -> target 里实例化 IceNIC -> punchthrough 出 NICPort -> FireSim NICBridge 存在 -> guest Linux 可枚举 NIC`

当前如果最前面的 `WithNIC` 没有进 config，后面这整条链都不会成立。

### 4. 已生成的 target DTS 直接证明：有块设备，没有 NIC

检查目录：

- `/home/ubuntu/chipyard/sims/firesim-staging/generated-src/firechip.chip.FireSim.WithDefaultFireSimBridges_WithFireSimConfigTweaks_chipyard.GemminiLearningConfigSpadReRoCCGlobalNoC4C2x2P12x4x3CoupledDMAPairManagerDummy16x16Sbus128`

这个目录名本身就已经给了第一条强信号：

- 它是
  `WithDefaultFireSimBridges_WithFireSimConfigTweaks_...`
- 但不是
  `WithNIC_WithDefaultFireSimBridges_...`

继续检查 DTS：

- `/home/ubuntu/chipyard/sims/firesim-staging/generated-src/firechip.chip.FireSim.WithDefaultFireSimBridges_WithFireSimConfigTweaks_chipyard.GemminiLearningConfigSpadReRoCCGlobalNoC4C2x2P12x4x3CoupledDMAPairManagerDummy16x16Sbus128/firechip.chip.FireSim.WithDefaultFireSimBridges_WithFireSimConfigTweaks_chipyard.GemminiLearningConfigSpadReRoCCGlobalNoC4C2x2P12x4x3CoupledDMAPairManagerDummy16x16Sbus128.dts`

明确看到：

- `blkdev-controller@10015000`

但全文搜索：

- `ice-nic`
- `nic@10016000`
- `ethernet`

全部不存在。

这是一条很强的静态证据：

- 这版 target 的 guest 可见设备树里有 block device
- 但没有 NIC 设备节点

Linux 在这种前提下，本来就不应该枚举出可用网卡。

### 5. 这也解释了此前所有动态现象

之前动态上出现过这些看起来“矛盾”的现象：

- host `tap0` 能 `LOWER_UP`
- `switch0` 日志表明 `SSHPort` 路径已生效
- guest 里 `gdbserver` 能进入 `phase=listening`
- 但 `gdbserver.info` 里的 `net_dev=`、`guest_ipv4=` 仍然为空

现在可以统一解释为：

1. `example_1config + SSHPort + tap0`
   只让 host 侧 FireSim 网络拓扑成立
2. `gdbserver`
   只说明 guest 进程本身确实在 listen
3. 但 target 没有 IceNIC
   所以 guest Linux 没有网卡
4. 没有网卡
   就没有 `172.16.x.y`
5. 没有 guest IPv4
   host 当然也就不可能 `target remote 172.16.x.y:2345`

所以此前反复出现的：

- `guest_ipv4=unknown`
- `ip neigh ... FAILED`
- `No route to host`

并不是脚本探测太弱导致的全部问题，
而是更前面的硬件前提就缺了。

## 与 AWS F2 的关系

本轮也顺手核对了思路边界：

- AWS F2 只提供宿主机实例自己的 ENA/网络能力
- FireSim guest 想要在 Linux 里看到网卡，
  仍然必须依赖 target RTL 中存在 IceNIC 这一类设备

换句话说：

- F2 host 有网络
  不等于
- FireSim guest 一定有网络设备

这也是为什么继续围绕 AWS 实例网卡本身做排查，没有办法解决当前 guest 无 netdev 的问题。

## 当前结论

当前 `pipeline-runtime` 主线的 `gdbserver over guest TCP` 调试路径已经卡在一个明确、静态、可复现的前提缺失上：

- 不是应用程序又换地方卡了
- 不是日志把卡点“扰动”到了别处
- 不是 host `tap0` 还没准备好
- 而是当前 bitstream 对应 target 不带 NIC

## 下一步建议

1. 如果目标仍是 `gdbserver` live attach：
   先构建一版显式带 `WithNIC` 的 pairdummy bitstream，再回来走当前 SOP
2. 如果短期不想重建 bitstream：
   不要再押注 guest TCP `gdbserver`
   改走：
   - guest-side `gdb` batch
   - `ptrace` probe
   - 或继续 `TraceV`
3. 在新的 NIC bitstream 出来前，
   这一条 `gdbserver` workflow 不应再继续消耗 F2 机时
