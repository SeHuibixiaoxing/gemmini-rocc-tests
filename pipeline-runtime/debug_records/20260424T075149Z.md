## 新观察

### 1. 和远端最新 `main` 相比，当前真正和 NIC 卡死现象直接相关的本地改动只有 `SimpleNICBridge` 这一处

对比 `origin/main` 和 `upstream/main` 后，结论一致：

- `SimpleNIC.scala`
- `NIC.scala`
- `simplenic.cc`

这三份文件相对最新 `main` 没有本地语义性修改。

与当前 NIC 早死直接相关的差异只有：

- `SimpleNICBridge.scala`

而且就是本地之前加的 lockstep token 推进补丁：

- `tFireHelper` 新增 `ntht_queue.io.enq.ready`
- `tFireHelper` 新增 `htnt_queue.io.deq.valid`
- `hPort.toHost.hReady` / `hPort.fromHost.hValid`
  改成受 `tFire` 共同驱动
- `target.in.valid` 改成 `&& tFire`

这说明：

- 远端最新 `main` 并没有给出新的 `SimpleNIC` / `IceNIC` 主线修复
- 当前“`ready` 语义被抹平”的核心结构并不是我们最近才引入的

### 2. `data_in_ready := true.B` 和 `//target.out.ready := ...` 这两个可疑点，在最新 `main` 里也仍然存在

`git blame -L 199,213` 显示：

- `ntht_queue.io.enq.bits.data_in_ready := true.B`
- `//target.out.ready := htnt_queue.io.deq.bits.data_out_ready`

不是这次本地 lockstep 改动带来的。

这两行来自历史提交：

- `f23b1d283`

也就是 FireSim 从 Chipyard 拆分后的早期代码。

因此当前静态怀疑不能表述成：

- “本地新补丁把 `ready` 线路弄坏了”

更准确的表述应当是：

- upstream 主线长期就是这种 `Valid-only` + token 辅助位的建模方式
- 而我们现在观察到的 host-side `push()==0`
  很可能暴露的是这套旧语义在当前配置、当前 bitstream 或当前时序条件下的脆弱性

## 当前结论

本轮对比结果可以明确回答用户的问题：

### 一、最新 `main` 没有现成修复

和远端最新 `main` 相比，当前 NIC 早死路径上没有 upstream 新修复可直接拿来用。
真正和现象直接相关的本地差异，只有尚未提交的
`SimpleNICBridge` lockstep token 推进补丁。

### 二、当前最可疑的静态风险不是本地最近才改坏的，而是 upstream 长期就存在的桥接语义

`NICIOvonly` 去掉 `ready`，
再加上 `SimpleNICBridge` 中：

- `data_in_ready := true.B`
- `target.out.ready` 未反馈

这些都不是本地新引入，而是 upstream 长期存在的实现选择。

### 三、GitHub issue 没有直接命中，但 FireSim 邮件列表里有一个高度相似的 host-side mismatch 案例

那个案例证明：

- `withNIC` 走错 topology 时，确实会在 host-side `SimpleNIC` 层直接炸掉

但本地已经切到 `example_1config`，所以当前剩余问题并不能再用这个解释覆盖。

## 下一步建议

下一轮继续保持低扰动，优先做两件事：

1. 不再新增大量 guest 日志，而是在 `SimpleNICBridge` / stream 计数层加极小观测面
   目标是直接回答：
   - `from_cpu` stream 的 occupancy 是否在刚开始就异常偏满
   - target 是否真的在消费 host 注入的 NIC token
2. 在不影响现有大 bitstream 任务的前提下，优先在最小 metasim 或最小 host 驱动观测面上验证：
   - upstream 原始 bridge 是否复现相同早死
   - 本地 lockstep 补丁是缓解、无效，还是只是把故障表象换了位置

只有把这两点钉死，后面再决定是继续修 bridge 语义，还是回到 bitstream/timing 路径。
