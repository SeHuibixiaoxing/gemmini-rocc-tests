### 5. `tok=1217 > 1024` 不是 completion-slot wrap bug 的直接证据
- token id 通过 `__sync_add_and_fetch(&rt->next_dma_token_id, 1)` 单调递增。
- completion slot 是独立的 `0..1023` 池：
  - acquire 时扫描 `dma_completion_flag_used[]`
  - release 时清零 `used[slot]`
- 当前 `tok=1217` 已成功走到 `doneflag_end`，说明本次 slot acquire 已成功，不是“>1024 直接打坏 slot 池”。
- 仍需继续排查是否存在某些异常路径漏 release，但这不是当前 page60 frontier 的直接解释。

### 6. `ASYNC -> BLOCKING` 降级原因已再次确认
- 代码位置：`src/prt_runtime.c:4423-4433`
- 逻辑：
  - 默认把 `sync_mode` 设为 `ASYNC`
  - 但只要 `spm_xlate_enable=1`，就强制改成 `PRT_SYNC_MODE_BLOCKING_DEBUG`
  - 同时强制：
    - `dma_backend = PRT_DMA_BACKEND_BLOCKING_FENCE`
    - `gemmini_mode = PRT_GEMMINI_MODE_BLOCKING_FENCE`
- 设计原因：
  - 当前页粒度 SPM 翻译路径还没有实现“token-chained async paging”。
  - 因此一笔逻辑 DMA 在分页/翻译/作用域释放语义下，不能安全地按旧 async 方式放飞。
  - 当前正确性路径改为 fence-based completion：
    - program DMA
    - `hw_dma_fence()`
    - 必要时 `prt_rr_fence_scope()`
    - 再 release scope
  - 当前 backend 不再依赖 DMA doneflag 轮询作为完成判定。
