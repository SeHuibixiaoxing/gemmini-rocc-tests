## Observation

The stale AGFI did not reach OpenSBI/Linux. `runworkload` showed the driver and
switch alive, but the target never produced UART output after:

```text
FireSim fingerprint: 0x46697265
Commencing simulation.
```

Live GDB attach to host `FireSim-f2` and
`simplenic_t::dump_host_debug("live_gdb_snapshot", 58560, 0)` showed the bridge
had not advanced the first target cycle:

```text
debug_cycle = 0
minobs_marker = 0
target_cycle_ready = 0
all relevant ready/valid signals = 0
```

This places the failure earlier than Linux, earlier than `gdbserver`, and
earlier than any guest software breakpoint path.

## Root Cause

The current source had an over-broad from-host readiness aggregation in
`SimpleNICBridge.scala`. The NIC bridge was treating unrelated config channels
(`macAddr`, `rlimit`, `pauser`) as part of the per-cycle from-host NIC data
handshake. At reset/first cycle those config channels are not part of the NIC
packet token exchange, so this aggregation could hold `targetCycleReady` low
even when the only handshake that should matter is `hPort.nicIn.ready`.

The deadlock chain is:

```text
host driver enters simulation
-> bridge expects unrelated config-channel readiness as part of from-host cycle readiness
-> targetCycleReady remains 0
-> no target token fires
-> debug_cycle remains 0
-> no OpenSBI/Linux UART output
```

This also explains why UART/TSI-only hardware was unaffected: the failure is in
the NIC bridge's token-cycle gating, not in the base UART or TSI boot path.

## Fix Applied In Source

`generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`
now gates the from-host side only on the actual NIC input channel:

```scala
val nicInChannelReady = hPort.nicIn.ready
val fromHostChannelReady = nicInChannelReady
val nicInChannelValid = hPort.nicIn.valid
val fromHostChannelValid = nicInChannelValid
val targetCycleReady = toHostReadyDrive && fromHostChannelReady
val targetBlockedFromHostChannels = fromHostTokenAvailable && !hPort.nicIn.ready
```

The previous target-to-host CPU-managed stream fix remains required:

```scala
val readRequestActive = grant && axi4.ar.valid
ser_des.io.wide.in.valid := outgoingQueueIO.deq.valid && readRequestActive
outgoingQueueIO.deq.ready := ser_des.io.wide.in.ready && readRequestActive
```

That fix is in
`sims/firesim/sim/midas/src/main/scala/midas/core/CPUManagedStreamEngine.scala`
and prevents the width adapter from hiding the only outgoing token from the host
driver's FIFO count polling logic.
