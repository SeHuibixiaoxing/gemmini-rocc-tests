## NIC observations

The target Linux driver registered the guest NIC as:

```text
Registered IceNet NIC 00:12:6d:00:00:02
```

Before the static-neighbor attempt, the host learned a different ARP sender hardware address from the packet payload:

```text
172.16.0.2 lladdr 00:12:65:00:00:02
```

The switch log showed Ethernet source MAC `00:12:6d:00:00:02`, so the mismatch is inside the ARP payload rather than the Ethernet header. Replacing the host neighbor entry with the target driver's MAC fixed the L2 destination used by the host:

```text
172.16.0.2 lladdr 00:12:6d:00:00:02 PERMANENT
```

However, ping and TCP still failed. A manual checksum check on a target-to-host ICMP reply observed in `switchlog` reported non-zero recomputed checksums:

- IP checksum recomputation: `0x0800`
- ICMP checksum recomputation: `0x0004`

This is consistent with target-to-host packet corruption after frames leave the guest NIC path, not with GDB breakpoint semantics.

## Interpretation

This rerun did not reproduce the earlier old-AGFI GDB success. Because the hardware image is the known-good 1bp AGFI and the corrected expect harness never got past the initial TCP connection, the current blocking issue is most likely in the current host-driver/switch/runtime transport path or in the exact driver bundle deployed with this HWDB.

The most suspicious software delta remains the FireSim switch shared-memory path, especially the current `ShmemPort::send()` behavior that preserves the `0xDEADBEEFDEADBEEF` empty-round marker instead of restoring the older behavior that cleared it before sending. The next control should rebuild or redeploy an old-AGFI driver bundle with the conservative switch behavior restored, then rerun this same old-AGFI test before judging the new 1bp bitstream.
