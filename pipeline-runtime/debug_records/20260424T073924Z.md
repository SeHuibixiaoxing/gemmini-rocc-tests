## 新观察

### 1. FireSim 原生“带网卡”路径，本质上就是 `IceNIC` + FireSim networked topology

Chipyard 原生文档明确写的是：

- `IceNet` 是网络相关 Chisel 库；
- 其主要组件 `IceNIC` 主要用于 FireSim 的多节点网络仿真；
- Linux 侧默认就有 `IceNet driver`，能接入完整 Linux networking stack。

对应证据：

- `docs/Generators/IceNet.rst`
- `docs/Chipyard-Basics/Chipyard-Components.rst`

所以：

- 你现在说的“看看是否有别的网络内容，例如 icenet”，答案是有，而且它不是旁支，
  而是 FireSim 原生 NIC 主线。
- 当前这条 `WithNIC` 路径，target-side 外设本来就是 `IceNIC`。

### 2. 当前 FireSim `WithNIC` 目标配置，确实是在 target 里加了 `IceNIC`

`generators/firechip/chip/src/main/scala/TargetConfigs.scala` 中：

- `class WithNIC extends icenet.WithIceNIC(inBufFlits = 8192, ctrlQueueDepth = 64)`

这说明：

- FireSim 侧的 `WithNIC` 不是一个独立于 `icenet` 的神秘配置；
- 它就是把 target 中的 `NICKey` 设成 `IceNIC`，并给了较大的接收 buffer
  和控制队列深度。

### 3. 当前 FPGA 路径里，target-side 是 `IceNIC`，host-side 是 FireSim `SimpleNICBridge`

FireSim harness binder 里：

- `WithNICBridge` 把 `NICPort` 接到 `NICBridge(...)`

而这个 `NICBridge` 的 blackbox host module 就是：

- `firechip.goldengateimplementations.SimpleNICBridgeModule`

所以当前完整链路是：

1. target Linux / baremetal 软件看到的是 `IceNIC`
2. `IceNIC` 对外暴露 `NICIOvonly`
3. FireSim 把这组 NIC IO 交给 `SimpleNICBridge`
4. `SimpleNIC` host driver 再和 software switch / shared-memory 端口交互

这很关键，因为它说明：

- `icenet` 和 `SimpleNIC` 不是互斥替代方案；
- 它们分别在 target side 和 host bridge side；
- 你当前卡死的位置，仍然是在 `IceNIC` 之后、guest Linux 之前的 host bridge 层。

### 4. `IceNIC` 在 Chipyard 本地仿真里还有两种原生 harness 用法，但都不是当前 FireSim FPGA 主线

Chipyard harness binder 里有两条专门的 NIC harness 路：

- `WithLoopbackNIC`
- `WithSimNetwork`

其中：

- `WithLoopbackNIC` 是把 NIC 自己 loopback；
- `WithSimNetwork` 是挂 `icenet.SimNetwork` blackbox；
- `SimNetwork` 的实现来自 `generators/icenet/src/main/resources/vsrc/SimNetwork.v`
  和 `csrc/SimNetwork.cc`。

这条路径更像：

- Chipyard 本地仿真 / target-level sim / 非 FireSim harness 的网络模型；
- 它不是 FireSim manager 在 FPGA 上跑的那条 `switch0 + shmemport + SimpleNIC` 主线。

因此：

- 如果你想验证 `IceNIC` 自身 guest-visible 语义，`SimNetwork` 是有参考价值的；
- 但它不能直接替代当前 FPGA 上的 FireSim NIC bridge 路径。

### 5. FireSim 原生文档明确支持 networked simulation、custom topology、单节点 NIC、以及把模拟节点接到 host/TAP/外网

FireSim 文档中有几类正式支持的网络内容：

1. `networked simulation`
   - `topology`
   - `link_latency`
   - `switching_latency`
   - `net_bandwidth`
   - `user_topology.py` 自定义拓扑
2. 单节点 networked cluster
   - `example_1config`
3. 把单节点模拟机通过 `SSHPort + tap0` 接到宿主机网络
   - 可直接 SSH 进 guest
   - 可做 NAT 出外网

这意味着：

- FireSim 原生并不只支持“纯交换机内部网络”；
- 它原生就支持把模拟节点挂到 host TAP，再从 host 转发到真实网络；
- 这对 `gdbserver` 路径是有直接启发的，因为它证明 guest 网络访问和 host attach
  是 FireSim 官方支持的使用方式，不是旁门左道。

### 6. FireSim 文档对 healthy NIC boot 的期望非常明确

cluster simulation 文档给出的正常 boot 片段是：

- `Registered IceNet NIC 00:12:6d:...`
- `Starting network: OK`
- 然后 Linux 登录

而 Ubuntu base workload 的 `start-firesim-network.sh` 也表明：

- 它会检查 `eth0` 的 MAC 前缀是否是 FireSim 的 `00:12:6d`
- 如果是，就切成 FireSim 静态地址配置

因此，如果当前系统健康，guest Linux 侧至少应能走到：

- `icenet-driver` probe
- `eth0` 出现
- `start-firesim-network.sh` 运行

而我们当前最小 smoke 根本没到这一步。

### 7. `icenet-driver` 的 guest 语义也很清楚：MMIO + IRQ + DMA + 标准 netdev 注册

Linux 侧驱动 `icenet.c` 里：

- 通过 device-tree compatible `ucb-bar,ice-nic` / `ucbbar,ice-nic` probe
- 读 MMIO `ICENET_MACADDR`
- `register_netdev`
- 最后打印 `Registered IceNet NIC ...`

这说明：

- 一旦 guest Linux 起来，并且 `IceNIC` 外设和中断映射没坏，
  这条打印应当非常早就出现。
- 当前看不到这条打印，不是 `icenet-driver` 静默失败，
  而是系统压根没进入那一层。

### 8. FireSim 文档还明确说：networked metasim 是正式支持的

`RTL-Simulation.rst` 明确写到：

- manager-based metasim 保持和 FPGA 一样的 `launchrunfarm -> infrasetup -> runworkload`
  流程；
- 支持 `topology` / `no_net_num_nodes`；
- 支持 networked simulation；
- 支持现有 FireSim debugging 工具。

这意味着：

- 如果后续我们需要把网络问题再缩小到非 FPGA 路径，原生推荐路径仍然是
  FireSim metasim，而不是随手拼一个独立 Verilator 回归。

## 分析

### 一、`icenet` 不是“可能存在的另一个网络实现”，而是当前 target-side NIC 的正式实现

当前路径不是：

- `SimpleNIC` 和 `IceNIC` 二选一

而是：

- target side: `IceNIC`
- host bridge side: `SimpleNICBridge` + host-side `simplenic` driver + switch model

所以从代码结构上看，当前 FPGA 卡点可以分成三层：

1. `IceNIC` target 设备是否已经被生成并连接到总线
2. `NICBridge/SimpleNICBridge` 是否正确把 target token 和 host token 对接
3. switch / shmem / tap0 / SSHPort 是否正确提供外部网络环境

而你现在碰到的最早期失败，仍然停在第 2 层。

### 二、原生文档支持“guest Linux 自动识别 NIC 并起网络”，所以当前不是 guest 网络配置问题

FireSim 官方文档的健康路径非常清楚：

- Linux 很早打印 `Registered IceNet NIC`
- 然后 `Starting network: OK`
- 然后可以登录，甚至可以继续用 `SSHPort` 接到 `tap0`

当前最小 smoke 完全没看到这些输出。

因此可以静态排除：

- guest `gdbserver` 启动脚本写错
- Ubuntu/Fedora/Buildroot 的启网脚本没跑
- Linux 内核里 `icenet-driver` 配置不对

这些都需要先进入 guest Linux 才有机会发生。

### 三、当前更像 FireSim 原生 bridge / switch 层问题，而不是 `icenet` 外设逻辑本身首先暴露的问题

FireSim bridge 文档明确写：

- NIC model 的 driver 会“成批搬运 token”，在 software switch 和 bridge module 之间移动 token。

这和我们当前现场现象吻合：

- `simplenic_t::push()` 在 bulk push 时直接返回 `0`

而 `icenet-driver` 的 guest 层语义根本还没开始执行。

所以回到当前问题本身，阅读原生文档后的静态结论是：

- 你建议看的 `icenet` 很重要；
- 但它更多帮助我们确认“guest 看到 NIC 后本该发生什么”；
- 对当前这个“仿真刚开始就死在 token push”的卡点，最直接的主责模块仍然是
  FireSim `SimpleNICBridge` / host-side `simplenic` / switch 交界。

### 四、FireSim 原生还有一个很实用的网络旁路工具：`SSHPort + tap0`

这是这轮文档审计里最值得记住的额外能力。

它说明：

- FireSim 官方就支持把单节点 networked simulation 接到 host TAP；
- 这样 guest 可以通过 `172.16.x.x` 被 ssh 进入；
- 甚至可以从 guest 出真实外网。

对当前主线的启发是：

- 一旦我们先把最早期 `SimpleNIC` host-side 早死修掉，
  后续不一定非要先把 `gdbserver` 自己的复杂自动探测脚本打磨到完美；
- 也可以用官方 `SSHPort/tap0` 路径，先把 guest 网络 attach 路径打通，
  再决定是继续用 `ssh`、`gdbserver`，还是 host 上的端口转发。

## 当前结论

1. FireSim/Chipyard 原生网络主线就是 `IceNIC` / `IceNet`，不是旁支。
2. 当前 FireSim `WithNIC` 目标已经在 target 里加入了 `IceNIC`。
3. 当前 FPGA 主线的真实路径是：
   `IceNIC -> NICPort -> SimpleNICBridge -> host simplenic driver -> switch/shmem/tap0`
4. `WithLoopbackNIC` / `WithSimNetwork` 是 Chipyard 本地 harness 网络模型，
   不是当前 FireSim FPGA NIC 主线。
5. FireSim 原生文档正式支持：
   - networked simulation
   - custom topology
   - 单节点 `example_1config`
   - `SSHPort + tap0` 接 host/外网
6. 健康系统应当在 guest 很早看到：
   `Registered IceNet NIC` 与 `Starting network: OK`
7. 当前最小 smoke 连这一步都没到，所以问题仍然在 guest Linux 之前。

## 下一步建议

1. 不要把排查重心放到 `icenet-driver` 或 guest 启网脚本本身；
   它们是后续层，不是当前最早期卡点。
2. 继续把主责点收敛在：
   - `SimpleNICBridge.scala`
   - host-side `simplenic.cc`
   - switch/shmem 侧 token 交互
3. 后续一旦最早期 NIC bridge 早死消失，可以优先考虑用 FireSim 原生
   `SSHPort + tap0` 路径验证 guest 网络 attach，而不是一上来继续堆复杂 `gdbserver`
   自动化。
4. 若需要继续做低成本复现，优先保留 FireSim manager-based metasim 的 networked 路径，
   因为原生文档明确支持它，而且它比重新构 bitstream 成本低得多。
