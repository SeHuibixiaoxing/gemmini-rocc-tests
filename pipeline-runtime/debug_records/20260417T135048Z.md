## 关键结论

### 1. `workerpc` rerun 的 freeze 位置与前一轮一致

- `guest-sparse-log.txt` 尾部再次出现：
  - `worker stage=0 subbatch=1 done`
  - `stage-exec-views phase=begin segment=0 stage=0 layer=0 tensors=4`
  - `stage-fixed-load-sparse phase=begin ... slot=0 tensor=1000000`
  - `stage-fixed-load-sparse phase=end ... slot=0 tensor=1000000`
  - `stage-fixed-load-sparse phase=begin ... slot=1 tensor=1000001`
- 最后可见的 fixed-load 内部边界仍停在：
  `rr-acquire-wrap phase=after-call stage=0 manager=0 opcode=2 rc=0 cfg=0 valid=1`

这说明：

- 这轮不是 boot/launch 偶发问题；
- guest 又一次深入到真实 runtime 热路径；
- freeze 仍然稳定落在
  `stage-fixed-load-sparse(slot=1, tensor=1000001)`
  之后的更深窗口里。

### 2. `workerpc` timeout capture 中 `TRACEFILE-C*` 依然严格为 0

- `...trace-files.txt` 记录：
  - `/home/ubuntu/sim_slot_0/TRACEFILE-C0..C3`
    全部 `0 bytes`
- `...TRACEFILE-C0.tail.txt` 为空文件

因此当前可以确定：

- 不只是 instruction-trigger (`selector=3`) 没拿到 trace；
- 这轮 PC-trigger (`selector=2`, `0x2a2b0 -> 0x2ab22`) 也没有产出任何 trace token。

### 3. 当前更像是“TracerV token 根本没被 host pull 到”，不是“tracefile 写失败”

静态阅读 `generators/firechip/bridgestubs/src/main/cc/bridges/tracerv.cc`
与
`generators/firechip/goldengateimplementations/src/main/scala/TracerVBridge.scala`
后，可确认：

- host 侧只有在 `pull()` 拿到 stream token 后才会写 `TRACEFILE`
- `selector=2` 的 PC trigger 也不是范围比较，
  而是“遇到 start PC 置位，遇到 end PC 清位”

所以 `TRACEFILE==0` 的解释优先级应当是：

1. trigger 没命中真实退休 PC
2. 或 target trace port 根本没向 host 产出有效 token

而不是简单归因为文件路径/写权限。
