## 结论

1. rebuilt image 已正确部署；`traceV` 参数与 guest-side debug 脚本都已生效。
2. 本轮 freeze 不是 boot / wrapper / runner shell 早期问题，而是再次回到
   `stage=0 / subbatch=1 / dma-export-host first-chunk-submitwait-end` 这一稳定窗口。
3. “卡点移动”继续被证伪：
   当前可见 frontier 仍落在同一条有序热路径上。
4. 这轮最大缺口仍然是：
   没有 freeze 当刻的 guest-side stuck-PC / syscall。
5. 仅靠当前 `180,480,900s` delayed probe 方案，
   仍然太晚，没能在 freeze 之前把现场抓出来。

## 下一步建议

1. 不再继续扩大热路径文本日志。
2. 下一轮把 stuck snapshot 前移成更早的一次性 guest-side probe，
   优先考虑：
   - `10s/30s/60s` 级别的 delayed probe
   - 或单独的 “after-bin-spawn + early-stuck-probe” 专用快照文件
3. 保持当前 `workerpc` profile，其它变量不动，
   只缩短 stuck snapshot 的触发时间，避免再次错过 freeze 窗口。
4. 若仍希望继续利用 TracerV，
   下一步不应再只看 `TRACEFILE-C* size`，
   而应补一条能证明 bridge 是否实际 dequeue 过 token 的 host-side证据。
