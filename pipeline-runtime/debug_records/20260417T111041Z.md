## Round Goal

验证新的 runtime worker 本地 `TracerV` 指令触发路径是否真正生效，并在 live FireSim FPGA 运行中用直接证据判断：

- trigger 指令是否进入最终 workload 镜像；
- host `FireSim-f2` 是否真的以 instruction-trigger 模式启动；
- guest 是否真的执行到 `stage_worker_main()` 中的 marker；
- 如果以上都成立而 `TRACEFILE-C*` 仍然为 0，是否可以收敛为 TracerV trigger 链本身没有 arm 上。

## Key Evidence

### 1. 先发现并修掉了 build 环境变量丢失的根因

对上轮 `tracerv-inst` build 的实际 tmux command 脚本和 FireMarshal build log 做核对后确认：

- `scripts/firemarshal-tmux-run.sh` 的环境转发白名单里没有
  `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS`
- 因此 `host-init.sh` 实际收到的是默认值 `0`
- FireMarshal build log 明确打印：
  `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS=0`

这解释了为什么“源码已加 marker，但最终 workload 二进制里没有 marker 字节”。

### 2. 修复后，marker 已经进入最终 workload 二进制和镜像

修复环境转发并重跑 `image-closure` 后：

- FireMarshal build log 明确打印：
  `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS=1`
- 本地 freshness 新增字节级校验后通过：
  - `runtime-binary-src tracerv worker markers expected=1 start=1 end=1`
  - `runtime-binary-img tracerv worker markers expected=1 start=1 end=1`
- 对 `rerocc_pipeline_runtime-linux` 的静态扫描确认：
  - start marker `0x00008013` 位于 `stage_worker_main + 0x26e`
  - end marker `0x00010013` 位于 `stage_worker_main + 0xae0`

### 3. run host 上的实际 `FireSim-f2` 确实以 instruction-trigger 模式启动

在 live run host `192.168.1.170` 上直接读取 `FireSim-f2` 的 `/proc/<pid>/cmdline`，确认实际参数包含：

- `+tracefile=TRACEFILE`
- `+trace-select=3`
- `+trace-start=ffffffff00008013`
- `+trace-end=ffffffff00010013`
- `+trace-output-format=0`

并且 `/proc/<pid>/fd` 中已经打开：

- `TRACEFILE-C0`
- `TRACEFILE-C1`
- `TRACEFILE-C2`
- `TRACEFILE-C3`

### 4. guest 确实执行到了 wrapper、runner、runtime 二进制，以及 worker 线程入口

live `debugfs` 读取 guest image：

- `bertmini-batch8.wrapper.stage`
  - 到达 `after-child-spawn pid=133`
- `bertmini-batch8.runner-early.stage`
  - 到达 `before-runner-enter`
- `bertmini-batch8.runner.stage`
  - 到达 `after-bin-spawn method=ours2 pid=197`
- `bertmini-batch8.runner-proc.stage`
  - `pid=197` 的实际命令行为：
    `/root/rerocc-linux-tests/pipeline-runtime/rerocc_pipeline_runtime-linux ...`
- `bertmini-batch8.log`
  - 已经通过 pipeline YAML 加载、mapping 文件加载和 parse
  - 已出现：
    - `segment=0 worker-create ... rc=0`
    - `worker entry begin stage=0 ...`
    - `worker stage=0 ready entries=1 exports=1 ...`

### 5. 代码上，`worker stage=0 ready ...` 后一行就是 start marker

`prt_runtime.c` 中顺序为：

1. `PRT_PROGRESS_LOG("worker stage=%u ready ...")`
2. `prt_firesim_tracerv_worker_start_marker();`
3. `while (!ctx->stop && !rt->stop_requested && !rt->fatal_error) { ... }`

因此只要 guest log 中出现 `worker stage=0 ready ...`，就可以判定：

- start marker 指令已经在 live guest 中被执行到。

### 6. 在以上全部成立的前提下，trace 仍完全没有写出

run host live 状态始终是：

- `/home/ubuntu/sim_slot_0/TRACEFILE-C0..C3` 全部大小为 `0`
- `/proc/<FireSim-f2-pid>/fdinfo/7`
  - `pos: 0`

即使在 guest 已经走到：

- wrapper
- runner
- runtime 主体
- `stage_worker_main()` 的 `worker ready`

之后，也仍然没有任何 trace 输出。

## Conclusion

本轮已经拿到比上轮更强的收敛结论：

- 最终 workload 二进制中确实有精确 marker 指令；
- host `FireSim-f2` 确实带着 instruction-trigger 参数启动；
- guest 也确实执行到了 `stage_worker_main()`，并且至少执行到了 start marker 前一行；
- 但 `TRACEFILE-C*` 与 trace fd 位置仍始终为 `0`。

因此，本轮不再支持“是 guest 没跑到 marker”这种解释。

当前最合理的收敛结论是：

- instruction-triggered `TracerV` 路径本身没有真正 arm 上，或者
- host/bridge/target 之间对 instruction trigger 的比较条件没有实际匹配成功。

## Suggested Next Step

下一轮不应继续在 guest 侧加更多 shell/log 级探针，而应转向 bridge/hardware 侧的定点验证，例如：

1. 直接证明 `TracerV` bridge MMIO 中的 `hostTriggerStartInst/Mask` 和 `hostTriggerEndInst/Mask` 在实际运行实例上被正确写入。
2. 对比 `TracerVBridge.scala` 的 `trace.insn` 宽度和 retire token 中实际暴露的指令编码，确认与 `0x00008013/0x00010013` 的匹配语义没有偏差。
3. 如果需要，构造一个更小的“上电后极早退休固定指令”的最小 workload，用来隔离验证 instruction-trigger compare，而不是继续在完整 pipeline runtime 上碰运气。
