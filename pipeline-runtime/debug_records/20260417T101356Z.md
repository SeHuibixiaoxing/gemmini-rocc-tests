## Round Goal

静态解释为什么这轮 `TracerV` instruction-trigger rerun 里：

- guest 已经执行到 pipeline-runtime 热路径
- 但 `TRACEFILE-C*` 仍然始终为 0

## Key Evidence

### 1. Guest 确实执行了 instruction-trigger 包装命令

当前镜像内：

- `/etc/init.d/S99run` 调用 `/firemarshal.sh`
- `/firemarshal.sh` 内容为：

  `/usr/bin/firesim-start-trigger && /root/rerocc-linux-tests/run_rerocc_pipeline_runtime_bertmini_fileonly_sync_capture.sh --batch 8 && /usr/bin/firesim-end-trigger`

因此这轮不是 “FireMarshal 没有执行 trigger 命令链”。

### 2. Trigger 工具本身的第一条指令与 FireSim 文档一致

源码：

- `software/firemarshal/boards/firechip/base-workloads/br-base/trigger/start.S`
- `software/firemarshal/boards/firechip/base-workloads/br-base/trigger/end.S`

二进制 `.text`：

- `start`: `0x00008013`
- `end`: `0x00010013`

对应文档：

- `sims/firesim/docs/Advanced-Usage/Debugging-and-Profiling-on-FPGA/TracerV.rst`
  - `start: ffffffff00008013`
  - `end: ffffffff00010013`

因此这轮也不是 “trigger 小工具发错了指令值”。

### 3. TracerV instruction trigger 在硬件里是按每个 core 独立比较 `trace.insn`

硬件实现：

- `generators/firechip/goldengateimplementations/src/main/scala/TracerVBridge.scala`

关键点：

- 每个 bridge 实例维护自己的 `triggerInstValVec`
- 比较条件是：
  - `!((hostTriggerStartInst ^ trace.insn) & hostTriggerStartInstMask).orR`
  - `!((hostTriggerEndInst ^ trace.insn) & hostTriggerEndInstMask).orR`
- Host 端输出文件也是每核独立：
  - `TRACEFILE-C0`
  - `TRACEFILE-C1`
  - `TRACEFILE-C2`
  - `TRACEFILE-C3`

这说明 instruction trigger 不是全局一次性打开所有核，而是哪个 hart 退休了匹配指令，就只打开哪个 hart 对应 bridge 的 trace。

### 4. 当前 run 的 host 侧没有出现任何对 `TRACEFILE-C0` 的真实写入

run host `192.168.1.238` 上：

- `/home/ubuntu/sim_slot_0/TRACEFILE-C0..C3` 一直是 0 bytes
- `/proc/4488/fdinfo/7`（`TRACEFILE-C0`）的 `pos` 一直是 `0`
- 对 `FireSim-f2` 做短时 `strace -p 4488 -e write,writev,pwrite64`：
  - 成功 attach/detach
  - 没有捕到任何 write syscall

因此这轮不是 “trace 已经在写，只是还没 copy-back”；更接近 “当前没有向 trace fd 产生实际 host-side 输出”。

### 5. Guest 热点确实已经进入 runtime，且最终又停在老的同一条主路径上

本轮最终 capture 的 sparse log 前沿：

- 已经过：
  - `worker stage=0 subbatch=3 done`
  - `stage-fixed-load-sparse phase=end ... slot=0 tensor=1000000`
- 最后稳定停在：
  - `stage-fixed-load-sparse phase=begin ... slot=1 tensor=1000001`
  - 后面只有对应的 `rr-acquire-*`
  - 没有新的 `stage-fixed-load-sparse phase=end`

host watchdog 最终在 idle `626s` 后超时终止 run-farm。

### 6. “卡点移动”可以由同一条顺序路径上的不同观测边界解释

历史记录里出现过的末端包括：

- `stage-fixed-load-sparse phase=begin ... slot=1 tensor=1000001`
- `stage-fixed-load-sparse phase=end ... slot=1 tensor=1000001`
- `spm-xlate-release ... phase=restore-begin`

静态代码表明这些点在同一条顺序路径上：

- `prt_runtime.c:2095`
  - `stage-fixed-load-sparse phase=begin`
- `prt_runtime.c:2109`
  - `prt_dma_copy_dram_to_spm_pages(...)`
- `prt_runtime.c:2120`
  - `stage-fixed-load-sparse phase=end`
- `prt_runtime.c:2195`
  - `runtime_flush_stage_spm_xlate(...)`
- `prt_rerocc.c:190`
  - `spm-xlate-release ... phase=restore-begin`

因此不同 rerun 里“最后一条看见的日志”移动，并不等于 blocker 本体在移动，更可能是：

- 观测面不同
- 日志密度不同
- 同一条热路径在卡死前最后刷到的边界不同

### 7. 当前 instruction-trigger 方案很可能只 arm 了 shell 所在 hart，而不是 stage worker 所在 hart

当前 runtime 代码：

- `prt_runtime.c:658-681`
  - `stage_bind_current_thread()` 会对 worker 线程执行 `sched_setaffinity`
- `prt_runtime.c:3884+`
  - `stage_worker_main()` 在线程入口调用 `stage_bind_current_thread()`

当前 capture 中的 guest log：

- `worker stage=0 ready ... acc=0 dma=0 tiles=8`

而 `pick_affinity_cpu()` 用的是：

- `exec->stage_acc_ids[ctx->stage_id]`

这说明 runtime 的热点 worker 线程会在进入真正热路径后绑定到特定 CPU。

但 `firesim-start-trigger` 是在运行 runtime 之前、由 shell 主线程执行的。

对当前 workload 来说，这会产生一个很自然的失配风险：

- start trigger 只打开 shell 当时所在 hart 的 TracerV
- 真正执行 `stage_worker_main()` 热路径的 hart 可能是另一个 CPU
- 结果就是：
  - `TRACEFILE-C*` 全部不增长或只积累极少量未 flush 数据
  - 但 guest 程序本身仍然照常推进到后续热路径

### 8. guest 镜像里可用 `taskset`

本地 FireMarshal 镜像检查结果：

- `/usr/bin/taskset` 存在
- 是到 `../../bin/busybox` 的 symlink

因此可以先用最小改动验证上述 hart-mismatch 假设。

## Conclusion

当前最强解释不是：

- TracerV 硬件路径被注释掉
- trigger 工具失效
- FireMarshal 没执行 wrapper

而是：

- TracerV 的 instruction trigger 是按核独立的
- 现有 `firesim-start-trigger` 只在 shell 所在 hart 上退休
- 真实热点 `stage_worker_main()` 在之后重新绑到了目标 CPU
- 从而导致真正热点 hart 没有被 trigger arm
