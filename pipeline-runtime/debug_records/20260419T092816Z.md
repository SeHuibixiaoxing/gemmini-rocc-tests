## 新观察

### 1. `rr_release()` 的软件 helper 与 `rr_acquire_cfg()` 明显不对称

- `rr_acquire_cfg(cfg, mgr)` 的路径是：
  - 先 `rr_write_csr(CSR_RRCFGx, acq=1)`
  - 再 `rr_read_csr(CSR_RRCFGx)`
- 这意味着 acquire helper 会利用
  `csr_cfg_io(i).stall := cfg_acq_state =/= s_idle`
  的 read-stall 语义，
  一直等到 client 侧 acquire handshake 完成后才返回 acquire 结果。
- `rr_release(cfg)` 却只有一条 `rr_write_csr(CSR_RRCFGx, 0)`，
  没有任何读回或其它 completion 等待。
- 所以 `rr_release()` 的软件可见语义并不是
  “release handshake 完成”，
  而只是
  “release 请求已经发起”。

### 2. `restore-begin` 之后最可能卡住的不是日志，而是下一条 `RROPC3 csrrw`

- 当前 linux binary 反汇编已经把这段顺序钉死：
  - `0x266c0: csrrw csr=0x804`（`rr_fence` BAR 写）
  - `0x266c4: fence`
  - `...`
  - `0x2673e: jal prt_rr_release_scope`
  - `...`
  - `0x267dc: jal prt_progress_log_impl`（`restore-begin`）
  - `0x267e0: csrrw csr=0x803`（`rr_restore_opcode_binding(3U, prev_binding)`）
- 因而用户看到
  `spm-xlate-release ... phase=restore-begin`
  却始终看不到 `restore-end`，
  一个非常直接的解释就是：
  这条 `csrrw 0x803` 还没退休。

### 3. 真正挡住后续 RoCC CSR/fence 的第一层，不一定是 manager `io.busy`，而是 client 自己的 `io.busy`

- ReRoCC client：
  `io.busy := (cfg_acq_state =/= s_idle || credits非满 || cfg_fence_state非idle)`
- Rocket decode：
  `id_do_fence := id_rocc_busy && (fence || rocc-csr-write) ...`
- tile 顶层又把所有 RoCC 模块的 `io.busy` 汇总到 `core.io.rocc.busy`。
- 所以当 `rr_release()` 发起后，
  即便 manager 侧只是还没回 `sRelResp`，
  client 的 `cfg_acq_state` 也已经先把
  **下一条 RoCC CSR 写 / 普通 `fence`**
  挡在 decode。
- 这解释了为什么：
  - 普通日志还能出现在 `rr_release()` 之后
  - 但真正下一条 `RROPC3` / `RRBAR` / `fence`
    却可能完全发不出去

### 4. 第二层风险才是 manager `sRelResp` 被 `busy`/`inst_q` 长时间压住

- manager 只有在
  `state === s_rel_wait && !io.busy && inst_q.io.count === 0`
  时才会送 `sRelResp`。
- 对 pair wrapper manager，
  `io.busy := gemmini.busy || dma.busy`。
- 因而一旦某个 Gemmini / DMA 子块仍未完全 drain，
  `sRelResp` 会被继续推迟，
  client 侧 `cfg_acq_state` 也就一直回不到 `s_idle`。
- 于是表面冻结点就会落在：
  `release-end/restore-begin` 之后的第一条 RoCC-sensitive 指令上。

### 5. `rr_fence()` 为什么“看起来阻塞”，而 `rr_release()` 不阻塞

- `rr_fence(cfg)` 展开后是：
  - `csrrw 0x804, cfg`
  - 普通 RISC-V `fence`
- `csr_bar_io.stall` 本身并不是当前 blocking 语义的关键；
  关键在于 BAR 写会让 `cfg_fence_state` 进入非 idle，
  从而把 client `io.busy` 拉高，
  紧随其后的普通 `fence` 就在 Rocket decode 里被 `id_rocc_busy` 挡住，
  直到 `sUnbusyAck` 回来。
- 所以：
  - `rr_fence()` 的“阻塞感”主要来自后面的普通 `fence`
  - `rr_release()` 因为缺少这个 readback / fence 哨兵，会先把控制流放回普通代码

## 分析

- 当前“RR release 语义和硬件 busy 风险”的更精确版本是：
  1. `rr_release()` 返回过早；
  2. 普通日志还能前进，给人一种“已经越过 release”的错觉；
  3. 但下一条 RoCC CSR / `fence` 会先被 client `io.busy` 挡住；
  4. 若 manager `sRelResp` 又被 pair wrapper `busy` 或 `inst_q` 压住，
     这个 decode stall 就会长期存在；
  5. 于是表面 frontiers 会在
     `release-end`、`restore-begin`、甚至更早/更晚的热点之间漂移。
- 这不是“随机碰运气卡不同位置”，
  而是一个固定协议空窗被不同观测面截成不同前沿。

## 本轮修改

- `prt_rr_release_scope()` 现在在 `rr_release(cfg)` 之后，
  追加一次对同一 `RRCFGx` 的读回，
  把 runtime scope 语义改成 blocking release：
  - begin
  - release CSR write
  - readback wait
  - end
- 新增 breadcrumb phase：
  `PRT_BREADCRUMB_PHASE_RR_RELEASE_AFTER_CSR_WRITE = 309`
  用来区分：
  - release 写已经发出
  - 但 readback / ack 仍未回来
- 在 `observability.md` 里补充这条低扰动经验：
  优先用 `release + readback sentinel`
  钉死“到底卡在 release ack 还是卡在后续 CSR”。

## 暂缓项

- 静态阅读中注意到 ReRoCC client 的
  `csr_bar_io` / `csr_opc_io.stall`
  没有像 `csr_cfg_io.stall` 那样显式赋值。
- 这属于 RTL hygiene / 后续审计项，
  但不是本轮验证 `rr_release` 空窗的必要条件。
- 为避免引入任何硬件生成物变化，
  本轮先不修改 `generators/rerocc/src/main/scala/client/Client.scala`。

## 结论

- 当前最重要的新静态结论是：
  **`rr_release()` helper 少了 acquire 那样的读回等待，因此天然存在 release-return / next-rocc-op 空窗。**
- 这个空窗会先被 client `io.busy` 放大成
  “后续 RoCC CSR/fence 不能退休”，
  再被 manager `busy` / `inst_q` 是否清空决定会不会拖成长期 hang。
- 因而避免该风险的最低扰动做法不是继续堆日志，
  而是：
  **在 release 后立刻读回同一 `RRCFGx`，把 frontier 固定到 release ack 本身。**
