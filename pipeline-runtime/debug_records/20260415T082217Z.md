## 分析

- 代码默认值虽然是 async:
  - `main.c` 默认 `dma_backend=POLL_PROGRESS_THREAD`
  - `main.c` 默认 `gemmini_mode=ASYNC_EXPERIMENTAL`
  - `main.c` 默认 `sync_mode=ASYNC`
- 但当前固定配置实际启用了 `spm_xlate_enable=1`
- `prt_runtime_init()` 中明确有强制降级:
  - 若 `sync_mode==ASYNC && spm_xlate_enable==1`
  - 则强制改成 `sync_mode=BLOCKING_DEBUG`
  - 进一步强制:
    - `dma_backend=BLOCKING_FENCE`
    - `gemmini_mode=BLOCKING_FENCE`
- live token1173 sparse 日志也验证了这一点:
  - `init begin ... spm_xlate=1`
  - `init dma-backend begin backend=0`
  - `init gemmini-backend begin mode=0`
  - 即当前 run 实际用的是 blocking DMA + blocking Gemmini
- worker 主循环中:
  - 计算前先调用 `stage_wait_exports_ready()`
  - 在 blocking DMA 路径下，这里会等待 export pipebuf 变空
  - 所以不会带着前一 subbatch 的 export DMA 进入下一 subbatch 计算
- export 侧 `prt_process_c2()` / `prt_process_c6()` 中:
  - 只有 `allow_overlap` 为真才会 submit-ahead
  - `allow_overlap` 依赖 `export_overlap_enabled(rt)`
  - 而 `export_overlap_enabled(rt)` 只在 `dma_backend == POLL_PROGRESS_THREAD` 时为真
  - 当前 backend 已被强制成 `BLOCKING_FENCE`
  - 所以 live 日志中的 `overlap=0` 与源码完全一致
- 当前 live breadcrumb 的 `rr_acquire_after_call` 对应:
  - `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/src/prt_rerocc.c:336`
  - 这是 stage 进入下一段 RR acquire 包装后的更深位置

## 结论

- 对当前这套 `12-pair sbus128 + dummy model + spm_xlate_enable=1` 固定配置:
  - `subbatch=3` 的 DMA 与 `subbatch=4` 的计算不重叠
- 更准确地说:
  - `sb=3` 的计算完成
  - 然后执行 `sb=3` 的 blocking export DMA
  - DMA 退休后，stage 才推进到 `sb=4`
- 这不是纯静态推断，当前 live sparse + live breadcrumb 都支持这个结论
