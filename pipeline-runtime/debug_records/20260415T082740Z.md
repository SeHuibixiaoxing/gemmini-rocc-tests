## 新观察

- 当前 segment 不是多 stage 并发:
  - live sparse 明确显示 `segment=0 begin stages=1`
  - 只创建了一个 worker: `created=1`
  - `worker stage=0 ready ...`
- 当前 run 的 pipeline-runtime 线程模型:
  - 1 个主线程负责 segment 级 watchdog / sink-progress / join
  - 1 个 stage worker 线程负责 stage0 执行
  - 0 个 DMA progress thread，因为当前 backend 是 blocking
- 因此当前 runtime 内部并发线程数是 2，不是按 `tiles=8` 起 8 个 worker
  - `tiles=8` 是 stage 内 manager / tile 并行度，不是 pthread 数
- 当前 run 中会打 guest 日志的线程:
  - 主线程会打 init / worker-create / sink-progress 等日志
  - stage0 worker 会打大多数热路径日志
  - 没有单独 logger 线程
  - 没有 DMA progress thread 在写日志
  - breadcrumb / trigger 也不是单独线程，而是调用它们的当前线程顺手写
- 日志实现主路径并没有全局 logging mutex:
  - progress / deep / checkpoint 多数路径是本线程直接 `write()` 到 FD
  - guest file log 打开方式是 `O_WRONLY|O_CREAT|O_APPEND|O_CLOEXEC`
  - stderr 路径还特别做成 best-effort，避免部分写后继续阻塞
- breadcrumb 路径也没有 pthread mutex:
  - 直接写 mmap 区并用 `__sync_*` 原子原语更新 slot / update_count
- trigger log 有单独 mutex，但它只保护自己的 ring/file 状态:
  - 没看到它反向再去拿 pipebuf / ring 锁
- 但“日志扰动”依然真实存在:
  - 日志写是 inline 的，谁走到这里谁写
  - 少数路径会在拿着 buffer/ring 锁时打印，例如 `prt_process_c7/c8`
  - 所以日志可能把时序拉长，改变下一个观测 frontier

## 分析

### 1. 当前有多少线程并行

- 当前 segment0:
  - `stages=1`
  - `worker-create end stage=0 created=1`
- 所以当前 pipeline-runtime 运行期并发线程数是:
  - 主线程 1
  - worker 线程 1
  - 合计 2
- 若开启 async DMA backend，本来还会再多 1 个 `dma_progress_thread`
  - 但当前 backend 是 blocking，所以没有这个线程

### 2. 当前有多少线程在打日志

- 当前 run 的 guest 文件日志里，真实会打日志的 runtime 线程也是 2 个:
  - 主线程
  - stage0 worker
- 当前没有独立日志线程
- 当前没有 DMA progress thread
- trigger / breadcrumb 只是附着在现有线程上执行

### 3. 会不会是日志死锁导致的卡死且卡点会随日志漂移

- “卡点会随日志漂移”:
  - 是有可能的，而且过去的观测已经支持这一点
  - 更准确说是日志扰动 / 时序敏感，不一定是日志死锁
- “经典意义上的日志死锁”:
  - 目前看 **不像主因**
  - 原因:
    - 普通 progress/deep/checkpoint 日志没有全局 logging mutex
    - breadcrumb 没有 pthread mutex
    - trigger log 虽有 mutex，但没有看到它再去反向拿 pipebuf/ring 锁形成循环
- 但不能说日志完全无害:
  - 写日志是同步 inline 执行
  - 少数路径会拿着 buffer/ring 锁时打印
  - 这可能把持锁时间拉长，造成另一个线程更晚拿到锁
  - 于是 frontier 会漂移，甚至表现成“更早”或“更晚”卡住
- 因此更准确结论是:
  - 当前更像 **日志扰动导致的 timing drift**
  - 不像 **全局 logger mutex 导致的 deterministic deadlock**

### 4. 为什么要把 async 降级为 blocking

- 直接原因在 runtime 初始化里写得很明确:
  - `Page-granular DMA translation is currently retired synchronously`
  - `force blocking debug until token-chained async paging is implemented`
- 这不是保守过度，而是当前实现确实缺一环:
  - 开启 `spm_xlate_enable=1` 后，很多 DMA 不再是“一个物理连续 req 一把提交”
  - 而是变成:
    - 每页/每 chunk 做 host `virt->phys`
    - 做 RR acquire
    - 发 DMA
    - 立刻 wait/fence/retire
    - 再处理下一页
- 现在页粒度 export/fixed-load 路径里能直接看到 `submitwait-begin/end`
  - 也就是每页都是同步 retire
- 如果此时还表面上保留 async mode:
  - 上层会误以为 export / fixed-load 只是“已提交未退休”
  - 但底层 page translation + RR scope + submit/wait 仍是逐页同步退休
  - 这样会把 buffer/full-empty、subbatch_offset、ring fill/use、alias sync、下一 subbatch 推进语义搞乱
- 当前实现只有“DMA token + progress thread”这一层 async
  - 还没有把 `spm_xlate` 页翻译链路也纳入同一套 token-chained retire 语义
  - 所以只能在 `spm_xlate_enable=1` 时强制退回 blocking，先守住正确性

## 结论

- 当前 run 的 pipeline-runtime 并发线程数:
  - 2 个
  - 主线程 1 + stage0 worker 1
- 当前打 guest 日志的 runtime 线程数:
  - 也是 2 个
  - 没有独立 logger thread
- “日志会导致卡点漂移”:
  - 有可能，且很可能已经发生过
- “日志死锁是当前主因”:
  - 目前证据不支持
  - 更像日志扰动放大了本来就时序敏感的问题
- `async -> blocking`:
  - 是为了保证 `spm_xlate_enable=1` 时页粒度 DMA 翻译和 RR/fence 退休语义正确
  - 因为当前实现还没有完成 token-chained async paging
