## 设计思路

### 1. 为什么这轮不去加 guest 日志

因为当前失败发生在：

- Linux 启动之前
- guest 程序执行之前
- `gdbserver` 之前

所以继续在 guest 里加日志，对当前这条早死链路没有判别力。

### 2. 需要直接回答的两个问题

当前 `simplenic` 只知道：

- 它想往 `stream_from_cpu` 推 `915` beats
- 结果 `push()` 返回 `0`

但这不能区分下面几种根因：

1. host stream 本身 occupancy 读错
2. bridge 没有从 host stream 取 token
3. bridge 取了 token，但没送进 target 前的小队列
4. token 已经送到 target 前小队列，但 target 侧没有继续消费
5. target 在回传路径上卡住，导致 lockstep `tFire` 断掉

因此，本轮新增的观测面必须能把这些状态区分开。

### 3. 为什么选择 bridge MMIO 只读寄存器

原因有三点：

1. 改动最小
   不需要改变 `simplenic` 正常 fast path，不需要重写 stream engine。
2. 扰动小
   只增加少量只读寄存器和计数器，不引入新的 guest 行为。
3. host 失败时可直接打印
   `simplenic` 已经有 MMIO read 能力，失败时直接读寄存器即可。

## 本轮修改

### 1. `SimpleNICBridge` 新增低扰动 debug 寄存器

修改文件：

- `/home/ubuntu/chipyard/generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`

新增两类观测：

#### A. 当前状态快照

- `debug_htnt_queue_count`
- `debug_ntht_queue_count`
- `debug_flags`

其中 `debug_flags` 压了当前关键握手位：

- `tFire`
- `hPort.toHost.hValid`
- `hPort.fromHost.hReady`
- `htnt_queue` 的 `enq/deq valid/ready`
- `htnt_queue` 当前 token 的 `data_in_valid/data_out_ready`
- `target.in.valid`
- `target.out.valid`
- `ntht_queue` 的 `enq/deq valid/ready`
- `streamDeq.valid/ready`
- `streamEnq.valid/ready`
- adapter 两端的 `valid/ready`

这让 host 侧在失败当下能直接看到：

- lockstep 条件到底卡在哪一侧
- host stream token 是否已经走到 bridge 内部
- target 往返方向哪个方向不动

#### B. 累计计数器

- `debug_tfire_count`
- `debug_stream_deq_fire_count`
- `debug_stream_enq_fire_count`
- `debug_htnt_enq_fire_count`
- `debug_htnt_deq_fire_count`
- `debug_ntht_enq_fire_count`
- `debug_ntht_deq_fire_count`
- `debug_host_in_valid_token_count`
- `debug_target_out_valid_token_count`

这些计数器的作用是：

- 区分“当前这一拍没动”和“从开始到失败都没动”
- 区分 host->target 路径与 target->host 路径谁先停
- 区分 token 在 stream 边界停住，还是在 bridge 内部小队列停住

### 2. `simplenic` 在失败路径主动打印 bridge 调试寄存器

修改文件：

- `/home/ubuntu/chipyard/generators/firechip/bridgestubs/src/main/cc/bridges/simplenic.cc`
- `/home/ubuntu/chipyard/generators/firechip/bridgestubs/src/main/cc/bridges/simplenic.h`

新增：

- `dump_bridge_debug(...)`

它会在四种失败现场打印：

1. `init_pull_expected_empty`
2. `init_push_capacity`
3. `tick_pull_mismatch`
4. `tick_push_mismatch`

打印内容包括：

- 当前上下文名
- 请求/实际字节数
- `currentround`
- `LINKLATENCY`
- `done`
- 各种 fire 计数器
- 两个小队列当前 occupancy
- `debug_flags` 原始值和逐位解码

这意味着下一轮如果还死在：

- `ERR MISMATCH! on writing tokens in`

我们至少能直接回答：

- `tFire` 是否已经发生过
- `streamDeq` 是否真的从 host stream 拉过 big token
- `htnt_queue` 是否真正把 token 送到 target 前
- `ntht_queue` / `streamEnq` 是否有任何回传活动
