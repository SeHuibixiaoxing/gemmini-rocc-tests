## 新观察 / 新卡点

### 1. 当前 run **并没有**卡在 boot ROM `wfi`

虽然 `/home/ubuntu/sim_slot_0/metasim_stderr.out` 尾部只看到：

- hart1: `pc=0x10034 inst=10500073 wfi`
- hart0: `pc=0x10034 inst=10500073 wfi`

但 live gdb 直接读取 Verilator 状态得到：

- `bootAddrReg = 0x80000000`
- `clint.ipi_0 = 0`
- `clint.ipi_1 = 0`
- hart0 `reg_wfi = 0`
- hart1 `reg_wfi = 0`
- hart0 `reg_mie = 0x8`, `mstatus.mie = 0`
- hart1 `reg_mie = 0x8`, `mstatus.mie = 0`

结论：当前 cores 不是“仍睡死在 boot ROM 的 WFI”。

### 2. 当前两核 live PC 已在用户程序里，且位置和之前 sel0 run 一致

gdb live snapshot 直接读取 pipeline PC：

- hart0:
  - `wb_reg_pc = 0x80002364`（后续再采样落到 `0x8000235c`）
  - `mem_reg_pc = 0x80002354`
  - `ex_reg_pc = 0x80002354`
  - `ibuf_io_pc = 0x80002360`
- hart1:
  - `wb_reg_pc = 0x80002032`
  - `mem_reg_pc = 0x80002034`
  - `ex_reg_pc = 0x80002030`
  - `ibuf_io_pc = 0x80002032`

结合反汇编：

- `0x80002354/58/5c/60/64` 位于 `thread_entry` 的 `fill_pattern(stage0_src, ...)` 循环
- `0x80002030/32/34` 位于 `barrier_wait.constprop.0` 的等待循环

这与之前 `selector=0 + tsi_bootdiag` 那轮观察到的用户程序位置一致，说明当前 run 实际仍在用户程序 prefill 阶段。

### 3. `TRACEFILE-C0/C1` 为 0 的原因是：**还没有到 trigger start marker**

当前 instruction trigger 配置：

- start marker: `0x8000241c`，指令字 `0x00008013`
- end marker: `0x80002748`，指令字 `0x00010013`

而当前 hart0 live PC 仍在：

- `0x80002354 ~ 0x80002364`

即：仍在 marker 之前的 512 KiB `stage0_src` 填充循环中。

因此：

- `TRACEFILE-C0/C1 == 0`
- `selector=3` 下没有新的 trace 输出

这是**符合配置预期**的，不是新的 boot/TSI/CLINT 死锁证据。

### 4. 这轮“看起来又回到 boot ROM”的根因是：观察手段失真，而不是真卡回 boot ROM

当前 `metasim_stderr.out` 里的 `C0:/C1:` 仍然是 Rocket synth printf 的一小段早期输出；
在 `selector=3` 且 trigger 尚未命中前，不能把这个旧尾部误解为“程序当前 PC 仍在 0x10034”。

真正有判别力的是 live gdb 读出的 Verilator 状态，而不是单看 `metasim_stderr.out` 尾巴。

## 分析

- 之前关于“`selector=3` 导致系统重新掉回 boot ROM `wfi`”的判断，在当前 live snapshot 下**不成立**。
- `reset-pulse-length0=200` 没有改变问题本质，因为本质并不是 reset 窗口导致的 boot 唤醒失败。
- 当前 run 的真实状态是：
  - hart0 在 `fill_pattern(stage0_src, ...)` 的大循环里慢慢推进
  - hart1 在 barrier 等 hart0
  - TracerV trigger start 还没被执行，所以 trace 文件仍为 0
- 因此，“为什么之前到了，这次没到”的直接答案是：
  - **它其实已经到了用户程序，只是当前可见输出没有再告诉我们这一点**。
  - 上一轮 `selector=0` 因为全程 trace / synth 输出更多，更容易看到 `0x8000...`；
    这一轮 `selector=3` 直到命中 marker 前都更“安静”，所以造成了误判。
