## Root cause

The first stream-latch fix introduced an internal register in
`StreamWidthAdapter`:

```scala
io.wide.in.ready := !wide_valid
when(io.wide.in.fire()) {
  wide_data  := io.wide.in.bits.asTypeOf(Vec(beats, UInt(narrowW.W)))
  wide_valid := true.B
  wide_beats := 0.U
}
```

In the target-to-host CPU-managed stream path,
`outgoingQueueIO.deq.ready` was connected directly to
`ser_des.io.wide.in.ready`.

That means the adapter could dequeue one 512-bit token from the stream FIFO
before the host CPU had issued an AXI read. The host-side stream driver decides
whether to read by polling the FIFO `count` MMIO. If the only available token is
hidden inside `wide_data`, the FIFO count becomes zero, so the driver does not
issue the read that would drain the hidden token. This creates a deterministic
deadlock:

```text
target enqueues token -> adapter prefetches token -> FIFO count becomes 0
host driver polls count == 0 -> no AXI read -> adapter never drains token
```

This exactly matches the run: switch/driver were alive, but no target progress
was visible after simulation start.

## Fix

Changed `CPUManagedStreamEngine.elaborateToHostCPUStream` so the FIFO can only
dequeue into the latch while a matching AXI read request is active:

```scala
val readRequestActive = grant && axi4.ar.valid
ser_des.io.wide.in.valid  := outgoingQueueIO.deq.valid && readRequestActive
outgoingQueueIO.deq.ready := ser_des.io.wide.in.ready && readRequestActive
```

This preserves the latch for data stability but keeps FIFO count semantics
visible to the host stream driver.
