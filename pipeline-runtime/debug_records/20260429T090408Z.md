## 动态事实

该 AGFI 已经越过早期 boot 前 blocker，进入 Linux 和用户态：

```text
Registered IceNet NIC 00:12:6d:00:00:02
running /etc/init.d/S40network
running /etc/init.d/S99run
[gdbserver] phase=listening net_dev=eth0 guest_ipv4=172.16.0.2 endpoint=172.16.0.2:2345 pid=112
```

但是 host 到 guest 网络不通：

- host `tap0=172.16.0.1/16` 后，`ping -I tap0 172.16.0.2`
  100% loss。
- `tap0` TX 增长，RX 保持 `0`。
- neighbor `172.16.0.2` 进入 `FAILED`。

关键 GDB / UART 证据：

- C++ / switch 已收到 host->target 包。
- GDB 在 `simplenic.cc:1138 if this->pending_peer_valid_flits > 0`
  命中。
- `pending_peer_buf + 0x40` 处有有效 bigtoken header：
  `0x2490000000000000`，后续包含 DHCP/网络包内容。
- `simplenic_t::push(... pending_peer_buf + 64, 64, 0)` 返回 `64`。
- UART 中有：

```text
SIMPLENIC DEBUG [after_single_payload_bigtoken_push] requested_bytes=64 actual_bytes=64 ...
pending_peer_snapshot=1 pending_peer_valid_flits=6
```

RTL/OCL 侧仍没看到 host payload：

- `bigtoken_accept_count` / `pcie_in` 增长，说明 from-host
  CPU-managed stream 有被消费。
- `bigtoken_payload_emit_count=0`。
- `from_host_payload_capture_count64=0`。
- `from_host_stage current/pending valid=0`。
- `htnt_queue` 中长期是 empty token，`from_empty_drop` 大量增长。
- `target_in_bits` 仍为 0，guest NIC 没收到 host payload。

因此本轮已经排除：

1. 不是 guest 没 boot。
2. 不是 gdbserver 没 listen。
3. 不是 host/switch 没收到 host->target 包。
4. 不是 C++ `push()` 完全失败。

## 静态钉死的新问题

当前最硬的静态问题是 F2 shell PCIS 数据宽度与生成出来的
`F1Shim.io_pcis` 宽度不一致。

F2 顶层仍使用 512-bit PCIS 信号：

```text
sims/firesim/platforms/f2/aws-fpga-firesim-f2/hdk/cl/developer_designs/cl_firesim/design/cl_firesim.sv
  logic [511:0] sh_cl_dma_pcis_wdata_FIRESIM;
  logic [63:0]  sh_cl_dma_pcis_wstrb_FIRESIM;
```

但当前 `F2Config` 中：

```text
sims/firesim/sim/midas/src/main/scala/midas/Config.scala
  CPUManagedAXI4Key.dataBits = 64
```

最新生成 Verilog 证明 `F1Shim` 的 PCIS 写数据接口已经是 64-bit：

```text
sims/firesim/deploy/results-build/2026-04-29--05-23-31-firesim_rocket_singlecore_nic_notrace_30mhz/.../design/FireSim-generated.sv
  input [63:0] io_pcis_w_bits_data
  input [7:0]  io_pcis_w_bits_strb
```

而 F2 顶层仍直接连接：

```text
.io_pcis_w_bits_data(sh_cl_dma_pcis_wdata_FIRESIM)
.io_pcis_w_bits_strb(sh_cl_dma_pcis_wstrb_FIRESIM)
```

这会在 Verilog 端把 512-bit shell beat 截成低 64-bit，把 64-bit strobe
截成低 8-bit。对于 `simif_f2.cc` 通过 `fpga_pci_poke64()` 发出的
BAR4 写，如果 shell 把 64-bit payload 放在 512-bit beat 的非 0 lane，
FireSim 侧的 64-bit `CPUManagedStreamEngine` 就只能看到空 beat 或错误
beat。

这与现场完全吻合：

- host C++ 确认 `push()` 成功；
- `pcie_in` / `bigtoken_accept_count` 增长；
- 但 `BigTokenToNICTokenAdapter` 没有识别 payload header，
  `payload_emit_count=0`；
- target-facing NIC input 仍只看到 empty token。

## 次要但需要修的风险

`CPUManagedStreamEngine` from-host 写路径仍假设 AXI AW/W/B-ready/narrow-ready
同周期成立：

```scala
val writeHelper = DecoupledHelper(
  axi4.aw.valid,
  axi4.w.valid,
  axi4.b.ready,
  ser_des.io.narrow.in.ready,
)
```

这不符合标准 AXI 写通道 AW/W 独立握手语义。当前现场已经能看到 accept
计数增长，所以它不是唯一根因；但修完 F2 512->64 桥后仍应该把这里改成
标准写 FSM：独立 latch AW、接收 W beats、最后发 B。

## 下一步建议

优先修 F2 PCIS 512-bit shell 到 64-bit `CPUManagedAXI4` 的桥接，不能继续
直接连线。可选路线：

1. 在 F2 `cl_firesim.sv` 增加 PCIS 512->64 downsizer/lane selector，
   按 `awaddr` / `wstrb` 选择有效 64-bit lane，再接入 64-bit `F1Shim`。
2. 或回退 `CPUManagedAXI4Key.dataBits=512`，并重新处理 F2 host 端
   BAR4 写入粒度；这可能重新引入之前 32/64-bit partial-strobe 问题，
   不优先。

下一颗 bitstream 前建议增加更直接的可综合 debug regs：

- F2 顶层 PCIS snapshot：
  `awaddr/awsize/awlen/wstrb/wdata[7:0 lanes]/selected_lane/selected_data`。
- `CPUManagedStreamEngine` snapshot：
  `aw_fire/w_fire/b_fire/last_awaddr/last_wdata/last_wstrb/pack_count/pack_snapshot`。
- `BigTokenToNICTokenAdapter` snapshot：
  `last_nonzero_latched_word[0..7]`、
  `last_payload_latched_word[0..7]`、
  `payload_header_seen_count`。

## Baremetal / Local Metasim 分流

本轮提出的新分流思路：

- 不需要为 baremetal 测试启动 Linux。
- FireSim-managed local metasim 可以运行 baremetal workload；已有
  `pairmanager_baremetal_rr_release_probe` 文档和 workload 证明这条路径
  已在本项目中被使用。
- 但要复现当前 NIC 问题，需要注意：当前硬错误位于 F2 shell
  512-bit PCIS 到 generated `F1Shim` 64-bit 之间的顶层连接。普通
  local metasim 不经过 AWS F2 shell，因此未必能复现这处 F2-specific
  截断问题。
- local metasim 仍然有价值：
  1. 验证 `CPUManagedStreamEngine` 64-bit pack/unpack 本身是否正确。
  2. 验证 `BigTokenToNICTokenAdapter` 是否能把 64-bit lane 拼成 512-bit
     bigtoken 并识别 payload header。
  3. 如果 metasim 通过而 F2 失败，就进一步支持“F2 shell 宽度桥接”
     是当前真实根因。

因此下一步测试方案是：

1. 先找或构建一个最小 baremetal/metasim smoke，不启动 Linux。
2. 优先复用 FireSim-managed metasim flow，而不是裸跑 `sims/verilator`。
3. 若需要最小 NIC 复现，构建一个不依赖 Linux 网络栈的 target 程序；
   但如果 target 侧没有 IceNet baremetal 驱动，metasim 更适合先验证
   CPU-managed stream / bigtoken 适配器，而不是完整 Ethernet 协议。
