## 静态展开

生成物：

- `/home/ubuntu/chipyard/sims/firesim/sim/generated-src/f2/f2-firesim-FireSim-FireSimRocketNICNoTraceConfig-BaseF2Config/FireSim-generated.sv`

关键链路：

```text
targetCycleFinishing
  waits for ep_3_nic_out_*_source_ready & source_valid
  waits for ep_3_nic_in_*_sink_valid

ep_3_nic_out_*_source_ready
  = SimpleNICBridgeModule_0_hPort_toHost_hReady & sibling_source_valid...

SimpleNICBridgeModule_0_hPort_fromHost_hReady
  = ep_3_nic_*_sink_ready AND
  = targetCycleFinishing & ~fired ...
```

本轮发现上一版 SimpleNIC lockstep patch 仍残留一个 ready 方向组合依赖：

```scala
hPort.toHost.hReady := hPort.fromHost.hReady && localQueuesReady
```

由于 `hPort.fromHost.hReady` 是 `targetCycleFinishing` 的函数，而 `targetCycleFinishing` 又等待 NIC output source ready，形成：

```text
targetCycleFinishing
 -> hPort.fromHost.hReady
 -> hPort.toHost.hReady
 -> ep_3_nic_out_*_source_ready
 -> targetCycleFinishing
```

这比 timing 违例更直接，能解释为什么 NIC 本地队列已经 ready，但全局 target-cycle ready 长期为 0。

## 修改策略

修复方向：

- `hPort.toHost.hReady` 只由 NIC 本地队列条件驱动：
  - `ntht_queue.io.enq.ready && htnt_queue.io.deq.valid`
- 真正移动 token 仍只在 `tFire = hPort.toHost.hValid && hPort.fromHost.hReady && localQueuesReady` 时发生。

新增观测方向：

- TargetCycleDebugWidget 增加派生 blocker masks：
  - `hport_*_blocked`
  - `wire_input_missing_valid`
  - `wire_input_backpressured`
  - `wire_output_blocked`
  - `rv_input_*`
  - `rv_output_*`
- 每类 blocker 增加：
  - live / first / last mask
  - 累计 cycles
  - 当前 streak / max streak
  - per-endpoint bit count
- SimpleNIC 增加：
  - debug cycle
  - first/last/current blocked reason
  - `target_cycle/local_queues/pcie_in/pcie_out/to_host_ready` streak/max
  - last tFire / PCIE in / PCIE out cycle
