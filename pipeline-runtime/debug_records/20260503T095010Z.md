# single-core NIC cycle-0 deadlock 的静态根因钉证

日期：2026-05-03T09:50:10Z

## 背景

上一轮基于当前 single-core Rocket + NIC bitstream：

```text
agfi-0a8a558628a493d31
afi-00b92eebc6f4cacef
build: sims/firesim/deploy/results-build/2026-05-03--05-15-05-firesim_rocket_singlecore_nic_notrace_30mhz/
```

运行 `gdbserver` smoke 时，target 没有进入 Linux，FireSim driver 在约 604s
wallclock 后报：

```text

```

已保存现场：

```text
debug_records/artifacts/20260503T092001Z_agfi0a8_targetcycle0_deadlock/
debug_records/artifacts/20260503T093243Z_agfi0a8_targetcycle_debug_deadlock/
```

## 对照基线

更早通过的 single-core NIC AGFI：

```text
agfi-032d10150efc1d4ec
build: sims/firesim/deploy/results-build/2026-05-02--16-49-10-firesim_rocket_singlecore_nic_notrace_30mhz/
```

该 AGFI 已经能：

- 进入 `[gdbserver] phase=listening`；
- 接受 gdb 连接并退出 workload。

它后续暴露的是更深的 remote GDB TCP/RSP 数据问题，而不是 cycle 0 无法推进。

## 钉死的静态差异

对比 2026-05-02 通过版 generated RTL 与 2026-05-03 失败版 generated RTL 后，
确认 05-03 失败版丢掉了 NIC from-host sideband channel 的 grouped ready/valid
约束。

05-02 通过版在 `SimpleNICBridgeModule` 中实际生成：

```text
configChannelReady     = hPort_macAddr_ready & hPort_rlimit_ready & hPort_pauser_ready
fromHostAllReady       = hPort_nicIn_ready & configChannelReady
configChannelValid     = hPort_macAddr_valid & hPort_rlimit_valid & hPort_pauser_valid
fromHostChannelValid   = hPort_nicIn_valid & configChannelValid
targetCycleReady       = toHostReadyDrive & fromHostAllReady
targetBlockedFromHostChannels = ~fromHostAllReady
```

05-03 cycle-0 失败版变成：

```text
fromHostChannelReady   = nicInChannelReady
fromHostChannelValid   = nicInChannelValid
targetCycleReady       = toHostReadyDrive && nicInChannelReady
targetBlockedFromHostChannels = fromHostTokenAvailable && !hPort.nicIn.ready
```

也就是说，target-cycle close 只看 `nicIn.ready`，不再看
`macAddr/rlimit/pauser.ready`。但 FPGATop 侧仍然存在这些 channelized sideband
ready 信号，它们不是可以随意忽略的普通常量线。

这一点和 targetcycle debug 现场独立吻合：早期 live dump 中看到 NIC from-host
侧 `nicIn/macAddr/rlimit/pauser` 一组 channel 进入 backpressure，target cycle 0
无法闭合。注意：targetcycle 最后一帧全 0 dump 不可信；本轮结论不依赖该全 0
尾帧，而是依赖 generated RTL A/B 差异和早期 live channel 现象。

## 本轮修复

修改：

```text
generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala
```

恢复 sideband grouped readiness：

```text
configChannelReady   = macAddr.ready && rlimit.ready && pauser.ready
fromHostChannelReady = nicIn.ready && configChannelReady
configChannelValid   = macAddr.valid && rlimit.valid && pauser.valid
fromHostChannelValid = nicIn.valid && configChannelValid
targetCycleReady     = toHostReadyDrive && fromHostChannelReady
targetBlockedFromHostChannels = !fromHostChannelReady
```

同时让 `fromHostEmptyBlocked` 和相关 debug 阻塞位使用 grouped
`fromHostChannelReady`，避免再次把 sideband ready 从观察面漏掉。

该修复不会回退到之前的 `fromHostValidDrive` 互等错误：当前
`fromHostValidDrive` 仍为 `true.B`，sideband/config valid 继续独立稳定驱动；
本轮只恢复 target-cycle close 和 debug/blocker 统计对全部 from-host channel
ready 的要求。

## 结论

05-03 `agfi-0a8a...` 的 cycle-0 deadlock 不是 remote gdbserver 软件层问题；
在进入 Linux 前 target-cycle close 已经被当前 NIC generated RTL 卡住。

这轮已经把当前源码和本地生成物恢复到“from-host sideband 参与 target-cycle close”
的形态。下一步必须基于当前生成物重新构建 single-core NIC bitstream。进入远端
Vivado 后，需要再次检查远端 build host 上的 `FireSim-generated.sv`，确认不是旧
generated RTL 被打进 AGFI。
