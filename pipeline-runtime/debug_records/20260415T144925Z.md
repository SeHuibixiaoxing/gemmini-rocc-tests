## Static Diagnosis
- The run itself did not prove a new semantic blocker.
- The more important finding is that `v23` was not actually a low-perturbation baseline.
- In `prt_dma.c`:
  - `dma_should_sparse_export_page_probe()` falls back to built-in export sparse logging when `PIPELINE_RUNTIME_DMA_EXPORT_PAGE_START/END` are not configured.
  - That built-in fallback enables page logs for:
    - `page >= 48`
    - `page == 0`
    - last page
    - `page % 8 == 0`
- In `pairdummy_sbus128_fixed_env.sh`, `v23` changed:
  - `PIPELINE_RUNTIME_DMA_EXPORT_PAGE_START=""`
  - `PIPELINE_RUNTIME_DMA_EXPORT_PAGE_END=""`
- Therefore `v23` unintentionally re-enabled the default export sparse page logs for `stage=0 / tensor=2`, even though `PIPELINE_RUNTIME_DMA_EXPORT_PROBE_ENABLE=0`.
- This explains why the guest sparse log contained many `dma-export-host page=48..63` lines and why the supposed control rerun regressed relative to earlier, quieter rounds.

## Conclusion
- The authoritative result of this round is not a new functional blocker.
- The authoritative result is a configuration-semantics bug in the observability baseline:
  empty `DMA_EXPORT_PAGE_START/END` re-opened hot-path export sparse logging.
- The next step must be:
  1. restore a true low-perturbation baseline by pinning export sparse page selection to a non-matching sentinel
  2. rebuild/refresh the image
  3. rerun control from that corrected baseline before making any new blocker claim
