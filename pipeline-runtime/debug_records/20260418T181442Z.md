## 新观察 / 新卡点

### 1. 当前已经不能再把问题归因到 boot ROM / TracerV / MSIP host path

live gdb 读取到：

- `bootAddrReg = 0x80000000`
- `clint.ipi_0 = 0`
- `clint.ipi_1 = 0`
- 两个 hart 的 `mstatus.MIE = 1`
- 两个 hart 的 `mie = 0x8`

这说明：

- bootaddr 寄存器没有异常值
- hart 侧软件中断使能是开的
- 采样时看不到卡在“CLINT 的 MSIP 一直没写到”这类现象

更关键的是，
`TRACEFILE-C0` 和 `TRACEFILE-C1`
都明确显示两颗 hart 已从 `0x100xx`
进入 `0x80000000` 段用户程序，
所以“还在 boot ROM wfi”这个结论不再成立。

### 2. 两颗 hart 当前都停在非常具体的用户程序循环里

`TRACEFILE-C0` 尾部稳定重复：

- `0x8000232a`
- `0x8000232e`
- `0x80002330`
- `0x80002332`
- `0x80002336`

反汇编对应：

- `0x8000232a: mulw a5,a5,a2`
- `0x8000232e: addi a4,a4,1`
- `0x80002330: addw a5,a5,a3`
- `0x80002332: sb a5,-1(a4)`
- `0x80002336: bne a1,a4,0x8000232a`

这正是
`fill_pattern(stage0_src, sizeof(stage0_src), 0x13572468u);`
的逐字节填充循环。

`TRACEFILE-C1` 尾部稳定重复：

- `0x80002024`
- `0x80002026`
- `0x80002028`

反汇编对应：

- `0x80002024: nop`
- `0x80002026: lw a5,0(a3)`
- `0x80002028: beq a4,a5,0x80002024`

这正是
`barrier_wait()`
里等待 `barrier_epoch` 变化的自旋循环。

### 3. 所谓“卡点移动”本质上是软件把观测点放在了一个超大静默初始化区之后

源码里：

- `cid == 0` 会先执行：
  - `fill_pattern(stage0_src, 512KB, ...)`
  - `fill_pattern(stage1_src, 64KB, ...)`
- 然后才执行：
  - `set_stage_progress(cid, 10U);`
  - `barrier_wait(logical_cores);`

而 `cid == 1` 不做 `fill_pattern()`，
会很快进入 `barrier_wait()`。

因此运行形态天然就是：

- hart1 很早就卡在 barrier 自旋
- hart0 长时间在 `fill_pattern()` 里无声跑
- 任何放在 `stage_progress=10` 之后的卡点，
  在这段预热没结束前都不会触发

这就是之前“只要改日志/改卡点，卡点就不断移动”的根因：
不是硬件随机碰运气，
而是观测窗口根本设在一大片无显式 breadcrumb 的长前置初始化之后。

### 4. 当前现场不是“完全死锁”，而是在缓慢前进

`TRACEFILE-C0/C1` 文件大小和尾部 cycle 在 3 秒窗口内持续增长：

- `TRACEFILE-C0`：
  `1818871 -> 1827063`
- `TRACEFILE-C1`：
  `3510474 -> 3530954`
- cycle 也从约 `11,095xx`
  增长到约 `11,151xx`

所以当前 metasim 现场不是完全不动，
而是：

- hart0 在继续执行 `fill_pattern(stage0_src)`
- hart1 在继续 barrier 自旋等待 hart0

### 5. 这个 repro 的前置内存初始化量非常大

源码常量：

- `REROCC_EXPORT_STAGE0_BYTES = 512 * 1024`
- `REROCC_EXPORT_STAGE1_BYTES = 64 * 1024`

ELF `.bss` 总大小：

- `1703968` bytes

本轮 live gdb 一次采样中，
hart0 的 `addi a4, a4, 1` 写回值约为：

- `0x80124e89`

对比 `stage0_src` 起始地址：

- `0x80123100`

说明当时只完成了约：

- `7561 / 524288 = 1.44%`

也就是说，
当前观测到的“反复在同一小环”
并不是逻辑死循环，
而是一个本来就非常长的逐字节填充过程。

## 分析

- `TracerV` 路径已经在 stage A 和当前 live `TRACEFILE` 中双重证明可用；
  继续在 trigger 窗口上兜圈子没有价值。
- boot 唤醒链路也不是当前主要矛盾；
  两颗 hart 都已进入用户程序。
- 这轮真正暴露出来的问题是：
  `rerocc_lc_export_dma_bertmini_segment3_repro.c`
  在任何 stage breadcrumb 之前，
  就让 hart0 做了 `576KB` 的逐字节 seed 初始化，
  导致：
  - hart1 先进入 barrier
  - 外部日志只能看到“卡在 barrier / 卡点没到”
  - 若仅靠移动日志/卡点，会持续得到漂移现象

因此，本问题当前最合理的定性不是：

- “卡在 boot / MSIP / TracerV”

而是：

- “repro 的前置软件初始化区过大且没有有效观测点，
   导致实际卡点长期被隐藏在初始化之前”

## 下一步

1. 不改硬件、先改 repro 结构，消掉这个大静默区。
   最小方案优先级：
   - 方案 A：
     把 `set_stage_progress(cid, 10U)` 前移到 `fill_pattern()` 之前，
     再增加一个专门表示“fill_pattern 完成”的固定 stage 值。
   - 方案 B：
     给 metasim 专用构建覆盖
     `REROCC_EXPORT_STAGE0_BYTES` / `REROCC_EXPORT_STAGE1_BYTES`
     为更小值，
     先把问题推进到真正的 DMA/export 路径。
   - 方案 C：
     保持数组大小不变，但把 `fill_pattern()` 改成按 `uint64_t`
     或更宽粒度批量生成/写入，缩短前置时间。

2. 下一轮真正重跑前，
   应先把上述最小改动方案汇报给用户，
   得到同意后再执行新的
   `infrasetup/runworkload`。

3. 若用户只想先验证“后续 stage 是否能到”，
   最快路径是方案 B；
   若用户想保留原始数据规模但提高可观测性，
   优先方案 A。
