## New Observations

### 1. 现有“live `TRACEFILE-C* == 0`”证据本身不够强，不能直接推出 trigger 没命中

- `tracerv_t::tick()` 当前实现是：
  - `process_tokens(this->stream_depth, this->stream_depth);`
- 当前 pairdummy target 的 `stream_depth` 来自生成常量：
  - `6144`
- `STREAM_WIDTH_BYTES = 64`
- 这意味着 host driver 只有在单个 TracerV stream 至少累积到：
  - `6144 * 64 = 393216 bytes`
  之后，才会真正把 token 从 stream 拉到 host 内存并写文件。
- 在这之前，即使 target 端已经开始出 trace token：
  - `TRACEFILE-C*` 仍可能保持 `0`
  - `/proc/<pid>/fdinfo/<fd>` 的 `pos` 也仍可能保持 `0`

### 2. `TRACEFILE-C*` 还受 `FILE*` 用户态缓冲影响，`fdinfo` 不是“零输出”的充分证据

- `tracerv.cc` 里 trace 文件是：
  - `fopen(..., "w")`
  - `fprintf/fputs/fwrite`
- 没有在 `tick()` 内部 `fflush`
- 因此即使 host 已经从 stream 拉到 token，只要 stdio 缓冲未刷出：
  - 内核文件偏移和文件大小仍可短时间保持 `0`

### 3. 这几轮 `tracerv` / `tracerv-inst` run 都没有自然收口，manager 在监控阶段异常退出

  3. host 已拉流，但 stdio 尚未 flush
  4. manager 先异常退出，模拟器未正常 `finish()`，结果未回传

### 5. Rocket 指令值链路静态上仍然是自洽的

- 对于我们插入的 32-bit marker：
  - `0x00008013`
  - `0x00010013`
  静态上仍应以相同编码出现在 `trace.insn`。
- 因此“编码被 Rocket trace port 改写”目前没有静态证据支持。

## Analysis

- 当前 repeated blocker 漂移里，至少混入了两类“假结论”来源：
  1. probe / observability 改变 frontier
  2. live `TRACEFILE` 观察面本身并不 authoritative
- 对 `TracerV` 当前最稳妥的说法应改成：
  - guest 已大概率执行到 marker；
  - host 启动参数也已对齐；
  - 但现有 live 文件证据不足以证明 trigger compare 一定失败。
- 如果继续维持当前 `minimum_batch = 6144`：
  - 以后仍会反复落入“远程看起来没 trace，但其实可能只是没被 host 拉出来”的误判。
- 现在 `trace-min-batch=0` 已经上机，因此后续若满足下面两个条件：
  1. guest 已进入 wrapper / runner / runtime
  2. `TRACEFILE` 仍然严格为 `0`
  才能更有力地继续怀疑 selector `3` compare / arm path。
