## 新观察

### 1. `page28` 不是末页，下一步理论上确实应该进入 `page29`

live sparse 里同一条 export target 直接给出：

- `target=address2`
- `bytes=65536`
- `pages=64`

因此当前命中的 `page=28`
不是末页；
`page28 after_accounting`
之后，正常控制流确实应该继续进入 `page29`，
而不是自然出 loop。

### 2. 当前源码里的 export `v2p` probes 已经存在

当前 `src/prt_dma.c` direct export path 已经有：

1. `dma_trigger_export_host("v2p-b", ...)`
2. `dma_breadcrumb_export_loop_phase(... DMA_PAGE_BEFORE_V2P ...)`
3. `prt_host_virt_to_phys_debug_scope_push("dma-export-direct-dst")`
4. `prt_host_virt_to_phys(...)`
5. `prt_host_virt_to_phys_debug_scope_pop()`
6. `dma_trigger_export_host("v2p-e", ...)`
7. `dma_breadcrumb_export_loop_phase(... DMA_PAGE_AFTER_V2P ...)`

`src/prt_page_table.c`
里也已经支持：

- export/fixed-load 分家的 `host-v2p` trigger family
- `iv2p-b / iv2p-pb / iv2p-pe / iv2p-ok`

### 3. 但 `20260420-114608` 那轮 live run 早于这批 probes

关键时间关系是：

  `pairdummy-sbus128-runworkload-20260420-114608`

### 4. `page28 -> page29` 之间剩余走廊很窄，而且当前最强嫌疑顺序不变

对 fresh binary 而言，
`after_accounting(page28)` 到 `before_v2p(page29)` 之间剩下的主要是：

- 下一轮迭代的整数地址/长度计算
- `dma_trigger_export_host("pset", ...)`
- `dma_chunk_needs_bounce(...)`

这轮旧 capture 同时还显示：

- `guest_trigger=0`
- 默认 export chunk marker stride 是 `32`
  而 page29 既不是 `0` 也不是 `32` 的倍数

因此：

- trigger/marker I/O
  继续只能算低优先级嫌疑
- fresh rerun 里最该先验证的，
  仍然是 export `v2p` 本身
