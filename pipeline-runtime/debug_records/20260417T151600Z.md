## 本轮结论

1. 这轮没有出现“卡点移动”；freeze 仍然收敛在同一条 `stage=0 / subbatch=1 / tensor=2 export DMA` 热路径内。
2. sparse log 报出的 `page0 first-chunk-submitwait-end` 不是最终真实边界；breadcrumb 证明真实执行已经继续深入到后续 page。
3. 当前 `runner-proc delayed probe` 方案失败的真正原因不是 probe 太晚，而是：
   - 它依赖 guest `sleep`
   - 而 guest 时间在 freeze 后停在约 `00:00:04Z`
   - 所以这些 probe 永远不会醒
4. 因而继续沿用 “guest shell delayed probe” 这条调试思路，只会继续错过 freeze 当刻现场。
5. TracerV 仍未提供任何可用 host trace evidence。

## 对下一步的约束性建议

1. 下一轮不要再沿用 guest `sleep` 型 probe。
2. 下一轮应优先选择 **不依赖 guest 时间推进** 的证据机制，例如：
   - 利用现有 breadcrumb/trigger-gated 短日志，把 page 窗口继续收窄；
   - 或在 runtime C 热路径内加 progress-coupled 的一次性 stuck snapshot，而不是 shell 后台 sleep。
3. 在当前证据下，最合理的继续方向不是再改 wrapper/runner shell，而是直接读：
   - `prt_dma.c`
   - `dma_submit_wait_annotated_scoped()`
   - 以及 breadcrumb 所对应的 DMA submit/wait/cleanup phase
   来决定最小扰动的下一针打在哪里。
4. 按用户要求，在得到明确同意前，不再进行新的 `launchrunfarm / infrasetup / runworkload`。
