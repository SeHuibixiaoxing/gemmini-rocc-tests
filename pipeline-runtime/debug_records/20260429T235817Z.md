## 静态排查结果

### IceNet checksum offload 链路

相关代码：

- `software/firemarshal/boards/firechip/drivers/icenet-driver/icenet.c`
  - 第 26 行定义 `CONFIG_ICENET_CHECKSUM`
  - `icenet_probe()` 把 `NETIF_F_SG | NETIF_F_HW_CSUM | NETIF_F_RXCSUM` 写入 `ndev->hw_features`
  - `icenet_open()` 写 `ICENET_CSUM_ENABLE=1`
  - `post_send()` 在 `skb->ip_summed == CHECKSUM_PARTIAL` 时写 `ICENET_TXCSUM_REQ`
- `generators/icenet/src/main/scala/Checksum.scala`
  - `ChecksumRewrite` 会按 `req.offset` 把 16-bit checksum 回写进 outgoing stream
- `generators/icenet/src/main/scala/NIC.scala`
  - `IceNicSendPath` 在 `csumEnable` 为真时，让发送数据走 `ChecksumRewrite`

重要反证：

- Linux ICMP reply 源码 `software/firemarshal/boards/default/linux/net/ipv4/icmp.c` 中，`icmp_push_reply()` 在算完 ICMP checksum 后执行：
  - `icmph->checksum = csum_fold(csum);`
  - `skb->ip_summed = CHECKSUM_NONE;`
- 也就是说，对普通 ICMP echo reply，正常驱动路径应当写 `ICENET_TXCSUM_REQ=0`，不应触发 TX checksum rewrite。

因此，checksum offload 仍然是现象上最像的链路，但还不能直接写成根因。要让它成为根因，必须满足下面至少一条：

- `post_send()` 实际仍看到了 `CHECKSUM_PARTIAL` 的 ICMP skb；
- `ICENET_TXCSUM_REQ=0` 写入没有按预期进入硬件队列；
- checksum request 队列与 send request 队列发生错位，某个非 ICMP 包的 rewrite request 被套到了 ICMP reply 上；
- 或者 `ChecksumRewrite` 在 `check=false` 情况仍错误改写数据。

### SimpleNIC / switch token 链路

相关代码：

- `generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`
  - `NICTokenToBigTokenAdapter` 把 7 个 64-bit NIC flit 打成 1 个 512-bit big token
  - `BIGToken` 布局与 switch 侧 `flit.h` 当前一致：低 64 bit 为 `pad+rvls`，后 7 个 64-bit word 为 data
- `sims/firesim/target-design/switch/flit.h`
  - `get_flit()` 从 `base * 8 + offset + 1` 读取 data
  - valid/last bit 使用 `43 + token*3` 与 `45 + token*3`
- `sims/firesim/target-design/switch/baseport.h`
  - 每轮只清空每个 bigtoken 的低 64-bit header；data 残留依赖 valid bit 为 0 时不被消费

当前没有直接证据证明 BIGToken 布局错了；链路能跑到 `gdbserver` 连接也说明基本 valid/last/data 对齐不是全局性错误。但 payload 固定位点损坏仍可能来自 target->host stream 搬运、partial pull、或旧数据残留与 valid bit 的组合错误，需要下一步用更细的 token/flit 捕捉证据确认。

## 下一步判别实验

先做不需要新比特流的软件实验：

1. 在 IceNet driver 中临时关闭 checksum offload：
   - 不定义 `CONFIG_ICENET_CHECKSUM`
   - 不向 Linux 宣告 `NETIF_F_HW_CSUM/RXCSUM`
   - 不写 `ICENET_CSUM_ENABLE`
   - `post_send()` 不再产生 `ICENET_TXCSUM_REQ`
2. 重建 `rocket-singlecore-nic-gdbserver-smoke` workload/rootfs。
3. 用同一颗最新 AGFI `agfi-019e0b22099a5214b` 重新跑 fresh F2 runfarm。
4. 在 host 侧重复 ICMP payload 组合：
   - 默认 ping
   - `-p ff`
   - `-p 00`
   - `-p 0123456789abcdef`
   - `-s 16`
   - `-s 56`
   - `-s 80`

判据：

- 若关闭 offload 后 payload 不再损坏，则根因收敛到 IceNet checksum offload 控制链路，优先修软件/driver；无需新比特流。
- 若关闭 offload 后 payload 仍损坏，则 checksum offload 分支被证伪，下一轮应在硬件侧给 target->host 方向补更深的可综合观测：
  - IceNet send path 输出
  - `hPort.nicOut`
  - `ntht_queue.enq/deq`
  - `NICTokenToBigTokenAdapter` 每个 flush 的 slot/data/valid/last
  - CPU stream pull 出来的 bigtoken 原始 data/header
  - 对已知 ICMP payload 模式的 byte-level watchpoint
