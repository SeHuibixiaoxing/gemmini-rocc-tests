### 2. `runworkload` 很快结束，但不是 guest 正常完成

### 6. 这条错误在 host 代码中的精确定义是“CPU-managed stream 认为 FPGA 侧空闲空间不足”

错误串来自：

- `generators/firechip/bridgestubs/src/main/cc/bridges/simplenic.cc`

其触发条件是：

```cpp
token_bytes_sent_to_fpga = push(..., BUFWIDTH * tokens_this_round, BUFWIDTH * tokens_this_round);
if (token_bytes_sent_to_fpga != tokens_this_round * BUFWIDTH) exit(1);
```

而 `push()` 在：

- `sims/firesim/sim/midas/src/main/cc/bridges/cpu_managed_stream.cc`

中的返回 `0` 条件是：

```cpp
auto space_available = fpga_buffer_size() - mmio_read(count_addr());
if ((space_available == 0) || (space_available < threshold_beats)) {
  return 0;
}
```

也就是说，这不是“`write()` syscall 失败”，而是：

- host 通过 MMIO 观察到 FPGA 侧 `from_cpu` 队列没有足够空位
- 因为本次 `required_bytes` 要求整批写满，所以直接返回 `0`

### 7. 从参数上看，这个“空位不足”在启动早期本来不应该发生

已知：

- `TOKEN_QUEUE_DEPTH = 3072`
- `wanted bytes = 58560`
- `BUFWIDTH = 64`

因此本次 push 需要：

- `58560 / 64 = 915` beats

而 stream queue 总深度是：

- `3072` beats

所以要让 `push()` 因“空位不足 915 beats”而直接返回 `0`，
则 `mmio_read(count_addr())` 至少要接近或超过 `3072 - 915 = 2157` beats。

对一个刚 `Commencing simulation.` 的最小 smoke 来说，这非常不自然。
它更像：

- stream occupancy 状态已经漂移 / 读错
- 或者 target 侧根本没有按预期消耗 `from_cpu` token
- 或者 AGFI 在这一段 stream / MMIO 路径上存在硬件不稳定

### 8. 这版 AGFI 同时存在明确 timing violation

同一 bitstream 的构建证据明确显示：

- build pane 中多次出现
  `WNS=-3.544`, `TNS=-2652.809`, `WHS=-3.652`
- post-route timing report 中存在大量
  `Slack (VIOLATED)`
- 最终产物是
  `post_route.VIOLATED.dcp`

因此这轮 FPGA 现象不能被当成“纯软件或纯 bridge 语义”的干净证据。

## 分析

## 这轮失败点已经比之前更明确

它不是：

- `pipeline-runtime` 用户程序卡死
- guest Linux 中 `gdbserver` 没监听
- guest 内网络没有配置好

而是：

- FireSim host-side `SimpleNIC` 在刚进入仿真后立刻因为
  `from_cpu` stream 看起来“没有足够空位”而退出

## 为什么这不能直接证明 `SimpleNICBridge.scala` fix 无效

之前已经做过一轮最小 local metasim A/B：

- 去掉 `SimpleNICBridge.scala` fix，`1 CPU + NIC + hello-baremetal` 仍能通过
- 恢复 fix，也同样通过

那轮结论已经说明：

- 本地最小 metasim 不是这条 FPGA 失败的充分 reproducer

而本轮又新增了一个关键限定：

- 当前这颗最小 Rocket NIC AGFI 本身 timing 不收敛

所以现在更严谨的判断应当是：

1. `SimpleNICBridge.scala` 的锁步修复在静态语义上仍然合理
2. 但这轮 FPGA 失败不能用来单独证明“fix 仍然有 bug”
3. 因为 timing-violated AGFI 完全可能在 stream 计数 / MMIO / queue 路径上制造假象

## 为什么这轮也不能拿来证明 `gdbserver` 已经打通

原因同样直接：

- guest 根本没到 Linux 用户态
- `gdbserver.info` 和 `gdbserver.log` 都未生成

所以这轮最多只能说明：

- FireSim manager workflow 跑完了
- 但 `NIC + Linux + gdbserver` FPGA smoke 仍然没有越过最早期 host NIC path

## 当前最稳妥的结论

这颗：

- `agfi-06c821df02283a12e`

可以用于“验证最小 FPGA NIC 路径是否还有极早期失败”，
但不能继续承担“判定 guest 软件链路是否正确”的职责，因为它本身不 timing-clean。

## 下一步

1. 不要把这轮结果记成 `gdbserver` 语义失败；应记成
   “timing-violated NIC AGFI 上，host-side `SimpleNIC` 早死”。
2. 若继续走 FPGA 路径，优先换成 timing-clean 的 NIC bitstream，
   再复跑同一条最小 `1 CPU + NIC + Linux + gdbserver` smoke。
3. 若短期内拿不到 timing-clean NIC AGFI，则不要继续在这颗 AGFI 上堆更多 guest 层调试动作，
   因为它还没越过最底层 host NIC 注入阶段。
4. 后续若要继续缩小问题面，优先加的是 host-side `SimpleNIC` / CPU-managed stream
   occupancy 观测，而不是 guest 程序日志。
