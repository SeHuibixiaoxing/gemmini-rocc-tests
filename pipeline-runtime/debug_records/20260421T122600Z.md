## 分析

### A. 这轮与更早的 `segment3` plateau 是同一类问题，而不是新回退

- 这轮和先前 `20260421T015501Z` 的主线 rerun 一样，都能：
  - 越过旧的 `segment0 export` frontier
  - 推进到 `segment3` compute 区域
- 因而 `cfg32` 的引入至少没有让主线回退到更早卡点。

### B. 但这轮又多了一条重要证据：stall 不是只发生在“最后一条 sparse log”所在点

- sparse log 最后一条可见内容位于：
  `segment3 stage0 pointwise / rr-acquire handoff`
  附近
- 但 Linux `RCU stall` 又告诉我们：
  某个 `rerocc_pipeline` 线程卡进了
  `pagemap_*`
  路径
- 因而当前最稳妥的说法不是：
  “就是最后这条 `rr-acquire-wrap` 卡住”
- 更稳妥的说法是：
  **当前 plateau 位于 `segment3` compute 主线；直接证据把嫌疑收敛到 `segment3 stage0 pointwise/rr handoff` 与并发线程中的 `pagemap` 相关路径。**

### C. 这轮 breadcrumb 仍然不够回答 `segment3` 的最后相位

- 当前 breadcrumb filter 仍然是：
  - `segment=0`
  - `global_stage=0`
  - `local_stage=0`
- 所以它只能继续为我们确认：
  - `segment0 export` 已被越过
- 它不能直接回答：
  - `segment3 stage0` 最后一条 pointwise breadcrumb 是 `call-b`、`mm-b`、`mm-e` 还是 `postcall fence`

## 结论

- `cfg32` 软件主线已经在新的 bitstream 上再次进入 `segment3`
- 去掉主线 `TraceV` 依赖后，stall 仍然存在
- 当前主线 authoritative plateau 仍在：
  `segment3`
  compute 区域
- 结合 sparse log 与 `uartlog`，现阶段最值得继续缩窄的是：
  - `segment3 stage0 pointwise / rr handoff`
  - 与并发线程中的 `pagemap` 路径的关系
