## 直接证据

### 1. `custom_boot_pin` 确实被带入了 live run

manager pane log 与 live process command line 都包含：

- `+custom_boot_pin=1`

因此这次 run 不是口头假设，而是真实走了
`HarnessBinders.WithCustomBootPinPlusArg`
驱动的 target-side `CustomBootPin` 路径。

### 2. TracerV 不再停死在 boot ROM `wfi`

与上一轮只到 `0x100034 wfi` 不同，这次 `metasim_stderr.out` 中出现了：

- hart0 从 `0x100034` 继续前进到
  `0x100040`, `0x100044`, ... `0x1000b8`
- hart1 也继续前进到
  `0x100084`, `0x100088`, ... `0x1000b8`
- hart0 一度到达
  `pc=0x80000000`

这说明：

- 两颗 hart 都已经从原先的 boot ROM 睡眠点被唤醒
- 原问题并不是“guest 程序自己的某条指令卡住”
- 只要换一条 target-side 唤醒路径，boot ROM 就不再永久停在 `wfi`

### 3. host-side bootdiag 依旧打印了那次原始 TSI MSIP 写

同一份 `metasim_stderr.out` 仍包含：

- `[tsi-bootdiag] entering tsi_t::reset for hart0 msip`
- `[tsi-bootdiag] write_chunk addr=0x2000000 nbytes=4 data=0x1`
- `[tsi-bootdiag] returned from tsi_t::reset`

因此本轮并不是“关闭了 TSI，所以才好了”。
恰恰相反，是在原始 host TSI 写仍存在的情况下，
额外加入 target-side custom boot pin 后，系统才不再停死在最初的 `wfi`。

### 4. live gdb 显示这次 CLINT / hart 状态与失败现场发生了本质变化

对 `PID 16601` 进行 live gdb 采样，得到：

- `bootAddrReg = 0x80000000`
- `clint.ipi_0 = 0x0`
- `clint.ipi_1 = 0x1`
- hart0 `reg_wfi = 0x0`
- hart1 `reg_wfi = 0x0`
- hart0 `mstatus.mie = 0x0`
- hart1 `mstatus.mie = 0x0`
- hart0 `mie = 0x8`
- hart1 `mie = 0x8`

和上一轮失败现场相比，最关键的变化是：

- 失败现场：
  - `ipi_0 = 0`
  - `ipi_1 = 0`
  - 两颗 hart `reg_wfi = 1`
- custom boot pin 现场：
  - `ipi_1 = 1`
  - 两颗 hart `reg_wfi = 0`

无论 `ipi_0/ipi_1` 与 hart 编号在当前设计里是否存在命名/观察上的对应差异，
这已经足够证明：

- target-side custom boot pin 路径确实能在 CLINT 侧留下有效的唤醒状态
- 而原始 host TSI 路径做不到

## 综合结论

这轮对照实验已经基本坐实：

`原始 hang 的根因在 host-side TSI -> serial-TL -> CLINT 的唤醒路径，而不在 guest 程序本身`

更精确地说：

- host-side `tsi_t::reset()` 的 `write_chunk(0x2000000,4,1)` 确实执行
- 但它没有在失败现场形成有效的 CLINT 唤醒电平
- 改用 target-side `CustomBootPin` 之后，hart 立刻能越过 boot ROM `wfi`

## 建议的后续方向

优先级最高的后续不再是继续移动 guest 卡点，而是二选一：

1. 工程化修复：
   在 metasim / FireSim bringup 路径中优先使用 `CustomBootPin`
   作为 boot wake 机制，避免依赖当前失效的 host TSI MSIP 写
2. 根因修复：
   继续缩到 `host TSI serial-TL` 的地址可达性/应答路径，
   重点检查为什么 `write_chunk(0x2000000,...)`
   会被 target 接收为“已完成”，却没有在 CLINT 上留下有效电平

就当前调试目标而言，第 1 条已经足以证明原始卡死点不在用户程序。
