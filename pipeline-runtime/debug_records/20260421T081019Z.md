### 3. 第一轮 networked run：证明 host topology 已经起来

run host：

- `tap0` 从之前 `NO-CARRIER` 变成了
  `UP ... LOWER_UP`
- `switchlog` 明确显示：
  - `Slot ID not specified. Assuming tap0`
  - 已经打开两组 shmem port
  - `SSHPort` 已绑定 `tap0`

guest：

- `uartlog` 出现：
  - `[gdbserver] phase=prelaunch ...`
  - `[gdbserver] phase=listening ...`
  - `[gdbserver] phase=inferior ...`
- 从 live image 读回：
  - `gdbserver.log` 记录 `Listening on port 2345`
  - `runner-proc.stage` 记录 inferior `State: t (tracing stop)`

结论：

- host topology blocker 已经消失
- `gdbserver` 路径也仍然有效

但同时出现新的 blocker：

- host 侧对 `172.16.0.2:2345` 仍然 `No route to host`
- `ip neigh show dev tap0` 对 `172.16.0.2` 只有 `FAILED`
- live image 中 `gdbserver.info` 显示：
  - `net_dev=eth0`
  - `guest_ipv4=`

这说明问题已经转成 guest netdev/IPv4，而不是 host topology

### 4. 第二轮：修 guest 侧 `eth0` 硬编码

为验证 “接口名不是 `eth0`” 这个假设，新增两处低风险修正：

- workload-local `S40network`
  - 若 `eth0` 不存在，则退化为选择第一个非 `lo` 接口
- runner `guest_ipv4` 探测
  - 若未显式指定 `GDBSERVER_NET_DEV`，
    则优先 `eth0`，否则退化为选择第一个非 `lo` 接口

第二轮 run 结果：

- `S40network` 卡在 `Starting network:`
- 用 live image 读回时，
  `runner.stage` / `gdbserver.info` 仍为空
- 说明这次连 `S99run` 都还没真正开始跑完

静态推理：

- Buildroot 里 `/etc/network/interfaces` 只有 `lo`
- 所以 `ifup -a` 本身不应长时间阻塞
- 更合理的解释是：
  “第一个非 `lo` 接口” 误选中了 `sit0/gre0` 这类虚拟接口

### 5. 第三轮：把接口筛选收窄到真实以太网设备

将 guest 侧接口选择都进一步收窄为同时满足：

- `/sys/class/net/<if>/device` 存在
- `type=1`
- MAC 非 `00:00:00:00:00:00`

第三轮 run 结果：

- `S40network` 已恢复为：
  `Starting network: OK`
- `S99run` 能继续往下跑
- `uartlog` 出现：
  - `[gdbserver] phase=prelaunch ... guest_ipv4=unknown`
  - `[gdbserver] phase=listening ... guest_ipv4=unknown`

从 live image 读回：

- `gdbserver.info`：
  - `phase=prelaunch`
  - `net_dev=`
  - `guest_ipv4=`
- host 侧对 `172.16.0.2:2345` 仍然 `No route to host`

## 本轮结论

### 结论 1

“当前 gdbserver path 无法 host attach” 的主要 blocker 已经不再是 FireSim topology。

直接证据：

- `topology: example_1config`
- `tap0` 稳定 `LOWER_UP`
- `switchlog` 明确绑定 `tap0`

### 结论 2

当前剩余 blocker 已经转成 guest netdev/IPv4：

- 第三轮里 `S40network` 虽然回到了 `OK`
- 但 `gdbserver.info` 仍显示：
  - `net_dev=`
  - `guest_ipv4=`
- 说明 guest 内没有出现任何满足当前筛选条件的可用以太网 netdev

### 结论 3

因此现在不应继续围绕：

- `switch0`
- `tap0`
- SSH 隧道

再做碰运气式调试。

下一轮的最小有效信息应该直接来自 guest：

- `/sys/class/net` 目录枚举
- 每个接口的：
  - `type`
  - `address`
  - `device` 是否存在
- 若 icenet 确实创建了接口，再确认其最终名字是什么

## 建议下一步

1. 在 runner 或更早的 guest init 阶段，新增一份极小的 netdev 审计输出：
   把 `/sys/class/net/*` 的名字和关键属性直接写到 guest 文件
2. 若仍无任何真实以太网 netdev，
   就要转去检查：
   - icenet 设备树/枚举
   - Linux 驱动 probe
   - 该 target 是否真的向 guest 暴露了可用网口
3. 在拿到 guest netdev 枚举前，不要再继续只试图 host 侧连 `172.16.0.2:2345`
