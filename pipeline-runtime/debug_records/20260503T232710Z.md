- guest 侧 workload 打印 `*** PASSED ***`，说明最小测试程序自身没有失败。

- `tap0_gdb_attempt.pcap` 和 `switchlog` 表明 target->host 的 GDB RSP 文本在到达 host TAP 前已经损坏，不是 GDB、Linux socket、port-forward 或 gdbserver 逻辑问题。

## 关键证据

`tcpdump` 和 `switchlog` 中同一个 RSP `qSupported` 响应出现固定 bit clear：

- `QEnvironmentUnset` 的 `Q` 变成 `0x11`
- `qXfer` 的 `f` 变成 `&`
- `read` 的 `a` 变成 `!`
- `fork` 的 `r` 变成 `2`
- `Randomization` 的 `R` 变成 `0x12`
- `exec-file` 的 `x` 变成 `8`

这些都对应 byte bit `0x40` 被清掉。

更关键的是，错误位置不是随机分布，而是固定落在每个 64B bigtoken 的 word/byte 位置上：bigtoken 内偏移 `+16`，也就是 512-bit token 中第 2 个 64-bit word 的最低 byte。`switchlog` 在 `ShmemPort recv` 层已经看到损坏，所以坏数据已经进入 host-side switch 之前的 CPU-managed stream 读出路径。

## 静态结论

本轮把强嫌疑从 NIC 协议/guest 软件进一步收窄到 FireSim target->host CPU-managed stream 的 512-bit -> 64-bit wide-to-narrow 读出边界。

原因：

- 已经在 `SimpleNICBridge` 的 `pcieOutQ` 前后加过 2-entry 队列，仍然出现同一固定位置 bit clear，说明只在 NIC packer 输出前加队列不足以消除问题。
- host 侧从 F2 PCIS/BAR4 drain 一个 512-bit bigtoken 时，会执行 8 次 64-bit destructive read。
- 旧 `StreamWidthAdapter` 在 wide-to-narrow 路径中直接组合读取 `io.wide.in.bits.asTypeOf(Vec(...))(wide_beats)`，同时只有 `wide_last_beat && io.narrow.out.ready` 时才让 wide source ready。这会把一个 512-bit 源 beat 暴露给 8 次独立 CPU/PCIS 窄读周期。
- 当前错误刚好是“固定 512-bit lane/byte 出错”，与这个边界高度一致。
- 配套把 CPU-managed AXI 的最大单次 transfer 收紧到 `axiBeatBytes * 256`，也就是 F2 上 2048B，避免把一笔 FIFO 交易拉得过长后再叠加 destructive read 边界的不确定性。

因此本轮修复策略是：在 wide beat 被接受时一次性锁存完整 512-bit 数据，再由本地寄存器按 64-bit beat 输出，避免后续 8 次窄读继续依赖上游 wide source 的组合数据。
