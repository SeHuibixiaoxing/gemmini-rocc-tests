# NIC 新构建比特流退化的二次静态钉证与回退

日期：2026-05-03T03:28:45Z

## 本轮目标

用户要求再次结合历史 `debug_records` / `change_records` 静态排查：

- 后续新构建的 single-core NIC bitstream 为什么相对旧通过版跑不通；
- 到底是哪类改动让新构建不再等价于旧通过硬件；
- 能回退的回退，不能只停留在“可能”。

本轮不启动新 bitstream，只完成静态钉证、源码回退和本地 `replace-rtl` freshness gate。

## 已经钉死的回归链

历史记录中最硬的链路仍然是：

```text
04-30 target->host bit-clear 失败
  -> 添加 payload snapshot
  -> agfi-0079cbbca617eca4e 跑通 remote gdb
  -> 05-02 硬件归位时裁掉 payload snapshot
  -> agfi-032d10150efc1d4ec 又复现 target->host payload corruption
```

关键记录：

- `20260430T152736Z.md` / `20260430T162000Z.md`：
  target->host payload 在 switch/TAP 前已经损坏；
- `20260430T162900Z.md`：
  加入 `hPort.nicOut` history、`NICTokenToBigTokenAdapter.pcie_out` last bigtoken、
  host `SIMPLENIC TX SNAPSHOT`；
- `20260502T164142Z.md` / `20260502T164947Z.md`：
  05-02 归位时裁掉 payload-heavy OCL surface；
- `20260502T223837Z.md`：
  裁掉后新 AGFI 再次出现 target->host payload corruption。

这不能证明 snapshot 的语义本身在修包，但它证明删掉 snapshot 后的新硬件不再等价于
旧通过版。考虑到这些 snapshot 给 target->host payload 关键路径提供寄存/keep/观测负载，
当前回退原则是：恢复旧通过版里已经存在的 snapshot surface。

## 当前结论

本轮把“后续新构建比特流跑不通”的硬件差异进一步收敛为两类：

1. 05-02 归位裁掉了 04-30 通过版已有的 payload snapshot surface，这是导致
   `agfi-032d10150efc1d4ec` 重新出现 target->host payload corruption 的最硬 old/new
   差异证据。
2. 上一轮修复又加入了 04-30 通过版没有的 first16 三段观测，以及残留 PCIS 写顺序
   debug/status 改动，使 `agfi-08caa7b45db625368` 这类新构建不再是“回到旧通过版”的干净验证。

当前源码已经归位为：

- 保留 04-30 通过版已验证存在的 NIC payload snapshot；
- 去掉未被旧通过版验证的 first16 三段观测；
- PCIS bridge 回到 04-30 通过版功能/观测形态；
- 保留 `fromHostValidDrive = true.B` 和 `done = !(toHostFire || fromHostFire)`，因为它们属于
  04-30 后已验证链路，不应回退到 04-26 中间态。

下一轮如果要验证，应使用当前生成物重新构建 single-core NIC bitstream，并在远端进入 Vivado 后
核对上述 SHA / marker，确保没有 stale generated collateral。
