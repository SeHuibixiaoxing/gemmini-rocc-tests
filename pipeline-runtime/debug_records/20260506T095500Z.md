## Interpretation

This is not a gdbserver, rootfs, FireMarshal, software breakpoint, or NIC
runtime failure. The build never produced a hardware image to run.

This is also different from the mainline cfg32 NIC failure:

- mainline cfg32 NIC failed at `Phase 3 Detail Placement` because the CL pblock
  did not have enough available CLBs;
- noTrace cfg32 NIC passed placement but failed route legality with thousands
  of node overlaps.

The noTrace fallback reduced resource pressure enough to place, but not enough
to route. The failure is a congestion/routing legality failure in the dense
12-manager cfg32 NIC image. A pure timing interpretation is too weak: Vivado did
not simply report negative slack; it reported an illegally routed design with
5975 overlaps and partially-conflicted nets.

The post-place/post-phys-opt worst timing path was shell/PCIS SLR2 dominated,
but the final conflicted route nets include ReRoCC manager, DMA buffer, GlobalNoC
router, and Gemmini local logic. That points to broad fabric congestion in the
CL, not one isolated timing path.

## Next decision

Do not update the cfg32 NIC HWDB and do not run gdbserver on this build.

The next build should not be launched blindly. Candidate directions, in order of
confidence:

1. Further reduce resource/routing pressure while keeping the gdbserver-debug
   objective. Examples: smaller manager count debug target, less aggressive
   cfg32/NOC pressure, or selective observability/resource removal beyond
   noTrace.
2. If the user insists on exactly `12p4c128sbus32cfg`, try one implementation
   strategy variant only after comparing route/congestion reports. Strategy
   alone may not be enough because the failure is 5975 node overlaps, not just
   marginal WNS.
3. Keep the software/gdbserver path unchanged. It was already validated on the
   single-core 1BP NIC AGFI and preflighted for cfg32 NIC; this failure occurred
   before any workload could run.
