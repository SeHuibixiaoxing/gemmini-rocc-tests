## Result

Status: **infrastructure/harness fail after meaningful GDB success**.

The old AGFI did accept the remote GDB connection and executed a substantial part of the old software-breakpoint capability path:

- `target remote :32345` succeeded.
- GDB stopped at `_start`.
- Three software breakpoints were inserted:
  - `main`
  - `smoke_iteration_hook`
  - `smoke_worker_heartbeat`
- `continue` reached `Breakpoint 1, main`.
- `bt` worked.
- `info registers pc sp ra a0 a1` worked.
- `x/12i $pc` worked.
- `print smoke_counter` worked and returned `0`.

The failure was not a target transport reset or breakpoint failure. The expect driver crashed locally while constructing the GDB command for `smoke_memory_probe[0]`:

```text
invalid command name "0\"
    invoked from within
"gdb_cmd "print/x smoke_memory_probe\\[0\\]""
```

Root cause: Tcl command substitution treated the array index brackets as syntax because the generated expect script over-escaped the brackets. The shell script was fixed after this run to emit:

```tcl
gdb_cmd "print/x smoke_memory_probe\[0\]"
gdb_cmd "set variable smoke_memory_probe\[7\] = 0xabcdef"
gdb_cmd "print/x smoke_memory_probe\[7\]"
```

## Interpretation

This run is strong evidence that the current host/network/software stack can still establish a real remote GDB session against the old 1bp AGFI. It does not yet prove the full old capability set, because the harness aborted before memory write/read, `next`, multi-breakpoint continuation, thread inspection after continuation, Ctrl-C, clean exit, and detach/quit coverage.

Next action: restart the old-AGFI workload to get a fresh `gdbserver --once`, then rerun the corrected expect harness as the first GDB connection.
