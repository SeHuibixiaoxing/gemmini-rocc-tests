## 新观察

### 1. 当前“主线走到哪一步”需要分两层读

如果只看非 `TraceV` 的低扰动主线 capture，
当前最后一个比较强的 authoritative frontier 仍是：

- `spm-xlate-release mgr=5 cfg=15 phase=restore-begin`

对应：

- `debug_records/20260417T052141Z.md`
- `triage_prt_capture.py` 复跑 `20260416` 官方 capture 也仍输出同样结论

但如果把后续 `TraceV/workerpc` 分支拿来当补充证据，
还能再多知道一层：

- freeze 并不是 boot / wrapper / runner early 问题
- 它会再次稳定回到
  `stage=0 / subbatch=1 / tensor=2 export DMA`
  热路径
- sparse log 表面上的
  `page=0 first-chunk-submitwait-end`
  不是最终真实边界
- breadcrumb 已经表明执行深入到更后面的 page

### 2. `dma_submitwait_after_cleanup -> dma_page_end` 之间是当前最值得补细的一小段

静态读 `src/prt_dma.c` 后可确认：

- callee `dma_submit_wait_annotated_scoped()` 在 line `1633` 记：
  `dma_submitwait_after_cleanup`
- caller `dma_copy_spm_pages_to_host_linux()` 返回后立刻做：
  - `dma_breadcrumb_page_end(...)`
  - `dma_trigger_export_host("sw-e", ...)`
  - `copied += chunk`
  - `remaining -= chunk`

这说明：

- 当前如果 breadcrumb 最后停在
  `dma_submitwait_after_cleanup`
  而没有更晚 page 级 phase，
  下一轮最该补的不是大范围字符串日志，
  而是把这个 tiny window 用新的二进制 breadcrumb phase 再切细。

### 3. `debug_records` / `change_records` 目前缺少按类别聚合入口

  不应该直接搬文件。

因此本轮采用：
