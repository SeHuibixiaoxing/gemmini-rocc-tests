# NIC DMA API driver fix: F2 dynamic validation

日期：2026-04-30T04:39:00Z

## 本轮目标

验证 `20260430T035726Z.md` 中钉死的 IceNet driver non-coherent DMA API 修复是否真的解决 F2 single-core NIC 的 target-to-host payload corruption，并同时确认 remote gdbserver 路径是否可用。

本轮没有重建 bitstream；使用最新 single-core NIC AGFI：

- AGFI：`agfi-019e0b22099a5214b`
- Run host：`i-056e8f205409d8433` / `192.168.1.191`
- workload：`rocket-singlecore-nic-gdbserver-smoke`
- 现场回收目录：`tmp/firesim-aws-f2/nic-scenes/dmaapi-driverfix-pass-20260430-0433/`

## Freshness 证据

本轮在启动 runworkload 前确认远端部署镜像包含本轮 driver 修复：

- 远端 rootfs SHA 与本地 smoke rootfs SHA 一致。
- 远端 bootbinary SHA 与本地 `br-base` / smoke bootbinary SHA 一致。
- 远端 bootbinary 可检索到新 driver 字符串：
  `IceNet DMA API mappings enabled; checksum offload and SG disabled`

UART 动态日志也确认 target 实际加载了新驱动：

- `uartlog` 第 2830 行：
  `icenet 10016000.ice-nic: IceNet DMA API mappings enabled; checksum offload and SG disabled`
- `uartlog` 第 2831 行：
  `Registered IceNet NIC 00:12:6d:00:00:02`
- `uartlog` 第 2847 行：
  `Starting network: OK`

## Host-side 干扰项

启动早期 `tap0` 上有 Xilinx `hw_server` 的 UDP 1534 discovery broadcast，源/目的为：

- `172.16.0.1:1534 -> 172.16.255.255:1534`

该广播会被 switch 注入 target，导致 UART 中出现大量 `Xilinx Hardware Server` 相关 NIC token debug。它不是 target 发出的异常包。为降低后续测试噪声，本轮只停止了远端 run host 上的 `hw_server` 进程；`FireSim-f2`、`switch0`、runfarm、bitstream 构建均未被停止。

## ICMP payload 验证结果

在 guest 网络 up 后，从 run host 对 `172.16.0.2` 执行：

- `ping -c 2 172.16.0.2`
- `ping -c 2 -s 16 -p ff 172.16.0.2`
- `ping -c 2 -s 56 -p ff 172.16.0.2`
- `ping -c 2 -s 80 -p ff 172.16.0.2`
- `ping -c 2 -s 80 -p 00 172.16.0.2`
- `ping -c 2 -s 80 -p 0123456789abcdef 172.16.0.2`

所有 case 均为 `2 packets transmitted, 2 received, 0% packet loss`。

pcap 证据：

- `tap0_dmaapi_driverfix.pcap`
- 80-byte `0xff` reply payload 中，target-to-host 回包保持连续 `ffff ... ffff`，没有上一轮看到的 `ff -> fe` 或 `ff -> fd` bit-clear。
- 80-byte `0x00` reply payload 保持连续 `0000 ... 0000`。
- 80-byte `0123456789abcdef` reply payload 保持连续 `0123456789abcdef` pattern。

UART token debug 也支持这一点。例如 `target_to_switch_pull event=14` 的 sample 中保留：

- `0x67452301efcdab89`
- 后续多个 flit 同样保持该 pattern。

这说明 corruption 已经不再出现在 IceNet send DMA 读出之后的 host bridge / switch / TAP 路径上。

## Remote gdbserver 验证结果

guest 侧已进入：

- `uartlog` 第 2866 行：
  `[gdbserver] phase=prelaunch net_dev=eth0 guest_ipv4=172.16.0.2 endpoint=172.16.0.2:2345 pid=0`

随后通过 SSH local forward 从 manager 侧连接：

```bash
ssh -f -N -L 32345:172.16.0.2:2345 ubuntu@192.168.1.191
riscv64-unknown-linux-gnu-gdb gdbserver-smoke \
  -ex 'target remote :32345' \
  -ex 'b main' \
  -ex 'continue' \
  -ex 'bt' \
  -ex 'detach' \
  -ex 'quit'
```

gdb 结果：

- `Remote debugging using :32345`
- 初始停在 `_start`
- 成功设置 `Breakpoint 1 at ... gdbserver-smoke.c:22`
- `continue` 后命中 `main()`
- backtrace 为 `#0 main ()`
- `detach` 成功

结论：remote gdbserver 的 host-to-target TCP 通道和 target-to-host TCP 回包路径在本轮硬件上实际可用。

## 结论

本轮动态证据支持 `20260430T035726Z.md` 的根因判断：

- 原 bug 是 IceNet Linux driver 在 RISC-V non-coherent DMA 环境下绕过 Linux DMA API。
- 使用 `dma_map_single` / `skb_frag_dma_map` / `dma_unmap_*` 后，上一轮稳定复现的 target-to-host payload bit-clear corruption 没有复现。
- 当前 single-core NIC + Linux + gdbserver smoke 已经能 boot、起网、ping pattern 验证、remote gdb attach 到 `main()`。

下一步不需要为这个 corruption 再构建新 bitstream。若要把 remote gdb smoke 变成自动 PASS workload，应调整 gdb 测试脚本或 SOP：测试 gdb 后不要在断点处 `detach`，而是 `continue` 到 inferior 正常退出，或让 workload 使用 local-gdb 自动批处理路径。
