## 静态结论

上一版修复后，`hPort.toHost.hReady` 已经不依赖 `hPort.fromHost.hReady`，但仍保留了一个更隐蔽的 lockstep 假设：

```scala
fromHostValidDrive = hPort.toHost.hValid && localQueuesReady
```

FAME target cycle 并不保证一个 bridge 的所有 channel 在同一个 host cycle 同时 fire。生成后的 `targetCycleFinishing` 会用 per-channel `*_fired_0` 记住已经完成的 channel；因此可能出现：

1. NIC output source channel 已经 fire；
2. 同一个 target cycle 仍在等待 NIC input sink valid；
3. `hPort.toHost.hValid` 因 source 已完成而下降；
4. SimpleNIC 旧逻辑随之把 `hPort.fromHost.hValid` 撤掉；
5. `targetCycleFinishing` 永远等不到 NIC input sink valid，CPU-managed stream 的 from-cpu FIFO 被顶满。

因此本轮根因判断不是 timing 首要问题，而是 SimpleNIC Bridge 把 target-cycle 双方向 handshake 误建模成同拍 lockstep。

## 本轮修复

修复后的 HostPort 方向语义：

```scala
toHostReadyDrive = ntht_queue.io.enq.ready
fromHostValidDrive = htnt_queue.io.deq.valid

toHostFire = hPort.toHost.hValid && hPort.toHost.hReady
fromHostFire = hPort.fromHost.hValid && hPort.fromHost.hReady

ntht_queue.io.enq.valid := toHostFire
htnt_queue.io.deq.ready := fromHostFire
```

`tFire = toHostFire && fromHostFire` 保留为 debug 指标，不再作为两个方向实际推进的唯一条件。新增 counters 记录：

- `to_host_fire_count`
- `from_host_fire_count`
- `to_host_only_fire_count`
- `from_host_only_fire_count`
- `last_to_host_fire_cycle`
- `last_from_host_fire_cycle`
