### 3. live gdb 采样表明 hart 已具备接收软件中断条件，但 CLINT 侧电平为 0

采样结果：

- `bootAddrReg = 0x80000000`

因此这次 hang 的关键事实是：

`host 已发出 MSIP 写，但 target 当前并没有看到 clint.ipi_0 = 1`

## 静态代码结论

### 1. host reset 路径已经收敛到单一行为

静态代码：

- `generators/firechip/bridgestubs/src/main/cc/fesvr/firesim_tsi.cc`
- `generators/testchipip/src/main/resources/testchipip/csrc/testchip_tsi.cc`
- `toolchains/riscv-tools/riscv-isa-sim/fesvr/tsi.cc`

结论：

- `firesim_tsi_t::reset()` 只是在 loadmem 完成后调用
  `testchip_tsi_t::reset()`
- `testchip_tsi_t::reset()` 最终只会做
  `tsi_t::reset()`
- `tsi_t::reset()` 只做一件事：
  `write_chunk(0x2000000, 4, 1)`

因此“host 控制流没走到 reset”这一支已被排除。

### 2. 现有设计里还有一条 target-side 唤醒路径：`CustomBootPin`

静态代码：

- `generators/testchipip/src/main/scala/boot/CustomBootPin.scala`
- `generators/chipyard/src/main/scala/harness/HarnessBinders.scala`

`CustomBootPin` 的行为：

- 通过 `+custom_boot_pin=1` plusarg 驱动
- 在 target 内部通过 `masterWhere = CBUS`
  先写 `BootAddrReg`
  再写 `CLINT msip`

关键注释原文已经明确：

- `This needs to write to clint and bootaddrreg, which are on CBUS/PBUS`

这条路径天然避开了 host-side TSI 那条 serial-TL 唤醒链。

## 综合结论

本轮已经把问题进一步钉死为：

- guest 还没开始执行
- 两颗 hart 都停在 boot ROM `wfi`
- host-side `MSIP` 写确实发出
- 但 target 当前 `clint.ipi_0` 仍为 0
- serial-TL / loadmem 现场空闲

因此当前最准确的故障描述是：

`host TSI 发出的最终 hart0 MSIP 唤醒写，没有在 target 侧形成有效的 CLINT 唤醒电平`
