## 关键现象

这轮已经越过以前的 pre-boot `from_cpu_stream` 塞满问题，进入 Linux 和
用户态：

```text
Registered IceNet NIC 00:12:6d:00:00:02
S40network
S99run
[gdbserver] phase=prelaunch ... endpoint=172.16.0.2:2345
```

但没有看到：

```text
[gdbserver] phase=listening
```

host 侧 `tap0` 状态：

- `tap0` 配置为 `172.16.0.1/16`。
- TX 计数增长。
- RX 计数保持 `0`。
- pcap 只有 host -> target / broadcast 包，没有 guest -> host 回包。

## NIC debug 证据

host driver 的 pending peer buffer 修复已经生效，能捕获真实 host->target
flit：

- `pending_peer_snapshot=1`
- `pending_peer_valid_flits=37`
- `peer_flit_sample` 中能看到 UDP/broadcast/DHCP-like payload。

但 target/RTL 侧仍没有真正把这些 payload 送进 guest NIC：

- `from_payload=0`
- `from_empty` 很大
- `target_bits in(data=000... keep=0 last=0)`
- `pcie_in_bits=0x000...`

因此本轮不是 “host 没发包”，而是 host->target payload 已经进入 host
driver snapshot，但在 FPGA bridge 进入 target-facing NIC input 前被大量
empty host->target token 挡住或淹没。

## 判断

`agfi-0979aad323cd3ca4d` 证明 `fromHostValidDrive` 已经把系统推进到
Linux/userland。当前新 blocker 是 host->target 方向真实 payload 未被及时
稳定送入 target NIC input：

1. host driver 已能看到真实 host->target 包；
2. target-facing `nicIn` 仍长期看到 empty token；
3. guest 能注册 IceNet，但收不到 host 回包，所以 remote gdb/gdbserver 双向
   通信无法建立。

最强嫌疑是 SimpleNIC bridge 内部把 CPU stream 中的大量 empty token 按普通
token 排队给 target，真实 payload 排在这些 empty token 后面；同时
target-facing input 缺少独立 staging，ready 低或队头变化时 payload 不能被
稳定保持到 leaf channel。

## 本轮静态修复方向

已在源码中准备下一颗 bitstream 的修复：

- `nicIn` 由 bridge 持续驱动 “无包” token，`hPort.nicIn.valid := true.B`。
- CPU stream 中 empty host->target token 直接 drop，不再排在真实 payload 前。
- host->target payload 进入两级寄存器 staging：
  - `fromHostPendingPayload*`
  - `fromHostCurrentPayload*`
- target-facing bits 在 target ready 低时保持稳定。
- target->host payload 必须入 `ntht_queue`；empty token 在队列满时 bypass，
  避免 target 被空包反压。
- `macAddr` / `rlimit` / `pauser` config sideband 持续 valid。
- 增加更深的可综合 debug regs，覆盖 payload capture、empty drop、
  current/pending staging、last capture cycle/data/meta 等链路状态。
