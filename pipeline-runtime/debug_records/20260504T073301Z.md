Category: gdbserver

## Context

The current NIC/gdbserver work is trying to minimize FPGA rebuilds. The
previous failure on stale AGFI `agfi-05336229a1326f9ff` stopped before Linux:
host GDB saw `debug_cycle=0`, `target_cycle_ready=0`, and all NIC
ready/valid/fire counters at zero. The live build already contains the
functional fixes for `targetCycleReady` and `readRequestActive`, but not the
new observation CSRs.

## Why Add More Output

The `0x05040001` debug surface could show the main progress milestones and
last event data. A later failure could still leave ambiguity in four places:

- whether a token adapter was stalled by its local ready/valid pair;
- whether a queue was stuck because `valid` or `ready` was missing;
- whether the first stall and the latest stall were the same problem;
- whether progress happened once and then stopped at a different downstream
  stage.

The `0x05040002` additions close those gaps with first/last queue and adapter
snapshots plus per-adapter backpressure counters.

## New Evidence Available In A Future Failing AGFI

A single `simplenic_t::dump_host_debug()` dump should now answer:

- Did host-to-target stream data reach the bigtoken adapter?
- Did the adapter emit into `htnt_queue`, or is `htnt.ready` missing?
- Is `htnt_queue` blocked on enqueue or dequeue?
- Did target `nicIn` accept payload, empty token, or neither?
- Did target `nicOut` emit a payload?
- Did `ntht_queue` accept and dequeue the target packet?
- Did `NICTokenToBigTokenAdapter` flush into PCIE-out?
- Did PCIE-out see backpressure?
- What were the first and last queue/adapter snapshots when progress or
  blocking was observed?
