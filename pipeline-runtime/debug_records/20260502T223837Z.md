因此当前问题不再是早期的 no-boot / no-listen / no bidirectional token progress。

## 失败现象

remote GDB attach 失败：

```text
Remote communication error. Target disconnected: Connection reset by peer.
channel 2: open failed: connect failed: Connection timed out
```

pcap 显示失败原因不是 gdb 脚本，而是 target->host TCP 包损坏：

- host 发出 SYN 到 `172.16.0.2:2345`；
- guest 返回 SYN-ACK；
- SYN-ACK 的 TCP checksum 在 host tap0 pcap 中错误；
- host 不接受该 SYN-ACK，并重复重传 SYN。

## pattern ping 证据

随后在同一现场抓 `tap0` 并执行固定 payload ping：

```bash
ping -c 8 -W 5 -p 00 172.16.0.2
ping -c 8 -W 5 -p 08 172.16.0.2
ping -c 8 -W 5 -p 10 172.16.0.2
ping -c 8 -W 5 -p 18 172.16.0.2
ping -c 8 -W 5 -p ff 172.16.0.2
```

结果：

- `00` 正常；
- `10` 正常；
- `08` 出现 `wrong data byte #24 should be 0x8 but was 0x0`；
- `18` 出现 `wrong data byte #24 should be 0x18 but was 0x10`；
- `ff` 稳定出现 `ff -> 7e/f7/fe` 等固定位置 bit 被清零。

对 pcap 按 Ethernet/TAP 对齐后解析，最强错误形态为：

```text
ICMP payload byte 24 -> tap buffer flit 8, flit % 7 == 1, byte 4, xor 0x08
ICMP payload byte 80 -> tap buffer flit 15, flit % 7 == 1, byte 4, xor 0x08
```

`ff` pattern 还暴露出：

```text
flit % 7 == 1, byte 0, xor 0x81
flit % 7 == 3, byte 6, xor 0x01
flit % 7 == 5, byte 2, xor 0x01
```

这说明 corruption 具有 token/bigtoken 周期性，不像 Linux/gdbserver 软件错误。

## 当前结论

当前 blocker 是 guest->host 返回路径的 payload integrity 问题：

```text
IceNet TX / target NIC out
  -> SimpleNICBridge target-to-host token path
  -> NICTokenToBigTokenAdapter
  -> CPU-managed stream / F2 PCIS read bridge
  -> simplenic_t target_to_switch_pull
  -> shmem switch
  -> SSHPort tap_send
  -> host tap0
```

ICMP reply 与 TCP SYN-ACK 的 checksum 都是在 host tap0 pcap 中已经错误。结合关闭 checksum
offload后仍出现 payload corruption 的既有记录，错误点应在 guest 生成包之后、host tap0
看到包之前。
