## 新观察

### 1. 旧 run-farm 已经进入回收态
- `aws ec2 describe-instances` 显示：
  - `i-090245dfe26a4a757`
  - `State = shutting-down`

### 2. 上一轮环境 blocker 的根因已经明确，而且已验证修复
- blocker 根因不是 workload / AGFI / runtime 本身，而是 manager 所在 `.conda-env` 缺少 `PyNaCl`。
- FireSim deploy 脚本把 `env.key_filename` 固定成 `~/firesim.pem`；当 `PyNaCl` 缺失时，`paramiko` 无法稳定解析该 `ED25519` key，导致 `instance_liveness` 卡住或失败。
- 现在已经验证：
  - `.conda-env` 中 `import nacl` 成功；
  - `Ed25519Key.from_private_key_file('/home/ubuntu/firesim.pem')` 成功。

### 3. `TracerV` instruction trigger 的 host-side 判定逻辑是有效的
- `generators/firechip/bridgestubs/src/main/cc/bridges/tracerv.cc`
  明确表明：
  - `+trace-select=3` 走 instruction trigger 分支；
  - `+trace-start` / `+trace-end` 的 64-bit hex 值会被拆成：
    - 低 32 位：目标指令编码
    - 高 32 位：指令 mask
  - 然后写入：
    - `hostTriggerStartInst`
    - `hostTriggerStartInstMask`
    - `hostTriggerEndInst`
    - `hostTriggerEndInstMask`
- 这不是猜测，也不是依赖合成 `printf`；是 `TracerV` bridge host driver 的直接 MMIO 配置路径。

### 4. guest 里的 instruction trigger 工具确实在 image 基础层存在
- `software/firemarshal/boards/firechip/base-workloads/br-base.json`
  明确包含：
  - `trigger/start -> /usr/bin/firesim-start-trigger`
  - `trigger/end -> /usr/bin/firesim-end-trigger`
- instruction trigger workload
  `...pairdummy-tracerv-inst.json`
  的 `run` 也明确包装成：
  - `firesim-start-trigger && run_rerocc_pipeline_runtime_bertmini_fileonly_sync_capture.sh --batch 8 && firesim-end-trigger`
