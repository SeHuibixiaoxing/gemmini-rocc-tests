## 直接失败证据

本轮 host 侧 `gdb` 能执行：

```text
target remote :2345
Remote debugging using :2345
```

但之后等待 GDB prompt 超时。也就是说，当前不是端口没开、不是 SSH tunnel
没通，也不是 `gdbserver` 没监听；失败发生在 remote GDB RSP/TCP 数据交互阶段。

现场已保存：

```text
debug_records/artifacts/20260503T190331Z_agfi0bd_relaxed_gdb_rsp_payload_corruption/
```

关键文件：

```text
local/remote-swbreak-expect-20260503T190331Z-192_168_1_186/remote-swbreak.expect.log
remote/tap0_icmp.txt
remote/ping_tap0.txt
remote/sim_slot_0/uartlog
remote/switch_slot_0/switchlog
remote/nic_scene.tgz
```

`tap0_icmp.txt` 与 `ping_tap0.txt` 钉死了 target->host payload 在到达 host TAP
前已经被清 bit：

```text
wrong icmp cksum 4f43 (->4f63)
wrong data byte #53 should be 0x35 but was 0x15
```

同一个包里 guest 返回的 ICMP checksum 仍按原 payload 计算；host 在 TAP 上看到的
payload 已经从 `0x35` 变为 `0x15`，所以 checksum 变错。这说明数据是在 guest
协议栈算完 checksum 之后、host TAP 收包之前被破坏，范围收敛到 target NIC
输出到 FireSim switch 的硬件/bridge 路径，而不是 guest TCP/IP 栈。

## 与历史现象的关系

这次问题和以下历史记录属于同一类 target->host payload corruption：

```text
debug_records/20260430T162000Z.md
debug_records/20260502T223837Z.md
debug_records/20260503T032845Z.md
debug_records/20260503T051319Z.md
```

区别是：`agfi-0bd...` 是移除旧 payload-history OCL taps 后的 min-observability
bitstream。它能 boot 并连上 `gdbserver`，但 target->host payload 又回到稳定
清 bit 的形态。由此判断，之前某些宽 payload-history/snapshot 观测点很可能只是
偶然改变了综合后物理/数据通路形状，并非真正修复了数据稳定性。

## 本轮静态判断

最小需要修复的位置是 `NICTokenToBigTokenAdapter` 输出到 CPU-managed stream
`pcie_out` 之间的边界。原路径直接把组合出的 512-bit bigtoken 接到下游
`io.pcie_out`，既承担宽数据 fanout，又把 ready/valid 压力直接传回 token packer。

如果旧宽观测点能影响失败概率，而去掉后稳定复现 payload bit-clear，则下一轮不应
再依赖“观测点改变布局”的副作用；应在真实数据路径上加入显式寄存/队列边界。

## 已准备的下一轮硬件修复

当前本地源码已在 `NICTokenToBigTokenAdapter` 的 `pcie_out` 前加入显式
2-entry `Queue(UInt(512.W), 2)`：

```text
val pcieOutQ = Module(new Queue(UInt(512.W), 2))
io.pcie_out <> pcieOutQ.io.deq
```

并新增低宽度可综合观测：

```text
nicbig_pcie_out_enq_count
nicbig_output_queue_count
minobs_build_marker = 0x05030002
```

本地 `replace-rtl` 后的关键 SHA：
