## 静态关联

switch 侧 `BasePort` 用 `0xDEADBEEFDEADBEEF` 标记整轮无有效 packet；
该常量本身在 bigtoken header 的 valid/ready/last 位上会解码出若干
“有效 flit”。因此 `ShmemPort send` debug 中出现
`marker=0xdeadbeefdeadbeef valid_flits=3` 并不等价于真实 target packet。

SimpleNIC host driver 入口有专门逻辑：

```c++
const bool peer_empty_marker = peer_words[0] == EMPTY_SHMEM_ROUND_MARKER;
const uint32_t peer_valid_flits =
    peer_empty_marker ? 0 : count_valid_flits(...);
```

也就是说，只要 marker word 完整等于 `0xDEADBEEFDEADBEEF`，SimpleNIC 会把
该轮当作空轮，不会把 marker 当成 host->target payload 推给 FPGA。

这条证据把“switch debug 里 marker 看起来有 valid flits”降级为日志歧义，
还不能证明 TCP/RSP payload 被 marker 污染。

## 当前结论

本轮失败点比“NIC 完全不通”更靠后：

- guest Linux 已启动；
- IceNet/gdbserver listener 已出现；
- run host tap 侧有双向 packet 计数；
- GDB 本地连接到 SSH forward 后断开；
- SSH tunnel 明确报告到 `172.16.0.2:2345` 的 channel connect timeout。

因此当前 blocker 需要用 packet capture 钉死：

1. 如果 pcap 显示 run host 对 guest 只发 SYN/ARP、没有完成 TCP handshake，
   问题在 host tap/switch/SimpleNIC host->target 或 guest->host 回包路径。
2. 如果 TCP handshake 完成、guest `gdbserver` 后续发 RST/FIN，
   问题转向 guest `gdbserver` / RSP / 被调试进程。
3. 如果 pcap 显示 guest 正常回包但 SSH tunnel/GDB 仍断开，
   问题转向 SSH forward 或 host-side 调试脚本。

下一轮必须 fresh launch F2，在 `[gdbserver] phase=listening` 后先启动
run host `tcpdump -i tap0 -s 0 -w ... host 172.16.0.2 and port 2345`，
再用真实 GDB 作为第一条连接，失败后复制 pcap、uartlog、switchlog、expect
transcript，再终止 runfarm。
