## 本轮结论

### 1. `SimpleNICBridge` lockstep patch 没有解决当前 smoke 里的根问题

这是本轮最重要的结论。

因为这次已经不是旧 AGFI，而是新 AGFI 的真实 FPGA 验证，所以现在可以更有把握地说：

- 问题不只是 `SimpleNICBridge.scala` 这几行 host/target lockstep 条件缺失
- 或者说，这个 patch 至少不是当前问题的充分修复

### 2. 当前最小复现继续指向更下游/更外层的问题

在这条最小链路里，仍需要优先怀疑：

- `SimpleNIC` host driver 的 bulk 交换策略本身与当前 bridge/stream 节奏不匹配
- `CPUManagedStream` / `StreamEngine` 与 `SimpleNIC` host driver 的批量阈值交互存在结构性问题
- 或者 `SimpleNIC` target-side token 生产/消费仍有另外一处没有被这次 patch 覆盖的失衡点

### 3. 这轮 negative result 很有价值，因为它缩小了根因空间

现在已经可以排除一个先前很强的假设：

- “只要把 `SimpleNICBridge` 两端用 `tFire` 绑成 lockstep，这个最小 smoke 就会恢复”

这个假设被新 AGFI FPGA run 直接否定了。

## 下一步建议

下一步不应该继续在 `SimpleNICBridge.scala` 上做小修小补碰运气，而应该把重心转向：

1. 继续静态审计 `simplenic.cc` 的 bulk 语义与 `CPUManagedStream` 阈值语义之间是否存在结构性错配。
2. 评估是否需要在不改网络协议语义的前提下，做一个更低扰动的 host driver 验证版本：
   - 只增加 success-path 计数/摘要
   - 或降低 bulk `required_bytes` 做受控实验
3. 如果还要继续硬件侧验证，优先抓：
   - `to_cpu` 真正成功被 pull 的轮次
   - `from_cpu` 真正成功被 push 的轮次
   - `tFire`、`ntht_queue`、`htnt_queue` 的 occupancy / fire 关系

## 当前结论一句话版

- 新 AGFI `agfi-06fbafa631d829a13` 上，最小 `singlecore + NIC + gdbserver smoke` 仍然复现与旧 AGFI 基本同样的 `SimpleNIC` host-side token 失配；因此 `SimpleNICBridge` lockstep patch 单独不足以修复当前问题。
