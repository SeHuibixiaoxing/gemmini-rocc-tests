# old AGFI remote gdbserver 软件回归恢复

日期：2026-05-02T12:30:27Z

## 背景

用户指出：之前同一个 single-core NIC gdbserver smoke 已经完整通过，新的失败不能直接归因
为 NIC 硬件，应先对照 `debug_records` / `change_records` 把成功路径复原。

本轮复原目标是：

- 暂停 8 hardware breakpoint / watchpoint 路线；
- 只验证 software breakpoint remote gdbserver；
- 使用已经在 2026-05-01 通过过的 old AGFI：
  `agfi-0079cbbca617eca4e`；
- 不复用旧 F2，fresh launch / infrasetup / runworkload。

## 关键复原

`20260501T045108Z.md` 与 `20260501T023200Z.md` 说明 05-01 成功路径依赖：

- `+simplenic-empty-switch-poll-interval=1024`
- CPU-managed stream debug 默认关闭，避免 early boot / RSP 握手阶段被大量
  `CPU_STREAM DEBUG` 输出拖慢

05-02 失败现场中，old AGFI + emptydriver 虽然能进入 Linux / IceNet / gdbserver，
但 UART 出现大量 `CPU_STREAM DEBUG pull_blocked`，随后 interactive expect 在
`target remote` 后 240s 内没有等到 prompt。这个现象不是纯 NIC 不通，因为同一轮
guest `gdbserver.log` 显示：

```text
Remote debugging from host 172.16.0.1
Killing process(es): 116
```

即 GDB 的 TCP 连接已经到达 guest，失败点是 RSP 初始握手 / stop prompt 太慢，随后
expect 超时关闭连接，`gdbserver --once` 杀掉 inferior。

本轮将 runtime 显式补成：

```text
+cpu-managed-stream-debug=0
```

避免不同 driver bundle 的默认值差异再次改变回归语义。

- run host：`i-07e6564b739ab1e01` / `192.168.1.221`
- AGFI：`agfi-0079cbbca617eca4e`
- HWDB：`config_hwdb_f2_rocket_singlecore_nic_notrace_30mhz_agfi0079_emptydriver.yaml`

远端 `sim-run.sh` 确认包含：

```text
+simplenic-empty-switch-poll-interval=1024
+cpu-managed-stream-debug=0
```

UART 中没有再出现 `CPU_STREAM DEBUG` 刷屏。

## 验证结果

Guest 走到：

```text
Registered IceNet NIC 00:12:6d:00:00:02
Starting network: OK
[gdbserver] phase=prelaunch ... endpoint=172.16.0.2:2345 pid=0
[gdbserver] phase=listening ... endpoint=172.16.0.2:2345 pid=112
```

随后通过 SSH tunnel 做第一次真实 GDB 连接，不使用 `nc` / `telnet` / 端口扫描。

GDB 证据：

- `target remote :32355` 成功停在 `_start`
- `break main` 成功
- `break smoke_iteration_hook` 成功
- `break smoke_worker_heartbeat` 成功
- `continue` 命中 `main`
- `next` 成功推进一行
- `continue` 命中 worker 线程 `smoke_worker_heartbeat`
- `continue` 命中主线程 `smoke_iteration_hook`
- `info threads` 看到 5 个线程
- `thread apply all bt` 返回主线程与 4 个 worker 的调用栈
- `info registers pc sp ra a0 a1` 成功

临时 expect 脚本在随后执行：

```tcl
gdb_cmd "x/12i $pc"
```

时失败：

```text
can't read "pc": no such variable
```

这是 Tcl 脚本转义错误，应写成 `\$pc`。失败发生在多个核心 GDB 能力已经成功验证之后，
不是 NIC / gdbserver 失败。

Guest 后续进入：

```text
[gdbserver] phase=exit ...
Simulation complete.
*** PASSED *** after 45163345922 cycles
```

`runworkload` exit code 为 `0`。

## 修正

- `config_runtime_f2_rocket_singlecore_nic_gdbserver_smoke_notrace_relaxed_noprint_preserve_30mhz.yaml`
  显式加入 `+cpu-managed-stream-debug=0`。
- `run_remote_gdbserver_software_expect_smoke.sh` 默认不再注入静态 ARP / host ARP；
  只有显式设置环境变量时才做，避免回归路径偏离 05-01 成功路径。
- 临时 `remote_gdb_multibp.expect` 中 `$pc` 已转义为 `\$pc`。

## 结论

old AGFI 的 software-breakpoint remote gdbserver 路径已经恢复：

- 之前 05-02 的 `target remote` 超时不是 NIC 完全不通，而是回归环境偏离 05-01：
  CPU-managed stream debug 刷屏显著拖慢初始 RSP 握手；
- 显式关闭该 debug 后，真实 GDB 能 attach，能下多个软件断点，能跨线程命中，
  能读取多线程调用栈和寄存器；
- hardware breakpoint / watchpoint 路线仍暂停，不作为当前 pipeline-runtime 调试前提。

下一步按用户要求，把当前硬件改动对齐到 debug_records 记录的已知有效语义，构建新的
single-core NIC bitstream 做回归；单核回归通过后，再提交硬件相关改动并启动
`12p4c128sbus32cfg + DMA 非对齐优化 + NIC` bitstream 构建。
