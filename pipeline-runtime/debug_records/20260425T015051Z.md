### 2. `uartlog` 显示 guest 根本没有进入 Linux 侧 `gdbserver` 主逻辑

关键文件：

- `/home/ubuntu/chipyard/sims/firesim/deploy/results-workload/2026-04-25--01-48-12-rocket-singlecore-nic-gdbserver-smoke-f2-rocket-singlecore-nic-gdbserver-smoke/rocket-singlecore-nic-gdbserver-smoke0/uartlog`

   - `FireSim fingerprint: 0x46697265`

2. `to_cpu` stream 持续积压：
   - `CPU_STREAM DEBUG pull_blocked ... stream=SIMPLENICBRIDGEMODULE_0_to_cpu_stream ...`

- 所以 guest 连最早的 `gdbserver` 结果文件都没有机会创建。

### 3. 新增 debug regs 已经把失败点收敛到非常具体的握手条件

本轮最有价值的新证据是：

- `SIMPLENIC DEBUG REGS [tick_push_mismatch] queues htnt=10 ntht=0 t_fire=0 t_fire_blocked={to_host_valid:0 from_host_ready:1 ntht_enq_ready:0 htnt_deq_valid:0}`
- `SIMPLENIC DEBUG REGS [tick_push_mismatch] hostport to_host(v=1 r=0) from_host(v=1 r=0) target(in_v=0 out_v=0)`
- `SIMPLENIC DEBUG REGS [tick_push_mismatch] adapters htnt(v=1 r=0) ntht(v=0 r=1) pcie_in(v=1 r=0) pcie_out(v=0 r=1) loop_iter=5 special_counter=2`
- `SIMPLENIC DEBUG REGS [tick_push_mismatch] counts t_fire=6415250 htnt_enq=6415260 htnt_deq=6415250 ntht_enq=6415250 ntht_deq=6415250 pcie_in=916465 pcie_out=916464`

这些值对应的静态含义是：

- `t_fire=0` 不是因为 `from_host_ready` 不足，也不是因为 `htnt_deq_valid` 缺失；
- 真正挡住 `tFire` 的是：
  - `to_host_valid=0`
  - `ntht_enq_ready=0`
- `htnt_queue_count=10`，`ntht_queue_count=0`
  - 说明 `host->target` 这一侧没有积压；
  - 反而是 `target->host` 路径无法继续把 token 送进 `ntht_queue`
- `hostport from_host(v=1 r=0)` 与 `pcie_in(v=1 r=0)` 一致：
  - host 正在往 NIC 送数据；
  - 但桥接路径没有接收
- `adapter loop_iter=5 / special_counter=2`：
  - 失败时 7-beat bigtoken adapter 处在一个未收敛的组内位置，不是“完全空闲”的稳态
- 计数器关系：
  - `htnt_enq=6415260`
  - `htnt_deq=6415250`
  - 差值正好是 `10`，与 `htnt_queue_count=10` 一致
  - `ntht_enq=ntht_deq=6415250`，与 `ntht_queue_count=0` 一致
  - `pcie_in=916465`，`pcie_out=916464`
    - 两者只差 `1`
    - 说明失败不是长期累积的 PCIe 方向性漏流，而是最后一个 token 级别的阻塞点

## 本轮结论

### 1. 新观测面是有效的，已经把问题从“卡在 SimpleNIC”推进到“卡在 target->host 入口 ready”

这轮最重要的正向结果不是“run 成功”，而是：

- 新增 debug regs 成功工作；
- 它们没有造成“卡点漂移到完全不可解释”；
- 反而把 failure 收敛成一个非常具体的状态：
  - `ntht_queue` 不满但 `ntht_enq_ready=0`
  - `from_host_valid=1` 但 `from_host_ready=0`
  - `pcie_in_valid=1` 但 `pcie_in_ready=0`

因此下一步已经不该继续盲目加通用日志。

### 2. 当前最像的根因，不是 host bulk 阈值本身，而是 `target->host` 方向在 adapter / queue 边界出现 ready 关闭

从这轮数据看：

- host 已经在推；
- PCIe 输入侧也已经在送；
- `ntht_queue` 并没有满；
- 但 `ntht_enq_ready` 仍是 `0`

这意味着更应该优先怀疑：

- `NICTokenToBigTokenAdapter` 的组包状态机；
- `ntht` enqueue 条件与 adapter `valid`/`ready` 的组合逻辑；
- 或 `target.out` / `target.in` 与 hostport 的方向连接中存在某个 “最后 1 token” 的闭锁条件。

### 3. 这轮 smoke 没有证明 gdbserver/NIC 正常工作

必须明确：

- 这次 `manager exit code=0` 只说明 FireSim 流程把一次失败 run 收尾了；
- **并不说明 guest 内的 `gdbserver` 成功起起来。**

真实结果是：

- `gdbserver.info` / `gdbserver.log` 不存在；
- `uartlog` 在 NIC host-side mismatch 处以 `COMMAND_EXIT_CODE="1"` 结束。
