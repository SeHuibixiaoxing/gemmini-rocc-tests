## 本轮静态结论

- 当前主线卡点仍不能强说“早于 `page29 before_v2p`”，因为现有 page-level breadcrumb 使用 `token_id=0`，而：
  - breadcrumb 是哈希槽表，不是时间序队列
  - 槽 key 不含 `phase`
  - 槽 key 也不含 alias `target_seq`
  - `page29/token0` 恰好命中当前歧义最重的 `slot14`
- 因而如果继续依赖 `page29/token0 -> slot14` 这条路径，只会不断重复“可能没到 page29，也可能到了但证据被 torn/collision 污染”的旧结论。

## 为什么本轮 probe 选 direct path

- 静态审计已经说明，`page28 after_accounting -> page29 before_v2p` 之间真正剩下的 direct-path 走廊非常短：
  - 下一页的地址/长度重算
  - `dma_trigger_export_host(\"pset\", ...)`
  - `dma_chunk_needs_bounce(...)`
- 对当前 `page29`：
  - `src=0x40006000`
  - `dst=0x103b31800`
  - `chunk=0x400`
  - 静态上应走 direct path，不应进入 bounce path
- 所以最有价值的新观测点，就是放在：
  - 已经完成 `pset`
  - 已经判定 `dma_chunk_needs_bounce(...) == false`
  - 但还没进入 `before_v2p`
  这一点上
- 一旦下一轮看见这条新 breadcrumb，就可以直接回答：
  程序已经进入 `page29` 的 direct path，而且卡点不可能再在
  `page28 after_accounting -> pset/bounce判定`
  这一小段里。

## 为什么这次 token 能避开旧歧义

- `copy_tensor_pages_to_model_aliases()` 原本已经维护了去重后的 alias target 顺序 `target_seq`
- 我重新核对了 `bertmini/model.layers.yaml` 中 `tensor_id=2` 的所有 alias 目标，当前只存在两个 unique 目标：
  - `target_seq=0` -> `address` -> `0x20400`
  - `target_seq=1` -> `address2` -> `0x842400`
- 本轮没有修改 page-level breadcrumb 的 `token_id=0` 语义，而是只给新的 direct-path probe 使用：
  - `token_id = target_seq + 1`
- 这样做的含义是：
  - `0` 仍保留给原来的 page-level notes
  - alias target 0 / 1 分别落在 `token_id=1 / 2`
  - 对当前 `segment=0, stage=0, subbatch=3, tensor=2, manager=0, page=29`
    的哈希结果，静态计算为：
    - `target_seq=0` -> `token=1` -> `slot25`
    - `target_seq=1` -> `token=2` -> `slot39`
- 所以这条新 probe 不再复用 `slot14` 等价类。
