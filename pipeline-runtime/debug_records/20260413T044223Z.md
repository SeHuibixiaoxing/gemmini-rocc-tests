## 分析

### 1. 当前 run 已推进到 `subbatch=3` 前的 build 阶段

- `guest-checkpoint-log.txt` 明确显示：
  - `subbatch=0` 到 `subbatch=2` 都已经到达 `after-build-stage-task`
  - 最新一轮已经到：
    `worker stage=0 checkpoint=before-build-stage-task subbatch=3`
- 因而 `worker stage=0 subbatch=2 done` 之后的 `rr-acquire`，
  不是原先 export-retire 卡点复现，而是后续 build / 固定张量装载路径上的 `rr-acquire`

### 2. `segment=0 stage=0` 的固定张量每个 subbatch 都会重新装载

- 从 `pipeline_mapping...ours2.yaml` 可见：
  - `fixTensorDramBypassIdList: [1000000, 1000001]`
  - `tensorUseLazyFetch: [0, 0, 0, 0]`
  - `localSpmPageCountList: [1, 64, 64, 64]`
  - 其中固定张量占用：
    - `1000000 -> 1` 页
    - `1000001 -> 64` 页
- 这意味着每一轮 `build_stage_task_desc -> stage_prepare_exec_views`
  都会重新触发固定张量 DMA 装载，而不是一次装载后复用

### 3. host watchdog 当前可能把“只在 checkpoint.log 中前进”的运行误判成死锁

- `scripts/firesim-prt-host-watchdog.sh` 当前只把这些文件的 size 增长视作前进：
  - `uartlog`
  - `guest_log`
  - `guest_sparse_log`
  - `guest_status`
  - 若干 `runner stage` 文件
- 它没有把：
  - `guest_checkpoint_log`
  的增长计入 progress
- 但当前 `subbatch=3` 阶段的主要新活动，
  恰好集中在 checkpoint 路径与固定张量 DMA 路径
- 因此当前 `04:27 UTC` 这轮：
  - 既有可能是真冻结
  - 也有可能是 sparse 主日志暂时不增长，而 watchdog 误判为 idle timeout
