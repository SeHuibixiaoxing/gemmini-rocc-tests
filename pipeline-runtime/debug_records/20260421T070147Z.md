## 核心证据

### 1. `gdbserver` 接入本身是成功的

`uartlog` 中出现：

- `running /etc/init.d/S99run`
- `[gdbserver] phase=prelaunch method=ours2 guest_ipv4=unknown endpoint=unknown:2345 pid=0`
- `[gdbserver] phase=listening method=ours2 guest_ipv4=unknown endpoint=unknown:2345 pid=207`

从运行中根镜像直接抽取的 guest 文件：

- `/root/pipeline-runtime-debug/bertmini-batch8.gdbserver.log`
  内容为：
  - `Process /root/rerocc-linux-tests/pipeline-runtime/rerocc_pipeline_runtime-linux created; pid = 221`
  - `Listening on port 2345`
- `/root/pipeline-runtime-debug/bertmini-batch8.gdbserver.info`
  内容为：
  - `phase=inferior`
  - `pid=221`
  - `gdbserver_pid=207`

### 2. inferior 的确被 `gdbserver` 冻住了，不是程序自己卡死

从 `/root/pipeline-runtime-debug/bertmini-batch8.runner-proc.stage` 抽取到：

- `gdbserver` wrapper：
  - `pid=207`
  - `cmdline=/usr/bin/gdbserver --once 0.0.0.0:2345 ...`
- runtime inferior：
  - `pid=221`
  - `Name: rerocc_pipeline`
  - `State: t (tracing stop)`
  - `TracerPid: 207`
  - `wchan=ptrace_stop.part.0`

这条证据非常关键：
当前 run 之所以停住，不是 `pipeline-runtime` 业务逻辑再次卡死，
而是 `gdbserver` 按预期把用户程序停在“等待外部调试器连接”的阶段。

### 3. `guest_ipv4=unknown` 不是“guest 没配 IP”，而是 runner 探测路径过弱

guest 根镜像内的 `/etc/init.d/S40network` 明确写着：

- 拉起 `eth0`
- 读取 `/sys/class/net/eth0/address`
- 按 FireSim 规则配置：
  `172.16.$machigh.$maclow/16`

本轮 `sim-run.sh` 使用的 MAC 是：

- `+macaddr0=00:12:6D:00:00:02`

因此 guest 预期 IP 就是：

- `172.16.0.2`

但 runner 原实现只用裸 `ip` / `ifconfig`，
而 Buildroot `S99run` 环境下 `PATH` 未必包含 `/sbin`，
所以 announcement 才会错误打印成 `unknown`。

### 4. 当前主线 `no_net_config` 下，host 侧 live attach 仍然不成立

FireSim 本地文档写明：

- `topology: no_net_config`
  是 `independent simulations, without a network simulation`

本轮实测：

- run host 初始没有 `tap0`
- 按文档手动补建：
  - `tap0`
  - `172.16.0.1/16`
  - MAC `8e:6b:35:04:00:00`
- 但 `tap0` 状态仍是：
  - `NO-CARRIER`
  - `state DOWN`
- 之后从 run host 探测：
  - `172.16.0.2:2345` 超时

因此可以收敛出一个清晰结论：

- guest 内部 `gdbserver` 能启动
- guest 内部 inferior 能被成功冻结
- 但当前 `pairdummy` 主线使用的 `topology: no_net_config`
  没有提供 host 可达 guest 的有效网络链路
- 所以不能完成 host `target remote`

## 本轮结论

### 结论 1

`gdbserver` 路线在 guest 内部已经跑通，不需要再怀疑：

- `kfrag` 是否生效
- rootfs 里是否有 `/usr/bin/gdbserver`
- wrapper / runner 是否真的进入了 `gdbserver` 路径

这些都已经被本轮 FPGA 实证确认。

### 结论 2

当前阻塞点已经不是 `pipeline-runtime` 程序本身，
而是 “当前 FireSim 主线拓扑无法给 `gdbserver` 提供 host 可达的 TCP 通路”。

### 结论 3

这也解释了为什么本轮不应该继续空等：
只要外部没有真正 attach，
inferior 就会一直保持 `ptrace stop`，
`runworkload` 不会自然收敛出更多业务信息。

1. 不要再把“当前主线能不能 host attach gdbserver”当成软件侧悬而未决问题；
