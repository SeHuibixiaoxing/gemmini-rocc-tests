## F2 静态结论

上一轮 F2 现场已经证明：

- Linux / gdbserver 已进入用户态；
- host C++ / switch 已拿到 host->target 包；
- `simplenic_t::push(..., 64, 0)` 返回 `64`；
- RTL 侧 `pcie_in` / `bigtoken_accept_count` 增长；
- 但 `bigtoken_payload_emit_count=0`，`from_host_payload_capture_count64=0`。

这次继续静态排查后，关键链路已经从“怀疑”收敛为确定的 F2 顶层接线错误：

- `F2Config` 将 `CPUManagedAXI4Key.dataBits` 设为 `64`。
- 最新生成 `F1Shim.io_pcis_w_bits_data/strb/r_bits_data` 是 `64/8/64` bit。
- F2 shell PCIS 和 `axi_clock_converter_512_wide` 仍是 `512-bit wdata` / `64-bit wstrb`。
- 原 F2 顶层直接把 512-bit clock-converter 输出接到 64-bit generated F1Shim，造成隐式截断。
- 原 F2 顶层还把 `axi_clock_converter_512_wide` 的 shell-side `awready/wready/bvalid/arready/rdata/rvalid` 等输出悬空，而不是接回 shell。

F2 目录已有的 `axi_dwidth_converter_0` 不能直接复用到 PCIS 下转换：

- 其 wrapper 参数是 `C_S_AXI_DATA_WIDTH=64`、`C_M_AXI_DATA_WIDTH=512`。
- 它是 DDR 路径使用的 64->512 upsizer，不是 shell PCIS 需要的 512->64 downsizer。

## 本轮硬件修复

修改文件：

```text
sims/firesim/platforms/f2/aws-fpga-firesim-f2/hdk/cl/developer_designs/cl_firesim/design/cl_firesim.sv
```

新增 `firesim_pcis_width_bridge_512_to_64`：

- wide side：接 `axi_clock_converter_512_wide` 的 512-bit PCIS 输出。
- narrow side：接 generated `F1Shim.io_pcis` 的 64-bit CPU-managed AXI4。
- 写路径：
  - 支持 `fpga_pci_poke64()` 这类单 lane 512-bit shell 事务；
  - 也支持整 64B 512-bit 写事务；
  - 对每个有效 8B lane 生成一个 64-bit、`len=0`、`size=3` 的单拍 AXI 写给 F1Shim；
  - 聚合所有 narrow B response 后再向 wide/shell 侧返回一个 B response。
- 读路径：
  - 对 64-bit read，把返回数据放回 wide beat 的对应 lane；
  - 对 512-bit read，连续发 8 个 64-bit narrow read 并重新拼成一个 512-bit R beat。
- 下游 AW/W/AR 与 B/R ready 会保持到同周期可完成，以适配当前 `CPUManagedStreamEngine` 对单拍 AW/W/B-ready 同周期的实现假设。

```text

```

每一级是否 fire、是否选错 lane、是否出现 partial strobe 或 response error。

## Metasim 判断

local metasim 已证明 host->target 能进入 RTL 和 baremetal：

- `payload_emit` 增长；
- baremetal `pingd` 能打印收到 ARP/IPv4 包；
- 卡点是 target->host ARP reply 没回到 host `tap0`。

这与 F2 当前失败不同：

- F2 是 host C++ push 成功后，RTL `payload_emit=0`；
- metasim 是 host->target payload 已经进 target，target->host 出口到 tap 未通。

因此 metasim 当前卡点更像 local switch/tap 出口链路问题，不是这轮 F2 host->target PCIS 宽度桥 blocker。下一步先用修复后的 F2 bitstream 验证 NIC 主线。
