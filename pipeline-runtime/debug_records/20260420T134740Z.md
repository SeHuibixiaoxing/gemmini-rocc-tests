## 新观察

### 1. `pipeline-runtime` 内部 raw `rr_release()` 只剩包装层这一处

`rg` 结果显示，
`pipeline-runtime` 源码下真正的 raw `rr_release(`
只出现在：

- `/home/ubuntu/chipyard/generators/gemmini/software/gemmini-rocc-tests/pipeline-runtime/src/prt_rerocc.c`

其余 DMA / Gemmini / SPM-xlate release 路径都不是直接调 raw helper，
而是统一经由：

- `prt_rr_release_scope()`

### 2. 之前担心的 release-return 短窗口，
在 `pipeline-runtime` 包装层里已经被封住

当前
`prt_rr_release_scope()`
的真实顺序是：

1. `rr_release(scope->cfg_id)`
2. breadcrumb `RR_RELEASE_AFTER_CSR_WRITE`
3. `rr_read_csr(CSR_RRCFG0 + scope->cfg_id)`
4. `scope->valid = 0`
5. breadcrumb `RR_RELEASE_END`

这意味着：

- raw `rr_release()` 本身仍然只是“发起 release”
- 但 `pipeline-runtime` 不会在 release CSR 写完后立刻把 scope 视为可复用
- 它会等同 `cfg` 的 `RRCFG` 读回退休后，
  才让软件层继续把该 scope 当作已释放

### 3. 因而这轮不需要做 repo-wide 修补

仓库里其它 workload / test
仍有 raw `rr_release()` 调用，
但用户已经明确：

- 这轮“全局修复”只指 `pipeline-runtime`
- 如果 `pipeline-runtime` 软件栈没有再暴露其它窗口，
  可以先不修其它子树

结合本轮审计，
当前结论是：

- `pipeline-runtime` 范围内，
  release 短窗口已经在包装层被统一修复
- 本轮需要补的是
  **把这个 invariant 写清楚**
  ，避免后续静态分析又把 raw helper 语义
  直接套到 `pipeline-runtime` 包装层上

## 本轮结论

- 对 `pipeline-runtime` 而言，
  “release 后 scope 过早失效/重用”的主风险已经不是当前未修问题。
- 当前更合理的收尾动作不是继续改 release 行为，
  而是：
  1. 在 `prt_rr_release_scope()` 附近补明确注释
  2. 在语义文档里区分
     raw `rr_release()` 与 `pipeline-runtime` release wrapper
  3. 新增一轮 debug/change 记录并重建分类索引
