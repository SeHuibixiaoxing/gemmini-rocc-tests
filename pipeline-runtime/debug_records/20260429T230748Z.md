# 20260429T230748Z - NIC gdbserver smoke: switch0 segfault root cause

类别：`gdbserver` / NIC / FireSim switch / host-target networking

本轮对象：

- Runtime config: `sims/firesim/deploy/config_runtime_f2_rocket_singlecore_nic_gdbserver_smoke_notrace_relaxed_noprint_preserve_30mhz.yaml`
- HWDB: `sims/firesim/deploy/config_hwdb_f2_rocket_singlecore_nic_notrace_30mhz.yaml`
- AGFI: `agfi-019e0b22099a5214b`
- 失败现场包：`tmp/firesim-aws-f2/nic-scenes/nic-scene-20260429-230105.tar.gz`

## 直接证据

1. 远端 F2 shell 没有 AWS shell / PCIS 超时：
   - `fpga_describe_slot0_M.txt` 中 `dma-pcis-timeout=0`
   - `pcim-*error=0`

2. target 已经越过 Linux boot，并进入 gdbserver workload：
   - `uartlog` 中有 `Starting network: OK`
   - `uartlog` 中有 `running /etc/init.d/S99run`
   - `uartlog` 中有 `[gdbserver] phase=prelaunch net_dev=eth0 guest_ipv4=172.16.0.2 endpoint=172.16.0.2:2345`

3. target 已经向 host 方向发出 ARP reply，问题不再是“target 没回包”：
   - `uartlog` 记录 `SIMPLENIC TOKEN DEBUG [target_to_switch_pull] event=3`
   - event 3 的首个 flit 是 `0x2bae9fe4d172004c`
   - 按 switch 的 little-endian + `NET_IP_ALIGN=2` 布局解析，该 flit 的以太网目的 MAC 是 `72:d1:e4:9f:ae:2b`，即 host TAP MAC；源 MAC 是 target 的 `00:12:6d:00:00:02`
   - `switchlog` 随后记录同一个包进入 switch：`ShmemPort recv port=0 event=3`，`BasePort input_packet port=0 event=3 flits=6`

4. `switch0` 在处理这个 ARP reply 后崩溃：
   - `switchlog` 停在 `BasePort input_packet port=0 event=3 ...`
   - event 1/2 的 IPv6 multicast 包都有后续 `SSHPort output_buf` 和 `SSHPort tap_send`
   - event 3 没有对应的 `SSHPort output_buf/tap_send`
   - `switchlog` 末尾：`COMMAND_EXIT_CODE="139"`
   - `dmesg_T.txt`：`switch0[3463]: segfault ... in switch0[...]`

5. segfault 的代码位置已经钉死：
   - `addr2line -Cfpie switch0 0x469e`
   - 结果指向 `target-design/switch/flit.h:78`
   - 该行是 `sendport = mac2port[sendport];`
   - 调用点是 `target-design/switch/switch.cc:182`

## 根因

当前生成的 switch config 是：

```c
#define NUMPORTS 2
#define NUMDOWNLINKS 2
#define NUMUPLINKS 0
uint16_t mac2port[3] {1, 1, 0};
```

这个 config 有两层确定错误：

1. root switch 新增的 `SSHPort` 被算进了 `NUMDOWNLINKS`，但它在语义上是“host 网络方向”的逻辑 uplink。FireSim switch 原逻辑使用 `NUMDOWNLINKS` 作为“任意 uplink”的哨兵端口号；把 `SSHPort` 算成 downlink 后，哨兵语义被破坏。

2. `mac2port` 表只覆盖 FireSim target 分配出来的 MAC suffix。host TAP MAC 是宿主 Linux 动态生成的普通 MAC，本轮是 `72:d1:e4:9f:ae:2b`，suffix 为 `0xae2b`。target 回 ARP 时目的 MAC 就是这个 host TAP MAC，因此 switch 走到 `mac2port[0xae2b]`，而表长只有 3，直接越界读并 segfault。

这两个事实解释了完整链路：

- host ARP request 能进入 target；
- target ARP reply 能回到 switch；
- switch 在对 host TAP MAC 做端口查表时崩溃；
- `tap0` 随 `switch0` 退出而消失，后续 host 无法 ping / gdb 连接 target。

## 本轮推进情况

这是比上一轮更深的卡点：

- 已解决旧卡点：F2 `dma-pcis-timeout` 和 target 无回包问题。
- 新前沿：target->switch 的 ARP reply 已经出现，失败发生在 FireSim host-side switch 把该回包转发到 `SSHPort/tap0` 前。

## 处理方向

本轮问题是 host-side FireSim switch C++ / Python config 逻辑问题，不需要新硬件 bitstream。

修复策略：

- 让 root `SSHPort` 作为逻辑 uplink 计数：`NUMDOWNLINKS=真实 target/downlink 数量`，`NUMUPLINKS=真实 uplink 数量 + root SSHPort`
- 生成 `MAC2PORT_SIZE`
- `get_port_from_flit()` 对 `sendport >= MAC2PORT_SIZE` 做边界保护：
  - 有 uplink 时走 `NUMDOWNLINKS` 这个“first uplink”哨兵
  - 无 uplink 时按 unknown unicast flood，不再崩溃
- 传入真实 `sender` 端口用于 debug 输出

预期下一轮不需要 `buildbitstream`，只需要重新 `launchrunfarm -> infrasetup -> runworkload`，让新的 switch binary 被构建并部署到 F2。
