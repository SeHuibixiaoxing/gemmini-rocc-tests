# single-core NIC 新比特流回归失败的静态复核

日期：2026-05-02T23:33:11Z

## 结论

本轮静态复核没有发现 `NICTokenToBigTokenAdapter` partial flush 是 05-02 新回归的证据：
旧可工作 AGFI `agfi-0079cbbca617eca4e` 的生成 RTL 也包含
`flushThisToken = slotIsFull | io_ntht_valid & io_ntht_bits_data_out_last`。

真正和历史通过版本不一致的点有两个：

1. 05-02 “硬件归位”把 04-30 18:47 可工作比特流里存在的 target->host payload-heavy
   OCL snapshot 移除了。新 AGFI `agfi-032d10150efc1d4ec` 失败时，坏 flit 已经在
   `target_to_switch_pull` / `ShmemPort recv_flit` 出现，但由于这些 snapshot 被删，无法继续区分
   `hPort.nicOut`、`NICTokenToBigTokenAdapter`、CPU stream/PCIS read 哪一级首次损坏。
2. F2 PCIS 512->64 bridge 的写通道 `s_axi_wready` 和旧可工作 RTL 不一致。旧版只在已有/同时收到
   AW 时接收 W；新版允许 W-before-AW。该差异更偏 host->target/OCL 写通道，不直接解释
   target->host read corruption，但它是明确的 old/new 功能语义差异，回退更安全。

因此本轮修复策略是：把 PCIS write ready 语义恢复成旧版，同时恢复并扩展 target->host
payload snapshot。这样下一颗单核 NIC 比特流既回到历史通过版本的可观测/扰动形态，也能在仍失败时一次性钉死坏 flit 的首个边界。

## 本轮静态对照

对照 04-30 18:47 可工作生成物和 05-02 16:49 失败生成物：

- `CPUManagedStreamEngine` 没有功能差异；
- `StreamWidthAdapter` 没有功能差异；
- `NICTokenToBigTokenAdapter` 仍保留同样的 `last` partial flush 语义；
- 05-02 失败生成物缺少 04-30 18:47 通过生成物中的：
  - `bigtoken_current_slot_data_*`
  - `bigtoken_last_latched_word*_*`
  - `nicbig_last_pcie_out_word*_*`
  - `to_host_hist_data*_*`
  - `to_host_hist_meta*`
- F2 PCIS bridge 唯一明确功能差异是：
  - 旧：`s_axi_wready = ... && (wr_aw_active || wr_aw_fire)`
  - 新：`s_axi_wready = ... && !wr_wbuf_valid`
