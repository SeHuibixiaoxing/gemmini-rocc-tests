## 修改内容

- 给 `prt_rr_release_scope()` 增加 release 后对同一 `RRCFGx` 的读回等待：
  - 先发 `rr_release(cfg)`
  - 记录 `RR_RELEASE_AFTER_CSR_WRITE`
  - 再 `rr_read_csr(CSR_RRCFG0 + cfg)`
  - 最后才把 scope 置 invalid 并记 `RR_RELEASE_END`
- 新增 breadcrumb phase：
  `PRT_BREADCRUMB_PHASE_RR_RELEASE_AFTER_CSR_WRITE = 309`
  用来区分：
  - CSR 写已经发出
  - 但 release ack / readback 还没回来
- 在 `observability.md` 补充
  “release + readback sentinel”
  作为 `rr_release` 类问题的推荐低扰动定位法。

## 原因

- 这轮静态排查确认：
  当前风险不是“release 之前一定有 bug”，
  而是 `rr_release()` helper 自身缺少 acquire 那样的读回等待，
  导致 software return 与 hardware handshake completion 之间出现协议空窗。
- 若直接继续跑旧逻辑，
  frontiers 仍会在 `release-end` / `restore-begin` / 更后 CSR 边界之间漂移，
  不利于判断到底卡在 release ack 还是卡在后继 CSR。
- ReRoCC client RTL tie-off 风险先记录为后续审计项，
  本轮不混入硬件改动。

## 风险 / 后续

- `prt_rr_release_scope()` 现在语义更接近 blocking release；
  若底层 release ack 真回不来，
  frontier 会前移并稳定在 `release-after-csr-write`
  到 `release-end` 之间。
- 这是本轮想要的效果：
  让问题固定到更接近真实 culprit 的 CSR 指令。
- 下一轮若用户批准本机 metasim，
  优先验证新增 phase `309 -> 308` 是否闭环，
  再决定是否需要额外 baremetal repro 或更深硬件侧信号抓取。
