## Motivation
- The detached FireSim manager environment was already fixed to preserve `PIPELINE_RUNTIME_DEBUG_TRIGGER_*`, but that alone was still insufficient.
- Root cause of the latest invalid rerun:
  - the guest runtime process reads trigger env from guest `/firemarshal.env`
  - the active guest image still carried the baseline control `firemarshal.env`
  - therefore the rerun advanced on the control path and `guest_trigger` stayed `0`
- The workflow needed an explicit step that materializes the host-side trigger overlay into the FireMarshal image before `infrasetup` and `runworkload`.

## Change
- Added `render_pairdummy_guest_env.sh`:
  - start from the checked-in baseline guest env
  - apply only the allowed temporary overlay family:
    - `PIPELINE_RUNTIME_DEBUG_TRIGGER_*`
  - write an effective guest env file under:
    - `tmp/pipeline-runtime-effective-guest-env/`
- Added `apply_guest_env_to_image.sh`:
  - replace `/firemarshal.env` inside the ext4 FireMarshal image with `debugfs`
  - re-read the file from the image
  - verify byte-for-byte equality with the rendered effective guest env
- Updated `pairdummy_sbus128_workflow.sh`:
  - `image-closure` now:
    - renders effective guest env
    - patches local image `/firemarshal.env`
    - runs local freshness against that effective env
  - `infrasetup` also patches and re-verifies the local image before pushing artifacts
  - `local-freshness`, `remote-freshness`, and `run` now consistently verify against the effective guest env path
- Updated `verify_pairdummy_firemarshal_image_freshness.sh`:
  - allow the expected guest env source to be overridden with:
    - `PAIRDUMMY_GUEST_ENV_OVERRIDE_PATH`
- Updated the workflow document to reflect:
  - fixed profile `v20`
  - effective guest env rendering
  - image patching requirement for trigger reruns

## Intended Effect
- A trigger-gated rerun now has a complete propagation chain:
  - shell overlay
  - tmux command env
  - rendered effective guest env
  - guest image `/firemarshal.env`
  - runtime process environment inside the guest
- This removes the previous false-negative state where host-side logs showed trigger env exported but guest-side runtime still executed with `DEBUG_TRIGGER_ENABLE=0`.
