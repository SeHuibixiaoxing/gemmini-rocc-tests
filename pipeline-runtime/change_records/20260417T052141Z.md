# 2026-04-17T05:21:41Z 修改记录

## 本轮目标

- 让 `triage_prt_capture.py` 能把当前最新 blocker
  `spm-xlate-release mgr=5 cfg=15 phase=restore-begin`
  正确识别为权威 frontier，
  并输出符合 workflow 约束的 `spm-xlate` trigger env。

## 修改文件

- `scripts/triage_prt_capture.py`

## 修改原因

- 当前代码里 `spm-xlate` trigger family 已经存在于
  `src/prt_rerocc.c` / `src/prt_trigger_log.c`，
  但 triage 工具还只会优先跟随 breadcrumb 的
  `rr_release_end`。
- 这会导致：
  - `frontier` 被错误表述成 `rr/rr_release_end`
  - `recommended_next_probe` 错误指向 `rr`
  - `--emit-trigger-env` 继续输出 `PIPELINE_RUNTIME_DEBUG_TRIGGER_KIND=rr`
- 由于 workflow 文档要求 trigger overlay 应来自
  `triage_prt_capture.py --emit-trigger-env`，
  这个工具层偏差会直接阻塞下一轮符合 SOP 的 rerun。

## 语义影响

- 新增 sparse 解析：
  - `spm-xlate-release mgr=<mgr> cfg=<cfg> phase=<phase>`
- 当 sparse tail 已经推进到 `spm-xlate-release` 时：
  - `frontier` 会优先输出 `spm-xlate-release mgr=<mgr> cfg=<cfg> phase=<phase>`
  - `verdict` 会指向 `prt_spm_xlate_release_scope()` 的静态阅读
  - `recommended_next_probe` 会改成 `static-read-spm-xlate-restore-then-sx-trigger`
  - `--emit-trigger-env` 会输出：
    - `PIPELINE_RUNTIME_DEBUG_TRIGGER_KIND=spm-xlate`
    - `PIPELINE_RUNTIME_DEBUG_TRIGGER_MANAGER=<mgr>`
    - `PIPELINE_RUNTIME_DEBUG_TRIGGER_TOKEN=<cfg>`
    - 并复用 breadcrumb 上的 `segment/stage/subbatch`
