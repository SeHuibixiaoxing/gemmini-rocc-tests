# 2026-04-17 11:10:41 UTC

## Change Summary

本轮修改分成两部分：

### 1. 修复 `tracerv-inst` 构建开关在 tmux wrapper 层丢失的问题

更新：

- `scripts/firemarshal-tmux-run.sh`

新增环境变量转发：

- `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS`

这样 `pairdummy_sbus128_tracerv_inst_workflow.sh` 导出的开关才能真正穿过：

- workflow shell
- `firemarshal-tmux-run.sh`
- FireMarshal
- `host-init.sh`
- `make`

最终进入 `rerocc_pipeline_runtime-linux` 的实际编译。

### 2. 给 local freshness 增加 TracerV marker 的字节级验真

更新：

- `pipeline-runtime/scripts/verify_pairdummy_firemarshal_image_freshness.sh`

新增检查：

- 当 `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS=1` 时，
  - 本地 `rerocc_pipeline_runtime-linux` 必须同时包含：
    - `0x00008013`
    - `0x00010013`
  - image 中提取出的 runtime binary 也必须同时包含同样两条字节序列。

这样可以直接防止再次出现：

- 源码里有 marker
- 但最终构建产物和镜像里没有 marker

这种“看起来已经改了，实际上没进产物”的问题。

## Why

本轮静态审计先发现：

- `prt_runtime.c` 中虽然已经加入 worker-local marker；
- 但之前那版 `tracerv-inst` build 的实际 FireMarshal tmux command 脚本里，没有导出
  `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS`
- 于是 `host-init.sh` 实际编译时拿到的是默认值 `0`
- 导致最终 runtime binary 根本没有 marker 指令。

这不是 runtime 逻辑问题，而是 build orchestration 问题。

## Verification

修复后重新执行 `image-closure`，得到直接证据：

- FireMarshal build log 中打印：
  `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS=1`
- local freshness 通过：
  - `runtime-binary-src tracerv worker markers expected=1 start=1 end=1`
  - `runtime-binary-img tracerv worker markers expected=1 start=1 end=1`
- remote freshness 也通过，说明下发到 run host 的 image 与本地一致。

## Scope

- 只改了 FireMarshal tmux wrapper 的环境变量转发和 isolated workflow 的 freshness 校验。
- 没改 FireSim/TracerV 硬件实现。
- 没改 canonical baseline workload 的默认行为。
