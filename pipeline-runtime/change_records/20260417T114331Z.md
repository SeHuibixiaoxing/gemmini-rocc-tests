## 修改内容

- 给 `TracerV` host driver 新增 plusarg：
  - `+trace-min-batch=<beats>`
- 默认行为保持不变：
  - 未传 plusarg 时仍使用 `stream_depth`
- `tick()` 现在按可配置的最小 batch 拉流，而不是硬编码 `stream_depth`
- 在 isolated `tracerv-inst` runtime config 里设置：
  - `plusarg_passthrough: "+trace-min-batch=0"`
  使该 debug 变体在 run 过程中就能持续把 trace 从 stream 拉到 host 文件。

## 原因

- 当前 live `TRACEFILE-C*` / `fdinfo pos` 观察面对 “是否真的开始 trace” 没有判定力：
  - stream 拉流门槛太高
  - 文件还是 stdio 缓冲
  - manager 又经常在 run 结束前掉线
- 继续用现状判断，只会反复把“尚未拉流/刷盘”误记成 “trigger 没命中”。

## 验证

- 静态核对：
  - 新 plusarg 仅影响 host driver，不涉及 bitstream / target RTL
  - 默认路径不变，只有显式传入 `+trace-min-batch=` 才改变行为
- 配置核对：
  - 仅 isolated `tracerv-inst` runtime config 增加该 plusarg
- live 部署核对：
  - 已重新执行 `launch -> infrasetup -> remote-freshness -> run`
  - run host `192.168.1.78` 上的 `FireSim-f2` 二进制已包含：
    - `TracerV: Host pull minimum batch is %u beats (stream depth %d)`
  - live `/proc/<pid>/cmdline` 已确认本轮真实带上：
    - `+trace-min-batch=0`
    - 以及原有 `+trace-select=3/+trace-start/+trace-end`

## 风险 / 后续

- 风险：
  - 更频繁拉流会增加 host 侧 trace I/O 频率，可能带来性能下降，但不改变 target 语义。
- 后续：
  - 当前 live run 仍在进行，需继续等 guest 进入用户态再解释 `TRACEFILE==0`
  - 若 guest 已进入 runtime 而 trace 仍为 `0`，再继续查 MMIO 寄存器写值或 selector `3` compare
