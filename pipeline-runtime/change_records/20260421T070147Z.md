## 修改内容

### 1. 新增 gdbserver 专用 runtime YAML

新增：

- `config_runtime_f2_gemmini_rerocc_pairmanager_dummy16x16_4c12p12_sbus128_linux_bertmini_pipeline_runtime_batch8_fileonly_sync_gdbserver.yaml`

其 `workload.workload_name` 明确指向：

- `rerocc-lc-linux-coupleddma-bertmini-pipeline-runtime-batch8-fileonly-sync-pairdummy-gdbserver.json`

原因：

- 原先 workflow 只改了 `workload_json`
- 但 FireSim 真正使用的还是旧 runtime YAML
- 导致 `infrasetup/runworkload` 实际部署的仍是旧 `pairdummy` 镜像

### 2. 让 gdbserver workflow 显式绑定新 runtime YAML

在：

- `pairdummy_sbus128_gdbserver_workflow.sh`

中新增：

- `PAIRDUMMY_RUNTIME_CFG=..._gdbserver.yaml`

这样 workflow 的 `show / infrasetup / run`
不会再悄悄落回旧主线 runtime config。

### 3. 修正 `guest_ipv4` announcement 的环境依赖

在两个 runner 副本里都修了 `guest_ipv4_for_dev()`：

- 裸 `ip`
- `/sbin/ip`
- `/bin/ip`
- 裸 `ifconfig`
- `/sbin/ifconfig`
- `/bin/ifconfig`
- 最后回退到读取 `/sys/class/net/<dev>/address`，
  按 FireSim 默认规则推导 `172.16.<machigh>.<maclow>`

原因：

- Buildroot `S99run` 的 `PATH` 未必包含 `/sbin`
- 实测 guest 已经把 `eth0` 配成 `172.16.0.2`
  但 announcement 仍打印 `guest_ipv4=unknown`
- 这个问题会误导后续调试，把“探测脚本弱”误判成“网络没起来”

### 4. 更新 gdbserver SOP

在 SOP 中补充了：

- 当前 `pairdummy` 主线仍是 `topology: no_net_config`
- FireSim 文档对它的定义是 “without a network simulation”
- 本轮实测结果：
  - guest `gdbserver` 能启动
  - inferior 会进入 `ptrace stop`
  - run host 补建 `tap0` 后仍是 `NO-CARRIER`
  - `172.16.0.2:2345` 不可达

因此明确写入：

- 当前主线下 `gdbserver` 可以冻结 inferior 并留下 guest 侧状态文件
- 但不能直接完成 host `target remote`
