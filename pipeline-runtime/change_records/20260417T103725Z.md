## Change Summary

将 isolated `tracerv-inst` 调试路径从 shell 级 trigger 切换为 runtime worker 本地 trigger：

- 在 `prt_runtime.c` 的 `stage_worker_main()` 中加入编译期开关控制的：
  - worker-start trigger word：`0x00008013`
  - worker-end trigger word：`0x00010013`
- 使用原始 `.word` 指令，而不是汇编助记符，确保与 `TracerV` 的精确指令匹配完全一致。

同时做了最小范围的构建/工作流配套：

- `rerocc-linux-tests/Makefile`
  - 新增 `PIPELINE_RUNTIME_FIRESIM_TRACERV_WORKER_MARKERS`
  - 传入 `PRT_ENABLE_FIRESIM_TRACERV_WORKER_MARKERS`
- `rerocc-linux-tests-coupleddma/workload/host-init.sh`
  - 仅透传该编译开关
- `pairdummy_sbus128_tracerv_inst_workflow.sh`
  - 只对 isolated tracerv-inst workflow 默认导出该开关为 `1`
  - 更新说明文字
- `...pairdummy-tracerv-inst.json`
  - 去掉 shell 级 `firesim-start-trigger` / `firesim-end-trigger`
  - 只保留纯 runtime runner 命令

## Why

本轮 live 证据已经表明：

- guest 已经进入 wrapper、runner、`rerocc_pipeline_runtime-linux`
- runtime 已经推进到 YAML 解析与初始化内部
- 但 `TRACEFILE-C*` 仍全部为 `0`

因此 shell 级：

- `taskset -c 0 /usr/bin/firesim-start-trigger`

这条验证路径已经不足以提供可用的 `TracerV` 触发。

把 trigger 下沉到 `stage_worker_main()` 后，可以直接把触发点绑在：

- 真正执行 hot worker 的线程
- 且已经完成 `stage_bind_current_thread()` 之后的 hart

这比 shell / wrapper 级触发更接近实际卡点。

## Scope Control

- 只影响 isolated `pairdummy-tracerv-inst` 调试路径。
- canonical pairdummy baseline 不默认启用这个编译开关。
- 保持 `PIPELINE_RUNTIME_MLOCKALL_MODE=2` 不变。
- 没有改 FireSim/TracerV 硬件实现，只改 runtime 本地触发点与 isolated workflow。
