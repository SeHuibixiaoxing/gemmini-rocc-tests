  补上 `fill_pattern()` 前后的确定性 breadcrumb，
  避免把整段大体量软件预热区都隐藏在 `stage_progress=10` 之前。

## 修改内容

- 在 `cid == 0` 的预填充路径中新增三个 stage breadcrumb：
  - `2U`：开始 `fill_pattern(stage0_src, ...)`
  - `3U`：完成 `stage0_src` 填充
  - `4U`：完成 `stage1_src` 填充
- 保留原有：
  - `10U`：进入首次 barrier 前

## 修改原因

- 本轮 live TraceV + 反汇编已经证明：
  - hart0 长时间停在 `fill_pattern(stage0_src)` 的逐字节循环
  - hart1 长时间停在 `barrier_wait()` 自旋
- 现有 `stage_progress=10` 放在两次 `fill_pattern()` 之后，
  导致前置 `576KB` 初始化区完全不可见，
  外部容易误判为“卡点随机移动”或“boot 没起来”。

## 验证

- 只完成了静态修改，尚未执行新的 `infrasetup/runworkload`。
- 该修改不改变：
  - 数组大小
  - DMA 调度路径
  - barrier 逻辑
  - TracerV marker 逻辑

## 风险 / 后续

- 风险较低，本质上只是把已有 `stage_progress` 机制前移。
- 下一轮若获批重跑，
  可以首先验证：
  - core0 是否会依次经过 `2 -> 3 -> 4 -> 10`
  - core1 是否保持在 `10` 等待 barrier
- 若仍然太慢，
  下一层手段应是：
  - 为 metasim 单独缩小 `REROCC_EXPORT_STAGE0_BYTES / STAGE1_BYTES`
    或
  - 单独优化 `fill_pattern()` 写入粒度
