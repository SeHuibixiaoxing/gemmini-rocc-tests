## 先给一句话结论

当前最严谨的结论是：

- 这轮 `g6 bertmini` fresh rerun 中，**最后一个可靠、稳定的 breadcrumb（面包屑二进制记录）**停在
  `page28 dma_page_after_accounting`。
- 但这**还不能直接推出**
  “程序一定停在 `page29 before_v2p` 之前”。
- 原因是：
  用来观察 `page29` 的那一个 breadcrumb 槽位，本身带有
  **哈希碰撞**
  和
  **半写快照**
  两种歧义。
- 与此同时，静态读代码又表明：
  如果程序真的还没走到 `page29 before_v2p`，那它就会卡在一段很短、而且看起来并没有明显阻塞调用的代码里。

所以当前更准确的说法不是：

- “已经证明没到 `page29 before_v2p`”

而是：

- “最后一个稳定证据只到 `page28 after_accounting`；
  `page29` 当前证据不够干净；
  而且如果真没到 `page29 before_v2p`，静态上也不好解释为什么会卡在那之前。”

## 背景：我们在调什么

当前主线调试对象是：

- `pipeline-runtime`
- 负载是 `g6 bertmini`
- 当前盯的是
  `segment=0`
  `stage=0`
  `subbatch=3`
  `tensor=2`
  的一段导出路径

这里先解释几个词。

## 术语表

### 1. `segment`

可以把它理解成：

- pipeline runtime 里的一段“大步骤”
- 程序会先把一个 `segment` 跑完，再进入下一个 `segment`

也就是说，不同 `segment` 之间是**串行**的，不是并行的。

相关代码：

- `src/prt_runtime.c:4864`

### 2. `stage`

一个 `segment` 里面，会分成一个或多个更小的执行单元，叫 `stage`。

在当前实现里：

- 同一个 `segment` 的不同 `stage`
  可以由不同 worker 线程并行推进

但这次我们盯的是：

- `segment0`
- `stage0`

而 `segment0` 本身就是单 stage，所以这轮问题里不需要再把“多 stage 并行干扰”当成主角。

相关代码：

- `src/prt_stage_worker_multi_action.c:22`
- `src/prt_runtime.c:3921`

### 3. `subbatch`

可以把它理解成：

- 一个大批次数据被切成了若干个小批次

这里我们盯的是：

- 第 `3` 个小批次，也就是 `subbatch=3`

### 4. `tensor=2`

这是当前导出路径正在处理的一块张量数据的编号。

### 5. `export`

这里的 `export` 指的是：

- 把当前 stage 在本地存储里算出来的数据，
  复制到模型别名地址或主存地址去

相关入口代码：

- `src/prt_runtime.c:2463`
- `src/prt_runtime.c:2564`

### 6. `page`

这里的 `page` 不是操作系统页表那个抽象语义，而是：

- runtime 把待传输的数据切成固定大小页面后的“第几页”

当前我们看到的关键页号是：

- `page28`
- `page29`

### 7. `breadcrumb`

这是当前 runtime 里的一种**低扰动二进制调试记录**。

它的目的不是打印大段文本日志，而是：

- 在热点路径上写入少量结构化状态
- 让 host 之后把这个二进制文件抓出来解码

你可以把它理解成：

- “程序在若干关键边界处留下的面包屑”

### 8. `slot`

breadcrumb 文件里不是一条条顺序追加的文本日志，而是：

- 一个固定大小的槽位数组

每条 breadcrumb 会根据若干字段算出一个槽位编号，然后把数据写进去。

### 9. `seq`

每个 breadcrumb 槽位都有一个 `seq` 字段，用来表示这次写入是否完整。

当前写法是：

1. 先把 `seq` 加一
2. 再写正文内容
3. 最后再把 `seq` 加一

所以：

- `seq` 是偶数：
  说明这次写入完整结束了
- `seq` 是奇数：
  说明采样时正好拍到了“写到一半”的状态

### 10. `v2p`

这是 `virtual to physical` 的缩写。

在这里指的是：

- 把一个虚拟地址转换成物理地址

对应函数是：

- `prt_host_virt_to_phys()`

相关代码：

- `src/prt_dma.c:904`
- `src/prt_page_table.c:217`

### 11. `bounce path`

有些情况下，源地址和目的地址的对齐方式不合适，不能直接做大块拷贝，于是程序会先拷到一个中转缓冲区，再从中转缓冲区拷出去。

这条“先中转一下”的路径，就是这里说的 `bounce path`。

如果不需要中转，走的就是 `direct path`，也就是直接路径。

相关代码：

- `src/prt_dma.c:768`
- `src/prt_dma.c:1442`

## 这次最早的观察是什么

在这轮 run 里，我们先看到的稳定 breadcrumb 是：

- `kind=dma`
- `phase=dma_page_after_accounting`
- `segment=0`
- `global_stage=0`
- `local_stage=0`
- `subbatch=3`
- `tensor=2`
- `manager=0`
- `page=28`

这表示：

- 第 `28` 页的数据拷贝已经提交过
- 已经等待完成
- 已经做完清理
- 已经把本轮传输了多少字节、还剩多少字节，这些记账动作都做完了

换句话说：

- `page28` 这一页本身已经走完了

## 为什么当时会自然地得出“还没到 page29 before_v2p”

因为接下来我们又看了 breadcrumb 解码结果，发现：

- 最后一个稳定记录在 `page28 after_accounting`
- 没有看到稳定的 `page29 before_v2p`

所以一个非常自然的推断就是：

- 第 28 页做完了
- 第 29 页的 `before_v2p` 还没看到
- 那程序应该就是停在两者之间

这个推断**不是胡乱猜**，而是一个很自然的第一反应。

问题在于：

- breadcrumb 这种观测手段本身并不等于严格时间线

也就是说，这个推断不是完全错，而是**证据强度不够支撑“已经证明”**。

## 为什么这个推断后来被认为“说重了”

这里有两个关键原因。

### 原因一：breadcrumb 不是顺序时间日志，而是哈希槽表

breadcrumb 的槽位计算逻辑在这里：

- `src/prt_breadcrumb.c:107`

它会把这些字段混到哈希里：

- 类型
- segment
- 全局 stage 编号
- 局部 stage 编号
- subbatch
- tensor 编号
- token 编号
- manager 编号
- page 编号

但是它**不会**把这些字段混进去：

- `phase`，也就是“当前到底是 begin、end、before_v2p、after_v2p 中的哪一个阶段”
- alias `target_seq`，也就是“这是第几个别名目标”

这意味着什么？

这意味着：

- 同一页的不同阶段，可能写到同一个槽位里
- 同一页但属于不同别名目标，也可能写到同一个槽位里

因此 breadcrumb 更像：

- “每个等价类的最近一次状态”

而不是：

- “一条不丢不覆盖的时间线”

### 原因二：解码脚本只显示稳定写完的槽，不显示半写槽

解码脚本的逻辑在这里：

- `scripts/decode_prt_breadcrumb.py:169`

它只把下面两种条件同时满足的槽位打印成“有效”：

- `seq != 0`
- `seq` 是偶数

如果 `seq` 是奇数，它就不算 populated。

这其实是合理的，因为奇数 `seq` 表示：

- 这条记录正在被写
- 我们抓取文件时正好抓在中间

但是这也带来一个副作用：

- “解码结果里看不到某个槽”
  不等于
  “原始文件里那个槽真的为空”

## 这轮最关键的新发现：`slot14` 不是空的

这次我不是只看解码结果，而是直接去看 breadcrumb 原始二进制。

结果发现，两份 live capture 里的 `slot14` 都不是空的，而是完全一样的一条“半写状态”：

- `seq=503`
- `kind=dma`
- `phase=dma_submitwait_after_cleanup`
- `segment=0`
- `global_stage=0`
- `local_stage=0`
- `subbatch=3`
- `tensor=2`
- `manager=0`
- `page=19`
- `token=1176`

这里最关键的是：

- `seq=503` 是奇数

这说明：

- 这不是一个稳定完成的槽位
- 而是抓取时拍到了“写到一半”的状态

所以之前如果只看解码输出，会看到：

- `slot14` 像是空的

但看原始文件才知道：

- 它并不空
- 它只是一个奇数 `seq` 的半写槽位

## 为什么 `slot14` 特别关键

因为按当前哈希公式复算后，得到：

- `page28/token0 -> slot17`
- `page29/token0 -> slot14`
- `page30/token0 -> slot15`

同时，这次原始文件里我们看到的那条半写记录：

- `page19/token1176`

也恰好写到了：

- `slot14`

也就是说，`slot14` 同时承担了两种角色：

1. 它是我们想观察的 `page29` page-level breadcrumb 可能会写到的地方。
2. 它又已经被另一条完全不同的记录撞到了。

这就带来一个很重要的推理变化：

- 之前我们说：
  “没看到稳定的 `page29 before_v2p`，所以大概率没到那”
- 现在必须改成：
  “没看到稳定的 `page29 before_v2p`，但这一点本身带碰撞和半写歧义，不能再单独拿来当定论”

## 换句话说，现在到底能确定什么，不能确定什么

### 当前可以确定的

1. 第 28 页确实已经做完记账，也就是 `page28 after_accounting` 是真的。
2. 当前最后一个**稳定** breadcrumb 前沿就在这里。
3. `page29` 的 breadcrumb 证据目前并不干净。

### 当前不能确定的

1. 不能再说：
   “已经证明程序一定还没走到 `page29 before_v2p`”
2. 不能再说：
   “只要解码里没出现 `page29 before_v2p`，就说明它没发生”

## 接下来静态读代码，又发现了什么

接下来我又回到代码里，继续看：

- 如果程序真的还没走到 `page29 before_v2p`
- 那它到底卡在什么地方

相关代码在：

- `src/prt_dma.c:740`
- `src/prt_dma.c:904`

从第 28 页记账结束，到第 29 页真正进入 `before_v2p` 之前，代码只剩下面几步：

1. 算这页的目标偏移、目标指针、页内偏移、剩余空间、源地址、传输字节数
2. 调一次 `dma_trigger_export_host("pset", ...)`
3. 判断这页需不需要走中转缓冲区，也就是 `dma_chunk_needs_bounce(...)`
4. 如果不走中转缓冲区，才会继续：
   - 打 `v2p-b`
   - 记 `before_v2p`
   - 调 `prt_host_virt_to_phys()`

注意这里很重要：

- 在 `before_v2p` 之前，**还没有新的 DMA 提交**
- 也没有新的等待完成
- 也没有新的 ReRoCC release/fence

也就是说，这一段比之前想象得还要短。

## 为什么说“如果真卡在这之前，静态上很不好解释”

因为这几个剩余步骤，逐个看都不像“正常会卡很久”的点。

### 1. `pset` 这条触发记录，在当前配置下会很快返回

对应代码：

- `src/prt_trigger_log.c:288`

当前 run 配置里：

- `PIPELINE_RUNTIME_DEBUG_TRIGGER_ENABLE=0`

所以 `prt_trigger_log_note()` 会很早直接返回，不会真的去做格式化和写文件。

因此：

- `pset` 不是一个强嫌疑点

### 2. `page29` 不是“默认要重点打印”的页面

页面探针逻辑在这里：

- `src/prt_dma.c:1159`

默认情况下，只有下面这些页更容易被打印：

- 第 0 页
- 最后一页
- 页号大于等于 48 的页
- 或者页号是 8 的倍数的页

`page29` 不满足这些条件。

所以它不是一个默认会多打额外日志的特殊页。

### 3. `page29` 也不是默认的 chunk marker 页

chunk marker 的默认步长在这里：

- `src/prt_dma.c:1427`

默认是每隔 `32` 页打一类粗粒度标记。

所以：

- `page0`
- `page32`
- `page64`

这类页面更容易打 marker；
`page29` 不是。

### 4. `page29` 静态上不应该走中转缓冲区

中转判断逻辑在这里：

- `src/prt_dma.c:1442`

当前从 `page28` 已知地址顺推，`page29` 大致是：

- 源地址 `0x40006000`
- 目标地址 `0x103b31800`
- 传输长度 `0x400`

这两个地址的低 6 位都是 0，也就是都对齐到 64 字节。

因此静态上满足：

- 可以走直接路径
- 不需要走中转缓冲区

所以 `bounce path` 也不是一个强嫌疑点。

## 这就形成了一个有点别扭的局面

把上面两部分合起来，就得到一个“别扭但真实”的现状：

### 从证据上看

- 最后一个稳定 breadcrumb 只到 `page28 after_accounting`
- 但 `page29` 的槽位又是脏的、模糊的

### 从代码上看

- 如果程序真的还没到 `page29 before_v2p`
- 那它就得卡在一段很短、而且没有明显阻塞调用的地方

这两个观察并不完全顺滑地指向同一个结论。

这就是为什么我说：

- 现在不能再把“已经证明停在 `before_v2p` 之前”写成定论

## 为什么这次不该再把问题讲成“segment3 的多 stage 并行”

这是另一个容易混淆的地方。

之前有一些调试是围绕：

- `segment=3`
- 多个 `stage`
- 是否在同一个 hart（硬件线程）上运行

这些问题展开的。

但这一次不一样。

当前这轮我们真正盯住的是：

- `segment=0`
- `stage=0`

而且：

- `segment` 之间本来就是串行的
- 当前 `segment0` 本身就是单 stage

所以这轮局部问题，不应该再用

- “是不是别的 stage 把它覆盖了”
- “是不是 segment3 的并行导致的”

来解释。

这类并行问题不是完全不重要，但它不是这条结论的主轴。

## 这次调试结论，翻译成最朴素的话

如果不用术语，把这次结论翻译成非常直白的话，可以这样说：

- 我们**确定**程序已经把第 28 页这一步做完了。
- 我们**不再确定**程序有没有进入第 29 页的下一个关键边界。
- 因为观察第 29 页的那个“摄像头位置”本身有遮挡和拍糊的问题。
- 更麻烦的是，如果程序真没走到那个边界，那它就像是卡在一小段看起来没什么障碍的走廊里，这从代码上也很难解释。

## 当前最严谨的结论版本

到当前为止，我建议统一使用下面这段话来描述当前状态：

> 这轮 `g6 bertmini` fresh rerun 中，最后一个稳定 breadcrumb 停在
> `segment=0 stage=0 subbatch=3 tensor=2 page28 dma_page_after_accounting`。
> 这说明第 28 页的传输、等待、清理和记账都已经完成。
> 但是，当前用来观察第 29 页的 breadcrumb 槽位同时存在哈希碰撞和半写快照问题，
> 因此还不能仅凭“没看到稳定的 `page29 before_v2p`”就断定程序一定还没到那里。
> 同时，静态代码分析表明：
> 如果程序真的停在 `page29 before_v2p` 之前，
> 那它会停在一段很短、且缺少明显阻塞调用的代码里。

## 这对下一步调试意味着什么

这意味着下一轮调试，不能再继续依赖当前这个模糊槽位去做强判断。

更合适的下一步是：

1. 设计一个新的低扰动观测点。
2. 这个观测点不要再复用当前 `slot14` 的等价类。
3. 目标是明确区分两种情况：
   - 情况 A：程序真的还没走到第 29 页的下一步
   - 情况 B：程序其实走到了，但当前 breadcrumb 记录方式把证据写花了

如果做不到这一点，就会一直在：

- “看起来像没到”
- “但也可能到了只是没记录清楚”

之间反复摆动。
