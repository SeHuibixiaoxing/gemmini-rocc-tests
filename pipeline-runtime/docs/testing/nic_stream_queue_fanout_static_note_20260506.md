# NIC Stream Queue Fanout Static Note - 2026-05-06

## Context

During monitoring of the active `12p dummy8x8/sbus64/cfg32/NIC/noTrace`
TIMING build, Vivado placer/physopt reported many very-high-fanout messages
under:

```text
WRAPPER/CL/firesim_top/top/CPUManagedStreamEngine_0/
  SIMPLENICBRIDGEMODULE_0_from_cpu_stream_incomingQueueIO_q/
    enq_ptr_value_reg[...]
```

At the same checkpoint, the build had not shown the old route-failure
signatures:

- no `Route 35-162`
- no `Route 35-2`
- no failed-routing signal count
- no node-overlap count

So this note is not a failure diagnosis yet. It records a plausible placement
pressure source to keep ready if the current builds later fail in route.

## Static Source Path

The relevant host-stream hardware is generated by FireSim/MIDAS, not by the
Gemmini pair-manager datapath itself.

Key files:

- `generators/firechip/goldengateimplementations/src/main/scala/SimpleNICBridge.scala`
- `sims/firesim/sim/midas/src/main/scala/midas/core/CPUManagedStreamEngine.scala`
- `sims/firesim/sim/midas/targetutils/src/main/scala/midas/Utils.scala`
- `sims/firesim/sim/rocket-chip/dependencies/chisel/src/main/scala/chisel3/util/Decoupled.scala`

SimpleNIC sets both CPU-managed stream queue depths to `TOKEN_QUEUE_DEPTH`:

```scala
val TOKEN_QUEUE_DEPTH = 3072
...
val fromHostCPUQueueDepth = TOKEN_QUEUE_DEPTH
val toHostCPUQueueDepth   = TOKEN_QUEUE_DEPTH
```

`CPUManagedStreamEngine` then builds the actual from-host queue:

```scala
val incomingQueueIO = FireSimQueueHelper.makeIO(
  UInt(BridgeStreamConstants.streamWidthBits.W),
  chParams.fpgaBufferDepth,
  isFireSim     = true,
  overrideStyle = Some(xdc.RAMStyles.ULTRA),
)
```

`FireSimQueueHelper.makeIO` instantiates a standard Chisel `Queue` with
`useSyncReadMem = isFireSim`, and the helper adds an UltraRAM style hint when
requested.

## Why This Can Become High Fanout

The Chisel `Queue` has these core state elements:

```scala
val enq_ptr = Counter(entries)
val deq_ptr = Counter(entries)
val maybe_full = RegInit(false.B)
val ptr_match = enq_ptr.value === deq_ptr.value
val empty = ptr_match && !maybe_full
val full = ptr_match && maybe_full
...
io.count := ...
```

For SimpleNIC, `entries = 3072` and the element width is the FireSim bridge
stream width. That makes each stream FIFO a large memory-backed queue. The
enqueue pointer bits do several jobs at once:

- select the write address across many inferred RAM blocks
- drive `full` and `empty` comparison logic
- contribute to `io.count`
- feed the MMIO-visible stream count register attached by
  `CPUManagedStreamEngine`
- participate in ready/valid backpressure for the CPU-managed stream path

This explains why Vivado reports high fanout on
`incomingQueueIO_q/enq_ptr_value_reg[...]`. The signal is a queue address/count
control bit with loads spread across a large inferred FIFO and host-control
logic.

## Relation To Current Resource Results

This is consistent with the formal resource comparison from the active
`12p dummy8x8/sbus64` build:

- `CPUManagedStreamEngine_0` total LUT stayed at about `32,252` when moving
  from dummy16x16/sbus128 to dummy8x8/sbus64.
- `SimpleNICBridgeModule_0` total LUT stayed at about `1,565`.
- `IceNIC` total LUT stayed at about `4,711/4,712`.

So the NIC/stream-engine pressure is mostly fixed cost. Cutting Gemmini mesh
size or sbus width does not materially shrink this block.

## Current Interpretation

This high-fanout queue is not automatically the root cause of the earlier route
failure. The old failing 12p dummy16x16/sbus128 build had congestion markers
spread across target-side ReRoCC/Gemmini/DMA/NoC names as well.

However, the queue is a credible contributor to placement pressure because:

- it uses large memory-backed stream FIFOs
- its control signals span RAM, count, and ready/valid logic
- Vivado specifically reports timing constraints preventing full VHFN
  optimization on the pointer nets
- physopt only replicated a small subset of candidate nets

If the current builds fail at route with the same kind of local congestion, this
block should be treated as one of the next levers, especially for NIC-enabled
pipeline-runtime debug bitstreams.

## Candidate Mitigations If Route Fails

These are not applied to the active builds.

1. Reduce `TOKEN_QUEUE_DEPTH` for the SimpleNIC debug-only bitstream.

   This directly shrinks the large CPU-managed NIC stream FIFOs and may reduce
   RAM banking plus pointer fanout. Risk: host/target network burst tolerance
   decreases. It should be tested with the old gdbserver capability matrix:
   connect, multiple breakpoints, continue/next, memory/register access,
   Ctrl-C, detach.

2. Add a config-level NIC debug queue-depth override instead of changing the
   global SimpleNIC default.

   This is safer than a broad source edit because the throughput-sensitive
   FireSim NIC configurations can keep the existing depth, while
   gdbserver/pipeline-runtime debug builds use the smaller queue.

3. Register or localize the MMIO count path.

   This may reduce count/control fanout, but it is riskier because the host
   stream driver polls queue count before issuing reads. Previous debugging
   showed that hiding tokens behind an adapter can deadlock the stream, so any
   count-path change must preserve externally visible queue occupancy semantics.

4. Avoid adding more NIC observability counters unless a build variant is
   explicitly meant to diagnose this block.

   The current route-risk direction is to reduce fixed bridge pressure, not add
   wider debug state around the stream queue.

## Decision For Active Builds

Do not change this path while the current TIMING builds are still running.

The active experiments already test two resource reductions:

- `12p dummy8x8/sbus64/cfg32/NIC/noTrace`
- `8p dummy16x16/sbus128/cfg32/NIC/noTrace`

If either build routes successfully, reducing SimpleNIC queue depth may be
unnecessary. If both fail with route congestion, a debug-only NIC stream
queue-depth override is a high-value next experiment because it targets a fixed
pressure block that the Gemmini/sbus reductions do not reduce.

## Current-vs-Main Static Audit - 2026-05-06 19:32 UTC

I compared the active local sources against local `main` while the two TIMING
builds were still running.

The current `SimpleNICBridge.scala` differs heavily from `main`:

```text
goldengateimplementations/src/main/scala/SimpleNICBridge.scala | 1426 +++++++++++++++++++-
```

That diff is not one uniform "debug only" change. It contains several
categories with different rollback risk:

| Change class | Examples | Rollback risk |
|---|---|---|
| Functional stream fixes | `BigTokenToNICTokenAdapter` latches a 512-bit big token before emitting 7 64-bit tokens; `NICTokenToBigTokenAdapter` can flush on `data_out.last`; `pcieOutQ` decouples target-to-host packing from PCIE stream backpressure; host IO is channelized instead of one monolithic `HostPort` bundle. | High. These changes are tied to the 1bp recovery history and should not be removed just to reduce resources. |
| Deadlock/corruption fixes in CPU-managed stream | `StreamWidthAdapter` wide-to-narrow path uses `wide_data`/`wide_valid`; to-host dequeue is gated by `readRequestActive = grant && axi4.ar.valid` so queue occupancy is not hidden from the host driver. | High. Historical records show the ungated prefetch variant can deadlock because the host polls queue count before issuing reads. |
| Observability | Many counters/snapshots/CR attachments, `minobs_build_marker = 0x05040003`, last-word captures, progress/blockage masks. | Medium. These can be reduced for a low-observability build, but they are not the first resource lever unless route fails narrowly and the candidate is otherwise close. |

The static audit therefore does not support reverting the whole
`SimpleNICBridge.scala` diff to `main`. The current bridge behavior is part of
the 1bp recovery path, and the mainline version was already identified in
earlier records as having token drift / lockstep risks for this workload.

The resource evidence also argues against treating SimpleNIC observability as
the main congestion lever:

- In the formal post-synth reports, `SimpleNICBridgeModule_0` is only about
  `1,565` LUT and `1,892` FF in the 8p build.
- `CPUManagedStreamEngine_0` is about `32,252` LUT and is unchanged by Gemmini
  mesh/sbus reductions.
- The placer high-fanout message names the CPU-managed incoming queue pointer,
  not one of the added SimpleNIC debug counters.

Practical implication:

1. Keep the functional 1bp stream fixes intact for the active line.
2. If route fails, first consider a debug-only SimpleNIC stream queue-depth
   override because it directly targets the large fixed FIFO block and pointer
   fanout.
3. A low-observability SimpleNIC rebuild is still a reasonable second
   experiment, but it should preserve `readRequestActive`, `wide_valid`,
   `pcieOutQ`, channelized host IO, and the conservative from-host payload
   buffering. Removing those would mix a resource experiment with a functional
   regression risk.
